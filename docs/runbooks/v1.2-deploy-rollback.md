# v1.2 deploy and rollback — GB10 (private) and Fly (public)

Written 2026-09-12 for the X0 deploy of Phases A + B, from a read-only
pre-flight of both estates (8 probes) and four adversarial reviews of the
first runbook (data loss, blast radius, ordering, false green). Every fix those
reviews asked for is built in below. Later phases reuse this document and
record their own pins.

**Read §0 before running anything.** Several steps are one-way.

---

## 0. What can and cannot be undone

| Step | Reversible? | How | Why not, if not |
|---|---|---|---|
| New images built beside the running stack | Yes | Containers keep their image IDs until recreated | — |
| Recreate onto v1.2 images | Yes, until the registry first opens | Re-tag `:pre-v1.2`, recreate | — |
| **Registry schema migration** | **No — from the v1.2 registry's first start** | R1 down-migration, or R2 restore | `RegistryStore.__init__` runs `ALTER TABLE` on open; the pre-v1.2 image's positional 8-value `INSERT` then fails, so `POST /agents` is a 500 |
| Ledger events written after the deploy | **No** without losing them | R2 restores the chain to the backup and drops them | A hash chain cannot have events removed from the middle; restoring truncates |
| Attestations, decommissions | Only by R2 (lost) or R1 (attestation columns dropped) | — | They are ledger events too |
| Fly machine image | Yes | `fly deploy --image <previous ref>` | — |
| Fly volume contents | Only by snapshot restore to a NEW volume | F-R2 | Fly snapshots restore to a new volume, never in place |
| **Ledger rotation (C-gate step 3)** | **No, for any image or CLI older than Phase C** | Images from Phase C on read it. Below Phase C: fix forward (§3, "After the C-gate rotation"); the verified merge there is an exception only Don can decide | A pre-C2 store reads `events.jsonl` alone: it reports `link break at index 0`, `/health` counts only the open segment, and its `verify --anchors` cannot parse a rotation anchor |
| GB10 `field-manifests` volume (Phase C) | Yes, with R1 step 4 | Copy the volume back onto `field-data` before the compose files are reverted | A pre-Phase-C compose file mounts nothing over `/data/manifests`, so every reader falls back to the frozen `field-data` copy, without anything installed since the seed |
| **Spend-governor D1 migration** (Phase D) | **No — from the D1 governor's first start** on the persisted `governor/spend.sqlite3` | R2 restores the pre-deploy file; or, with the stack stopped, `DROP INDEX idx_spend_agent_action_ts; ALTER TABLE spend DROP COLUMN source; ALTER TABLE spend DROP COLUMN action;` (rows kept, sentinel/self attribution lost; the new `rate_limits` table is left, and a pre-D1 image ignores it) | The D1 governor migration RUNS AT OPEN: `GovernorStore.__init__` adds `spend.action` and `spend.source` (PRAGMA, then `ALTER TABLE`). A pre-D1 image's positional 7-value `INSERT INTO spend` then fails ("table spend has 9 columns but 7 values were supplied"), so every `POST /governor/spend` is a 500. The down-migration and that failure were run on Windows SQLite 3.50.4 against the fixture DDL (not under docker, not on an estate) |
| Delegation token spend ceilings (Phase D, D1e) | Yes | — | The D1e `TokenStore` creates a side table, `token_spend_ceilings`, at open and never alters `tokens`. A pre-D1e image's positional 9-value `INSERT INTO tokens` still mints and revokes on that file (`services/delegation-authority/tests/test_d1e_token_ceiling.py`, the HEAD statements verbatim), it never reads the side table, and its mints carry no ceiling; ceilings already stamped are served again once the D1e image is back |
| Crosswalk regwatch state (Phase D) | Yes | — | A pre-D4 image ignores the stale-flags file's `sources` and `last_check` keys and drops them on its next write (the next D4 check re-baselines, no false flag), and ignores the zero-byte `crosswalk_stale_flags.json.lock` sidecar |

**Fix-forward rule.** Once a one-way step has run, a failed verification is
fixed forward unless the estate is unusable. Rollback order is always
disarm env/secrets → images → data. Data restore is the last resort.

**The GB10 shares its host** with unrelated live workloads (SpinTrader IB
gateway and TimescaleDB, open-webui, oikb, openapi-*, msexcel, open-terminal).
Every command below is scoped to compose project `field-platform` or names a
`field-platform-*` container. Never run `docker system prune`, `image prune`
or `volume prune` on this host: they would delete the rollback images.

## 2. GB10 deploy

`F="-p field-platform -f integration/demo/docker-compose.yml -f integration/demo/docker-compose.gb10.yml"`
and every command runs from `~/field-platform`.

### 2.1 Before the outage (nothing stops)

1. **State gate.** Every `field-platform-*` container is the one pinned in §1,
   and the ledger count equals the pin. Anything else means another operator
   or a write happened — stop and find out.
2. **Preserve the running images by image ID**, never from `:latest` (which
   the new build overwrites):
   ```bash
   for c in $(docker ps --filter label=com.docker.compose.project=field-platform --format '{{.Names}}'); do
     svc=$(docker inspect -f '{{index .Config.Labels "com.docker.compose.service"}}' "$c")
     img=$(docker inspect -f '{{.Image}}' "$c")
     docker tag "$img" "field-platform-$svc:pre-<phase>"
   done
   ```
3. **Save them to disk**, so a prune elsewhere on the host cannot destroy the
   rollback target once no container references them:
   ```bash
   docker save $(docker images --format '{{.Repository}}:{{.Tag}}' | grep ':pre-<phase>$') \
     python:3.12-slim | gzip > ~/field-backups/images-pre-<phase>.tar.gz
   ```
4. **Git marker**: `git tag -f pre-<phase>-gb10 HEAD` (local, not pushed), then
   `git pull --ff-only` and assert `git rev-parse HEAD` equals the deploy SHA.
5. **Build** with `FIELD_BUILD_SHA=$(git rev-parse HEAD) docker compose $F build`.
   The old stack keeps serving. The variable is a build argument baked into
   every image and reported as `build_sha` by every `/health`; without it they
   report `unknown` and §2.3's `--expect-build-sha` fails. Never put it in
   `.env`, where a stale value would be baked into every later build.
   Record the new image IDs (`docker images -q field-platform-<svc>:latest`)
   to `~/field-backups/image-ids-built-<phase>.txt` — §3 compares running
   containers against THIS file, not against a mutable tag.

### 2.2 The outage window

6. **Re-run the state gate** in the same shell, immediately before stopping.
7. **Quiesce**: `docker compose $F stop`.
8. **Quiesced backup, promoted only after it verifies**:
   ```bash
   TS=$(date -u +%Y%m%dT%H%M%SZ); B=~/field-backups/field-data-pre-<phase>-quiesced-$TS.tgz
   docker run --rm --pull never --network none -v field-platform_field-data:/data:ro \
     --entrypoint tar python:3.12-slim -C /data --numeric-owner -czf - . > "$B.partial"
   gzip -t "$B.partial"
   V=$(mktemp -d); tar -xzf "$B.partial" -C "$V"
   # The ledger gate uses the ledger CLI of the image built in step 5 on the
   # extracted copy: it verifies every live segment from GENESIS and prints the
   # GLOBAL length. Never `wc -l ledger/events.jsonl`: after the C-gate
   # rotation that counts only the open segment.
   LV="docker run --rm --pull never --network none -v $V:/v:ro field-platform-ledger:latest"
   $LV ledger verify --path /v/ledger/events.jsonl
   #   exit 0, first line "OK — chain intact over <pinned count> events"
   #   (a rotated ledger adds "(<n> segments, 0 archived; ...)")
   test "$($LV python -c "from sealed_ledger.store import LedgerStore as S; h = S('/v/ledger/events.jsonl').health_info(); print(h['event_count'], h['head_hash'])")" \
     = "<pinned count> <pinned head_hash>"
   #   PRAGMA integrity_check on every *.sqlite3 in $V must print ok
   mv "$B.partial" "$B"; chmod 600 "$B"
   sha256sum "$B" > "$B.sha256"
   echo "$B" > ~/field-backups/RESTORE_SOURCE        # the ONLY file R2 may restore
   ```
   From the Phase C deploy on, the GB10 also has the `field-manifests` volume
   (readers no longer see `field-data`'s copy of `/data/manifests`). Back it up
   the same way. The `if` keeps `docker run -v` from creating an empty volume
   on the Phase C deploy itself, where step 9's first `up` creates and seeds it:
   ```bash
   if docker volume inspect field-platform_field-manifests >/dev/null 2>&1; then
     M=~/field-backups/field-manifests-pre-<phase>-quiesced-$TS.tgz
     docker run --rm --pull never --network none -v field-platform_field-manifests:/m:ro \
       --entrypoint tar python:3.12-slim -C /m --numeric-owner -czf - . > "$M.partial"
     gzip -t "$M.partial"
     W=$(mktemp -d); tar -xzf "$M.partial" -C "$W"
     test -s "$W/.field-manifests-seeded.json"          # a seeded volume, not an empty one
     docker run --rm --pull never --network none -v field-platform_field-manifests:/m:ro \
       --entrypoint sh python:3.12-slim -c 'cd /m && find . -type f -exec sha256sum {} + | sort' > "$M.sums"
     (cd "$W" && find . -type f -exec sha256sum {} + | sort) | diff - "$M.sums"   # must print nothing
     mv "$M.partial" "$M"; chmod 600 "$M"; sha256sum "$M" > "$M.sha256"
     echo "$M" > ~/field-backups/RESTORE_SOURCE_MANIFESTS
   fi
   ```
   `field-keys` is deliberately NOT backed up: the anchor private key stays on
   the box, and its public key is kept off-box at A4 (§4).
   **If any check fails: abort (§2.4). Do not continue to step 9.**
9. **Bring v1.2 up, every container recreated**:
   `docker compose $F up -d --no-build --force-recreate`.
   `--force-recreate` is required: the proxy's config hash does not change, so
   without it the proxy keeps the old Caddyfile inode in memory and the new
   prefixes (`/lifecycle`, `/attest`, `/crosswalk`) silently fall through to the
   console.
   From the Phase D deploy on, spend-governor is recreated with or before
   conformance-sentinel (this step recreates both). A D1 sentinel in front of a
   pre-D1 governor ledgers `sentinel.metering_gap` on every ALLOW (the governor
   422s the new keys) and gets no throttle. The D1 governor's first start on
   the persisted `spend.sqlite3` is one-way for older images (§0).
   The X4 `witness` is behind the compose profile `witness`: until A5 puts
   `COMPOSE_PROFILES=witness` in `integration/demo/.env`, neither step 5's build
   nor this `up` includes it, and lifecycle's `FIELD_WITNESS_EVERY` is blank (no
   witness finding). `docker compose $F config --services | grep -x witness`
   prints nothing before A5. Once A5 is armed, both include it like any other
   service, and this deploy's `collateral --allow` adds `<none>:anchor.remote`.
   The X3 `canary-agent` is the same shape behind the profile `x3`: until A6
   (§4, "X3 halt endpoint (A6)") neither the build nor this `up` includes it,
   and `FIELD_KILL_ENDPOINT_ALLOWLIST` stays unset, so every kill ledgers
   `kill.endpoint_skipped`. Once armed, this `up` recreates it (a halted
   canary comes back not halted).
10. **Copy the quiesced backup off the host**, from rog-command:
    `scp gx10:$(ssh gx10 cat ~/field-backups/RESTORE_SOURCE)* <local safe dir>`,
    then `sha256sum -c` on the local copy.

### 2.3 Verify (evidence that can fail)

- Every running container's image ID equals `image-ids-built-<phase>.txt`.
- `python3 tools/estate_probe.py --base http://127.0.0.1:18080 health` — every
  prefix answers 200 **and** names the right service. A console fall-through
  names `ops-console` and fails. From Phase C on, add
  `--expect-build-sha $(git rev-parse HEAD)`: every `/health`, the console's
  included, must report the label step 5 baked in. A container that was not
  recreated reports a different one.
- `estate_probe.py … continuity --count <pin> --hash <pin head>` — history
  unchanged.
- Restart counts read twice, 60 s apart, and unchanged
  (`docker inspect -f '{{.RestartCount}}'`). A single early read hides a
  crash loop.
- Log scan with the exit status checked:
  `docker compose $F logs --since 10m 2>&1 | grep -ciE 'traceback|error' ; echo "pipe=${PIPESTATUS[0]}"`
  — `pipe` must be 0, or the count is meaningless.
- Canary checks per the plan (§4).
- From the Phase D deploy on the gateway is keyless-real: `/gateway/health`
  reports `mock: false`, and `POST /gateway/v1/messages` answers 502 naming
  `ANTHROPIC_API_KEY` until Don places the key (GB10 `integration/demo/.env`,
  Fly `fly secrets set`). That 502 is the expected state, not a failed deploy.
  With `FORCE_GATEWAY_URL` estate-wide, a judge-on sentinel or crosswalk
  suggester also depends on forcegw holding the key.

### 2.4 Abort during the outage (backup check failed)

`docker compose start` cannot restart the old stack: by now the checkout is
v1.2, compose loads the 14-service project, the three new services have no
containers, and the proxy — which depends on them — never starts. Start the
old containers directly, dependencies first:

```bash
docker start field-platform-ledger-1 field-platform-registry-1 field-platform-delegation-1 \
  field-platform-governor-1 field-platform-killswitch-1 field-platform-sentinel-1 \
  field-platform-replay-1 field-platform-forcegw-1 field-platform-fedbroker-1 field-platform-console-1
docker start field-platform-proxy-1
curl -sS --retry 12 --retry-delay 5 --retry-connrefused http://127.0.0.1:18080/ledger/health
```
Expect the pinned `event_count`. The restarted proxy re-reads the NEW Caddyfile,
so the three new prefixes answer 502 until the deploy resumes; the ten
existing prefixes work.

## 3. GB10 rollback

### After the C-gate rotation — read before R1 or R2

The ledger has rotated once `docker exec field-platform-ledger-1 test -e
/data/ledger/events.segments.journal` succeeds, or `/ledger/verify` (with the
`x-field-auth` header once the secret is armed) carries a `segments` key.
C-gate step 3 does this once per estate. From then
on `/data/ledger` holds `events-1.jsonl` (closed), `events.jsonl` (open),
`events.segments.journal` and `.events.jsonl.lock`, and:

- **No image or CLI older than Phase C may serve or read it.** Measured with
  the db5ad33 code on a rotated 59-event ledger (Windows, fix-round evidence,
  not on an estate): `verify` says `link break at index 0`, the store sees 4
  events, `ledger verify --path` prints `TAMPERED` and exits 1, and
  `load_anchors` raises `ValidationError` on a file holding a rotation anchor.
  So R1 and R2 step 4 go back only to images from Phase C on. Below Phase C
  the plan's rule holds: **fix forward**.
- **Rotation anchors go in their own file**, shipped off-box. `ledger rotate`
  runs INSIDE the ledger container (GB10) or the machine (Fly), so its
  `--anchors` path is a path in THAT filesystem: a host path such as
  `~/field-backups/...` would land in the container's own filesystem and be
  lost when the container is recreated. Write it under the persisted `/data`
  volume, then copy it off the host (the C-gate block in §4 has the exact
  commands):
  - GB10: `docker exec field-platform-ledger-1 ledger rotate --operator "<name>"
    --reason "<why>" --anchors /data/rotation-anchors/rotation-anchors-gb10.jsonl`
    (on field-data, so it survives a recreate), then on the GB10
    `docker cp field-platform-ledger-1:/data/rotation-anchors/rotation-anchors-gb10.jsonl ~/field-backups/`
    and on rog-command `scp gx10:field-backups/rotation-anchors-gb10.jsonl <local safe dir>/`.
  - Fly: `fly ssh console --app force-field-sandbox -C "env
    FIELD_LEDGER_URL=http://127.0.0.1:8002 ledger rotate --operator '<name>'
    --reason '<why>' --anchors /data/rotation-anchors/rotation-anchors-fly.jsonl"`
    (on `ff_data`), then on rog-command
    `fly ssh sftp get /data/rotation-anchors/rotation-anchors-fly.jsonl <local safe dir>/rotation-anchors-fly.jsonl --app force-field-sandbox`.

  The `anchor` object of the `POST /ledger/rotate` response (also in the
  printed result) carries the same signed anchor. Never append one to an anchors file that `ledger verify --anchors`
  reads with older code.
- **The backup gate** is §2.2 step 8 as written: `ledger verify` and
  `health_info()` of the newly built image report the global length and head.
  Do not use a line count.
- **R2 with a backup taken before the rotation** restores a single-file
  ledger without the rotation event. Record the cut as in R2 step 5, and
  treat the rotation as lost: the anchor key signed a head the ledger no
  longer ends at.

**The one exception: merging to a single file.** Only when Don decides that
a pre-Phase-C image must run again, and the decision is recorded in STATE.md
first. The stack is stopped and R1 steps 1–2 are done. `NEW` is the Phase C (or
later) ledger image and `OLD` is the image being restored. The merge keeps every
event and moves nothing but files. It was verified on Windows against the
db5ad33 code, with the shell run by Git's `sh`. It has NOT been run under
docker or on an estate:

```bash
NEW=field-platform-ledger:latest; OLD=field-platform-ledger:pre-<phase>
D="docker run --rm --pull never --network none"
$D -v field-platform_field-data:/data:ro $NEW ledger verify --path /data/ledger/events.jsonl
#   exit 0: "OK — chain intact over <G> events" and "(<n> segments, 0 archived; ...)".
#   Anything archived (retention apply ran): STOP, the archive copies are not merged here.
$D -v field-platform_field-data:/data:ro $NEW python -c "from sealed_ledger.store import LedgerStore as S; h = S('/data/ledger/events.jsonl').health_info(); print(h['event_count'], h['head_hash'])"
#   record: <G> <head>
$D -v field-platform_field-data:/data --entrypoint sh $NEW -c '
  set -e
  cd /data/ledger
  test ! -e .merged-events.jsonl
  test -s events.segments.journal
  n=0; while [ -e "events-$((n+1)).jsonl" ]; do n=$((n+1)); done
  test "$n" -ge 1
  test "$(ls events-*.jsonl | wc -l)" -eq "$n"
  set --; i=1
  while [ "$i" -le "$n" ]; do set -- "$@" "events-$i.jsonl"; i=$((i+1)); done
  cat "$@" events.jsonl > .merged-events.jsonl
  echo "merged $n closed segment(s) and events.jsonl"'
$D -v field-platform_field-data:/data:ro $OLD ledger verify --path /data/ledger/.merged-events.jsonl
#   exit 0: "OK — chain intact over <G> events" (the OLD code, from GENESIS)
$D -v field-platform_field-data:/data:ro $OLD python -c "from sealed_ledger.store import LedgerStore as S; print(S('/data/ledger/.merged-events.jsonl').head_hash)"
#   == <head>. Only now swap, keeping the segments beside the ledger (nothing is deleted):
$D -v field-platform_field-data:/data --entrypoint sh $NEW -c '
  set -e
  cd /data
  KEEP=ledger-c2-segments-$(date -u +%Y%m%dT%H%M%SZ)
  mkdir "$KEEP"
  mv ledger/events-*.jsonl ledger/events.segments.journal ledger/events.jsonl "$KEEP"/
  if [ -e ledger/.events.jsonl.lock ]; then mv ledger/.events.jsonl.lock "$KEEP"/; fi
  mv ledger/.merged-events.jsonl ledger/events.jsonl
  ls -A ledger "$KEEP"'
```

In the fix-round run, the pre-C2 service on the merged file answered `/health`
59 and `/verify` ok, appended with 201, and its `verify --anchors` still held
the two pre-rotation anchors. When the Phase C code rolled forward onto the
merged file, it verified the whole chain (the rotation event is an ordinary
event in it) against the separate rotation-anchor file and rotated again. The
rotation is no longer journaled after this: `segments` is gone from `/verify`.

### R1 — code rollback, keep the data

Use when v1.2 misbehaves but the data is sound and post-deploy events must
survive.

1. `docker compose $F stop`.
2. **Forensic copy, verified and off-host** before anything is changed:
   ```bash
   FC=~/field-backups/field-data-post-<phase>-failed-$(date -u +%Y%m%dT%H%M%SZ).tgz
   docker run --rm --pull never --network none -v field-platform_field-data:/data:ro \
     --entrypoint tar python:3.12-slim -C /data --numeric-owner -czf - . > "$FC"
   gzip -t "$FC" && tar -tzf "$FC" >/dev/null && sha256sum "$FC" > "$FC.sha256"
   ```
   then `scp` it to rog-command.
3. **Registry down-migration** — records the attestations it drops to a file
   and prints the count:
   ```bash
   docker run --rm --pull never --network none -v field-platform_field-data:/data \
     -v ~/field-backups:/b --entrypoint python field-platform-registry:pre-<phase> -c "
   import sqlite3, json
   c = sqlite3.connect('/data/registry/agents.sqlite3')
   cols = [r[1] for r in c.execute('PRAGMA table_info(agents)')]
   rows = c.execute('SELECT agent_id, attested_at, attested_by FROM agents WHERE attested_at IS NOT NULL').fetchall() if 'attested_at' in cols else []
   json.dump(rows, open('/b/attestations-dropped-by-R1.json', 'w'))
   for col in ('attested_by', 'attested_at'):
       if col in cols: c.execute('ALTER TABLE agents DROP COLUMN ' + col)
   c.commit()
   print('dropped', len(rows), 'attestations; columns', len([r for r in c.execute('PRAGMA table_info(agents)')]),
         'integrity', c.execute('PRAGMA integrity_check').fetchone()[0])"
   ```
   Expect `columns 8`, `integrity ok`. Run this ONLY with the stack stopped — a
   running v1.2 registry re-adds the columns on its next open.
4. **Manifests, when going from a Phase C GB10 back to a checkout before Phase
   C.** The old compose files mount nothing over `/data/manifests`, so readers
   see `field-data`'s frozen copy again. Copy the volume onto it first, and
   check every byte. The install log lists each file that changed since the
   seed:
   ```bash
   docker run --rm --pull never --network none -v field-platform_field-manifests:/m:ro \
     -v field-platform_field-data:/data --entrypoint sh python:3.12-slim -c '
     set -e
     test -s /m/.field-manifests-seeded.json
     mkdir -p /data/manifests
     cp -a /m/. /data/manifests/
     (cd /m && find . -type f -exec sha256sum {} +) | (cd /data/manifests && sha256sum -c --quiet -)
     echo "carried back: $(find /m -type f | wc -l) file(s)"
     cat /m/.field-manifests-installs.jsonl 2>/dev/null || echo "(no install since the seed)"'
   ```
   The volume itself is left in place (step 7's `--remove-orphans` removes
   only the `manifests-admin` container). Skip this step when the target
   checkout is Phase C or later. Checked on plain directories with the real
   `volume_admin.py` (fix-round evidence); not run under docker.
5. `git reset --hard pre-<phase>-gb10`. After the C-gate rotation, only to a
   Phase C (or later) tag (see above).
6. Point `:latest` back at the preserved images (reload them from
   `images-pre-<phase>.tar.gz` with `docker load` if a prune removed them):
   `for s in …; do docker tag field-platform-$s:pre-<phase> field-platform-$s:latest; done`
7. `docker compose $F up -d --no-build --force-recreate --remove-orphans`.
8. Verify with `estate_probe.py … health --only registry,ledger,delegation,sentinel,killswitch,governor,replay,gateway,federation`
   and `continuity` against the §1 pin.

### R2 — full data restore (loses every write after the backup)

Use only when the data itself is wrong. **Never restore a file that is not
named in `RESTORE_SOURCE`** — a newer tarball may be a failed or post-deploy
copy under a "pre" name.

1. Do R1 steps 1 and 2 (stop; verified off-host forensic copy). The forensic
   copy is the only record of the events R2 is about to discard.
2. Verify the restore source BEFORE touching `/data`:
   ```bash
   B=$(cat ~/field-backups/RESTORE_SOURCE)
   sha256sum -c "$B.sha256" && gzip -t "$B"
   ```
3. Unpack beside, verify, then swap — `/data` is never empty for a moment in
   which a check could still fail:
   ```bash
   docker run --rm --pull never --network none -v field-platform_field-data:/data \
     -v "$(dirname "$B")":/b:ro --entrypoint sh python:3.12-slim -c "
     set -e; rm -rf /data/.restore; mkdir /data/.restore
     tar -xzf /b/$(basename "$B") -C /data/.restore
     test -s /data/.restore/ledger/events.jsonl
     find /data -mindepth 1 -maxdepth 1 ! -name .restore ! -name lost+found -exec rm -rf {} +
     cp -a /data/.restore/. /data/ && rm -rf /data/.restore"
   ```
4. R1 steps 4–7 (manifests carried back when going below Phase C, code and
   images back, recreate). After the C-gate rotation, see the block above R1
   first.

## 4. Canary (live checks that mutate state)

No live check kills, revives, drills, throttles, mints for, revokes for or
attests a real agent. `tools/estate_probe.py` enforces this in code: mutating
subcommands accept only the EXACT ids `canary-gb10` / `canary-fly`, confirm the
registry record's domain is `canary`, and confirm the token belongs to that
canary before changing anything (an adversarial review showed a name prefix
alone let a real agent called `canary-release-bot` be killed and re-attested).

Each estate carries two canary records:

| Record | Purpose | State |
|---|---|---|
| `canary-<estate>` | every mutating live check | active, never decommissioned |
| `canary-<estate>-retired` | the ONLY legal target of `refused-kill` | retired |

`refused-kill` fires a kill that the platform must refuse. Aiming it at a
retired canary means a broken retired-guard — the exact failure it exists to
catch — can only ever damage that record, never a real agent.

same commands over `fly ssh console`). The manifest is always in place first:

`crosswalk regwatch clear` that logs `waiting for the store lock` is waiting
on a running check, for up to 30 s; then it fails with `StoreLockTimeout`
(exit 1, nothing written) and is simply re-run.

### X3 halt endpoint (A6) — GB10 only, scoped to `canary-agent` and the kill-switch

What it proves: a kill of `canary-gb10` really calls an agent-side process,
and that process stops its work and says so. `canary-agent` (compose profile
`x3`, `integration/demo/docker-compose.gb10.yml`) runs `python -m
field_agent.canary serve`: `POST /halt` (no field authn; requires
`x-field-kill-origin: kill-switch`; answers 200 with the nonce parsed from the
kill reason `x3-<nonce>`, which the kill-switch sends in `x-field-kill-reason`;
stops its work loop and never exits) and `GET /status` `{halted, nonce,
since, ...}`. It has no published port: the kill-switch reaches it as
`http://canary-agent:8090/halt`, exactly what `manifests/canary-gb10.yaml`
declares. A halt is sticky until the container restarts; a `/revive` flips
the registry, not the process. The origin header is a marker, not
authentication: anything on the compose network can halt the canary.

Pre-conditions: the Phase D image is deployed (it installs
`packages/field-agent`); `canary-gb10` is provisioned, `active`, domain
`canary` (§4); `manifests-admin install canary-gb10.yaml` has run.
