# C-201 reviewer report (Lane 5): comms/tools/gx10_verify.sh (independent read of R-21)

VERDICT: the script is a sound CI-equivalent runner for the `tests` job with FOUR findings: one step of that job is missing (MEDIUM), a failed fetch of the requested ref silently tests a different commit (MEDIUM, proven), a green `--quick` run prints a GREEN verdict line next to a NOTE that says it is not a full run (LOW), and the secret scrub list is short (LOW). Its numbers match every known baseline, and a deliberately failing test turns the verdict RED with exit status 1.

OBJECTIONS FIRST
1. It is a mirror, and a mirror drifts: the file header says it mirrors ci.yml "checked against main 444e49b"; ci.yml has changed since, and the one step I found missing is exactly the kind a later edit adds. Nothing in the repo compares the script to the workflow. [HIGH]
2. It runs on one Python (3.12.3 in the GX10 venv) against a CI matrix of 3.11, 3.12, 3.13 and 3.14, with PYTHONPATH of source directories instead of CI's `pip install -e`. Green here proves the code and tests on one interpreter with source-path imports; it does not prove packaging (entry points, package data, missing `__init__`) or the other three interpreters. [HIGH]
3. The script is a reviewer's own tool and the reviewer who wrote it (R-21) is not me, but I am reading a script whose output I have been using for my own verdicts in this session (C-204, C-206). If it were wrong in a way my cross-checks missed, those verdicts share the flaw. My cross-checks: the baseline numbers (below) and one negative control. [HIGH]
4. Skips are not failures (a skipped test counts as pass); there is no skip budget (card C-149 covers CI). The script prints skip counts but does not gate on them. [HIGH]

ASSUMPTIONS

2. ci.yml read on origin/main 7b54f26, `tests` job (the three docker jobs are out of the script's stated scope). [HIGH]

REASONING
1. Service lists. ci.yml "Test field-core + non-conftest services" runs `pytest -q packages/field-core/tests services/sealed-ledger/tests services/delegation-authority/tests services/spend-governor/tests services/kill-switch/tests services/federation-broker/tests`; "Test tools" runs `pytest -q tools/tests`; the per-service loop runs agent-registry, conformance-sentinel, incident-replay, compliance-crosswalk, force-gateway, lifecycle-manager, attestation-reporter, ops-console, claude-approver (cwd = service, `python -m pytest -q tests`) and `packages/field-agent`; "Deployed-topology lint" runs `python tools/topology_lint.py`. The script's steps 1 to 5 list the same six, the same tools run, the same nine services in the same form, field-agent, and topology_lint. Equal. [HIGH, read side by side]
2. FINDING 1 (MEDIUM): ci.yml's `tests` job has a step "Vendored field-agent templates in sync" (`bash plugins/field-agent/verify_sync.sh`) that the script does not run. The script's header says its set mirrors the `tests` job. I ran the check by hand on main: "templates in sync", exit 0, so no current red is hidden; the gap is that a template drift would pass the script and fail CI. Fix: one more `step verify_sync bash -c 'cd "$0" && bash plugins/field-agent/verify_sync.sh' "$WT"`. [HIGH]
3. Failure behaviour, tested with a negative control. I committed a test that asserts False to services/claude-approver/tests on a throw-away branch of main (7d6a4eb) and ran `gx10_verify.sh --name lane5neg --quick --foreground`. Result: `CI svc_claude-approver rc=1 1 failed, 101 passed`, `VERDICT RED (see logs)`, process exit status 1 (`exit $FAIL` is the last line). The other eleven CI groups were green with the known numbers. So a failing suite makes the run non-zero. A `cd` into a missing service directory, a failed `pip`/venv activation (`FAIL setup`) and a pytest "no tests collected" (rc 5) are also non-zero by construction (each step's rc is stored; any non-zero CI step sets FAIL). [HIGH, run]
4. The default (detached) mode returns 0 immediately after printing "started pid"; the verdict lives only in `summary.txt` and the `.done` marker. This is documented in the script's output line. A caller that checks only the launcher's exit status sees success. LOW, documented. [HIGH]
5. FINDING 2 (MEDIUM, PROVEN): when the requested ref cannot be fetched, the script silently tests something else. Code: `git fetch -q "$REPO" "$REF" 2>>"$OUT/driver.log" && TARGET=FETCH_HEAD || TARGET=$REF`. I ran `--repo /nonexistent/path --ref HEAD --quick --foreground`: the fetch failed (stderr only in driver.log), the script checked out the seed clone's own HEAD and printed `head 75a84c8f9357... (lane5fb)`; its `core_services` step started. A reviewer who asked for PR head X and mistypes the repo path gets a green run of the seed's old commit; the only tell is the `head` line, which a reader must compare to the sha they asked for. (With a ref name the seed lacks, the same run stops with `checkout ... failed`, which is correct.) Fix: with `--repo` or `--bundle` given, a failed fetch is a `FAIL setup` exit, never a fallback; and print the requested ref next to the resolved sha. I stopped my probe after the first step and removed its work tree. [HIGH]
6. FINDING 3 (LOW): `--quick` skips tools/tests and says so twice: the log line `SKIP tools (--quick)` and a summary line `NOTE tools/tests skipped (--quick): not a full CI-equivalent run`. But when everything else is green the next line is `VERDICT CI-EQUIVALENT STEPS GREEN`; the verdict line contradicts the note above it. A reviewer who greps the VERDICT line gets GREEN from a partial run. Fix: print `VERDICT PARTIAL GREEN (tools skipped)` under `--quick`. I confirmed this by reading the summary block at the end of the script; I only ran `--quick` on a red case. [MEDIUM: read, not run on a green case]
7. Secrets. The script never uses `set -x`, never echoes the environment, `unset`s FIELD_SHARED_SECRET, FIELD_OPERATOR_KEY, FIELD_OPERATOR_REGISTRY and ANTHROPIC_API_KEY, and exports only `CI=true` and PYTHONPATH. Its logs contain git messages, test output and file paths. On the GX10 login shell `env` holds no `FIELD_*` variable today (count 0; names only). FINDING 4 (LOW): the unset list is four names; other variables that point at live material (FIELD_OPERATOR_KEY_FILE, FIELD_LEDGER_SIGN_KEY, FIELD_DOA_ROSTER, FIELD_MANIFEST_DIR, FIELD_DATA_DIR and similar) would leak into the tests if a future shell exported them. A safer form unsets every `FIELD_*` and `ANTHROPIC_*` name by pattern. [HIGH on the code, LOW on impact today]
8. Isolation. The work tree is `~/ff-work/wt-NAME-verify` (a case guard refuses anything else), `rm -rf` only on that path; `--name` is restricted to `[A-Za-z0-9._-]`; no DB port, no estate, no network (the topology lint "needs no docker"). The seed is a local clone; nothing is pushed. [HIGH]
9. Baselines. Runs of the script on heads whose code equals main b1872ee (PR 99 docs-only head b588199, full): core_services 2181 passed 4 skipped, tools 1925 passed 3 skipped, agent-registry 238, conformance-sentinel 109, incident-replay 74, compliance-crosswalk 160 (1 skipped), force-gateway 208, lifecycle-manager 185, attestation-reporter 66, ops-console 171, claude-approver 101, field-agent 118; topology_lint OK. All twelve equal the card's list. The EXTRA defence-shield step: 1 failed 112 passed (C-147; reported separately, not part of the verdict, as the header says). The negative-control run (main plus one test file, `--quick`) gave the same eleven numbers. I did not run a literal `--ref b1872ee`; the docs-only head is code-identical to it. [HIGH]
10. Run-to-run: three runs of the script in this session (two full, one --quick) on different heads gave identical counts for every unchanged suite (for example ops-console 171 in each). [HIGH]
