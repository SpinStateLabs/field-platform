# C-155 reviewer report: services/agent-registry status/identity paths and mutation round (main 70fa59f)

VERDICT: one proven integrity gap: with the operator layer OFF (the state of every estate today), a retired (decommissioned) agent can be set back to active by one PATCH. The rest of the identity paths are pinned; 69 mutants, 49 killed, 20 survived.

OBJECTIONS FIRST
1. In OFF mode there is no operator identity, so "who may write" is anyone with the perimeter secret by design; the finding is about an invariant the code itself calls an integrity rule.
2. 69 mutants from two generators on api.py and store.py: not a coverage figure; models.py, redaction.py, discover.py, cli.py not mutated.
3. A mutant that survives the registry's own suite may be killed by the tools suite (I checked one: the attest guard is).

ASSUMPTIONS
1. Main 70fa59f; agent-registry suite 232 tests (6 s); generator v1 on api.py (30 mutants) and store.py (9), generator v2 on api.py (30 sampled of 106 candidates). I read `add_agent`, `update_agent` (PATCH), `attest_agent`, `on_behalf_of`, `update_with_previous`. [HIGH]

REASONING
1. MEDIUM, F-C155-1 (PROVEN): `update_agent` (api.py:~258-330). The retired guard ("a decommission is terminal ... no transition out of retired, for any identity", `raise HTTPException(409 ...)`) sits inside `if needs and operator_auth.mode() != operator_auth.OFF:`. Probe on the GX10 with no operator env (mode OFF): register `a1`, `PATCH {"status":"retired"}` -> 200 retired; `PATCH {"status":"active"}` -> 200 active; then `PATCH {"status":"killed"}` -> 200. With `FIELD_OPERATOR_REGISTRY` set the same second PATCH answers 409. The kill-switch refuses retired -> killed (api.py `_kill_one`, R-11) and the drill refuses retired agents, so the registry PATCH is the way around them in OFF mode. The kill-switch README states the rule "409 for every identity and also in log-only mode (an integrity rule, not an identity decision)"; OFF is not mentioned, and the OFF path is documented as byte-identical to before Phase G, which may be why the guard was scoped inside the mode check. Whether OFF byte-identity should outrank the integrity rule is a design question for Don. [HIGH on the behaviour]

LOW, F-C155-2: `on_behalf_of` (api.py:46-58): the scope check `if not auth.authenticated or not auth.has_scope("bypass_operator_list"): return None` survives as `if->False` and as `or` -> `and`; so no registry test shows that an authenticated identity WITHOUT `bypass_operator_list` has its `x-field-operator-on-behalf-of` header ignored. The docstring promises exactly that ("A header from any other caller is ignored"); the consequence of a regression would be a forged `operator_on_behalf_of` in a status-change ledger row (not probed, mitigations downstream not read). Also L56 (`k.lower() == ON_BEHALF_HEADER` for non-multi-dict headers) survives. [HIGH on the survivors]
