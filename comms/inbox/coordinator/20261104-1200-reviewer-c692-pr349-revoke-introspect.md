OBJECTIONS FIRST
1. F-C692-1 MEDIUM (PROVEN, regression of this PR): `app.state.revoke_lock` (api.py:140) is ONE `threading.Lock` per process, held across `app.state.ledger.append` (api.py:383-398), a network call with a 5 s client timeout (field_core/clients.py:275). The comment says "one revoke of a token at a time"; the lock is one revoke of ANY token at a time. Revokes are sync routes on the anyio threadpool (40 tokens), so waiting revokes hold threadpool tokens and every other sync route queues behind them, `/introspect` included (and `/oauth/introspect`, which uses `run_in_threadpool`). Run (real uvicorn server on loopback, ledger stub sleeping 0.3 s per append, 60 concurrent revokes of 60 different tokens): `/introspect` latency 0.004 s baseline, 5.27 s during the burst; the burst took 12 s to drain (serialized). conformance-sentinel's introspect client has a 5 s timeout (engine.py:140) and turns a timeout into BLOCK (engine.py:521-526), so the system fails CLOSED, but every governed action is blocked during a revoke burst against a slow or hung ledger (a hung ledger = 5 s per revoke, serialized). Before this PR revokes ran in parallel. Today's in-repo bulk caller (lifecycle-manager engine.py:1068-1072, decommission) is sequential, so the trigger needs many concurrent callers (consoles, several lifecycle runs): exposure is moderate. Fix: a per-token lock (a dict of locks keyed by token_id, or striped locks), so the idempotency guarantee is kept and unrelated tokens do not wait; optionally a timeout on acquire. [HIGH on the measurement, MEDIUM on production exposure]
2. F-C692-2 MEDIUM (PROVEN; partially documented): "concurrent revokes ... write ONE delegation.revoke event" (README row, PR body) holds only within one process and only when the ledger call's outcome is unambiguous. (a) Ledger commits, then the client sees an error (a read timeout after the server wrote): 502, token ACTIVE, 1 event; the retry succeeds with a NEW revocation id: 2 events, 2 distinct ids, the store holds the second. (b) Crash between the ledger write and the store write (`save_revoked` raising): 500 "Internal Server Error" (no detail leaked), token ACTIVE, 1 event; retry: 200, 2 events, token revoked. (c) Two apps on one database file both inside the ledger call: both 200 with ONE answered id, but 2 ledger events, one of which carries an id the store never held (the PR body states this limit; the README row states it too). Direction is correct (nothing acknowledged while active), but a ledger reader (replay, attestation, an auditor) that treats a `delegation.revoke` event as "this token is revoked" is wrong for the window until a retry, and indefinitely if nobody retries. Fix options: record a pending revocation id in the store BEFORE the ledger call and reuse it on retry (so retries emit the same id and a reader can dedupe), or a ledger idempotency key per token; at minimum, say in the README that an event without a matching stored revocation id is a revoke that did not take effect. [HIGH, run]
