## Objections first (FORCE-O)
1. The roster size-cap test passes for the wrong reason, and I measured it. With the cap REMOVED (`max_length=ROSTER_CSV_MAX_CHARS` deleted, mutant V11), POST /sweep with the test's over-size roster (1 MiB + 1 characters, one long field) still answers 422, because the same text trips the csv module's own 131072-character field limit: "owners.csv line 3: unreadable CSV (field larger than field limit (131072))". Measured on the head under that mutant: the over-cap roster is 422, but a roster of 300,000 short rows (about 1.2 MB) is ACCEPTED with 200. So the cap is real and effective for that input, yet no test would notice its removal; V11, V12 (cap +1) and V13 (cap -1) all survive the 26 tests and the whole lifecycle-manager suite (295 passed). The "exactly one MiB is not refused for size" assertion is also weak (`status != 422 or "at most" not in text`).
2. The interval floor is "proposed floor, Don to confirm" (a code comment): `FIELD_LIFECYCLE_EVERY` values 1 to 59 become 60 seconds with a warning. The test imports `MIN_ENV_EVERY_S`, so it adjusts itself: V1 (floor 59) passes the file AND the whole suite (295 passed). The literal 60 is asserted only for the input "60", which survives any floor at or below 60. The warning for a raised value (V9) is also unpinned. The floor is a behaviour change for any estate that set a short interval; it needs Don's confirmation per the comment, which I cannot verify.
3. The ASCII-digit rule is half tested. The code uses `isascii() and isdecimal()` because `isdigit()` accepts characters like "²" that `int()` rejects (the tests cover "²", "①", "1²"). But V6 (`isascii()` dropped) survives: Arabic-Indic digits are `isdecimal()` and `int()` accepts them (measured: `int("٣٦٠٠")` is 3600), so without the ASCII test a value in other scripts would be accepted. Untested direction; the stated aim ("ASCII digits") is not what a non-ASCII decimal test would prove.
4. Dead or redundant code, reasoned and partly measured: the `_rows` wrapper around the DictReader (V21, V26) is never reached by the three shapes in the tests because `_lines_with_a_space_after_an_unquoted_comma` runs first and wraps the same `csv.Error` (it reads the text with two readers before DictReader starts). V21 (the DictReader wrapper removed) survives the file and the whole suite. It may be a second line of defence for a text the plain reader accepts and the DictReader rejects; I did not find one (not proven unreachable).
5. CLI: the error line goes to stderr by design (`err=True`), but V30 (stdout) survives because CliRunner mixes the streams (the same limit I measured on PR 663). LOW.
6. A roster with an empty owner list is still refused; V20 (that check removed) survives the file and the whole suite (295 passed), so the "owner-less roster is refused" rule that guards against orphaning every agent is pinned elsewhere or not at all (the mutant lives in api.py, a pre-existing line moved into the new `try` block). I did not run the older roster tests individually. LOW to MEDIUM.
Steelman: before these commits a malformed roster in the request body or the configured file was a 500, a bare CR or an oversize field made the csv module raise `csv.Error` (not a ValueError) out of the CLI sweep and the API, `FIELD_LIFECYCLE_EVERY=²` crashed `create_app`, and POST /sweep accepted any size of `roster_csv`. Now the roster errors are named (422 for the body, 503 for the file), the error text carries a line number and csv's own text but never a field's content (SENTINEL checked in every path), and junk intervals leave the scheduler off with a warning that does not echo the value.
