## Objections first (FORCE-O)
1. A wrong-typed but FALSY `manifest_ref` still passes as "ok". The new guard `if not isinstance(ref, str)` sits AFTER the existing `if not ref: without += 1; continue`, so `0`, `[]`, `{}`, `False` and `0.0` never reach it. Measured on the head, one agent with each of those refs gives `status: ok`, `agents_without_manifest: 1`, `unresolvable: []`. The PR title and test docstring say a non-string ref (list, dict, number) is "invalid"; the truthy ones are, the falsy ones are counted as "no manifest" and the retention check reports OK. The retention check exists to say when an estate keeps data longer than policy; a registry answer with `manifest_ref: false` for an agent hides that agent. I found the same shape of gap in PR 671 (ops-console), where the author did check falsy non-strings and made them a refusal. MEDIUM.
2. The "names the type, not the value" test contains a vacuous assertion. `test_the_detail_names_the_type_not_the_value` asserts `"int" in check.detail and "str" in check.detail`, but the substring "str" is inside the word "registry" in every detail ("registry unavailable: TypeError: registry returned..."), so it holds whether or not the type name `str` is listed. Mutant Z2 (only the first odd type, `odd[0]`, is named) therefore survives; so does Z4 (types not de-duplicated or sorted). LOW.
3. Z12 (the older non-list check removed) survives as near-equivalent: a non-list answer is iterated by the new line and still ends as "registry unavailable" with a different message (for a dict, the keys are strings, so "list holding str").
4. Output shape: an invalid ref is listed as `{"agent_id": ..., "manifest_ref": "<int>", "reason": "invalid"}`. The `agent_id` is copied from the registry record unchanged and may itself be any JSON value (not guarded here); the check model types it as `Any`, so it passes through (LOW, not tested).
Steelman: before the change a registry answer holding a non-object (an int, null, string, nested list) raised AttributeError on `.get`, so GET /retention/check was a 500 and the offline CLI crashed; and a truthy non-string ref (a list, dict, number, True) reached `resolve_manifest_detail`. Now both are reported: the first as `unavailable` with a fixed detail (types only; SECRET-VALUE-xyz is not printed), the second as `unresolvable` with reason `invalid`; the HTTP route answers 200 and the CLI exits 3, never a traceback.
