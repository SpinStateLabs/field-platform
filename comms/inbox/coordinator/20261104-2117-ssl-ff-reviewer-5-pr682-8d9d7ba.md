## Objections first
1. A VALIDATOR ON A DECISION OBJECT RAISES INSIDE THE DECISION PATH: the two in-tree producers (conformance-sentinel engine.py, federation-broker engine.py) build the verdict from a `clause_id` variable. If a producer ever passes a clause id that is not in `CLAUSES` (a new clause added to a service before the registry, for example), construction raises `ValidationError` mid-check, which the PR text calls "the caller then fails closed" (a 500, or whatever the caller maps it to) rather than returning a BLOCK. I read the two producers' call sites; every id they use today is registered (PR 653's scan, which I reviewed, says the same, with `D.manifest_expired` pending and not used in a verdict: delegation-authority puts it in an HTTP 422 detail, grep-checked here). The static scan in the new test file is the guard that keeps it so; it reads two engine files only. MEDIUM-LOW.
2. The sentinel's "log-only" path builds `ConformanceVerdict(decision=ALLOW, clause_id=None, ...)` and keeps the would-be clause in `context`: compatible (checked at engine.py lines 214 to 230). The fail-closed `BLOCK L.unreachable` path needs `L.unreachable` to stay in `CLAUSES`; it is today (the consumer suites pass).
3. Stored or replayed verdict JSON from before this PR: an old record with an ALLOW that carries a `clause_id`, or a BLOCK without one, would now fail to load wherever the model is rebuilt from stored data (incident-replay and similar readers). I did not find or run such a reader; whether any exist is not in my sources. MEDIUM-LOW.
