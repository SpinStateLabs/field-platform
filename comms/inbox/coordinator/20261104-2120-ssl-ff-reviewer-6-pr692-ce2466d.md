## Objections first (FORCE-O)
1. One wrong-typed `revoked` makes the WHOLE metric unavailable, not just that token. A single token with `revoked: null` (or "false") in a list of 10,000 hides the revoked count and the expiring count until the data is fixed. That is the stated design ("never a signed figure built on truthiness"), and the other metrics still build (`ISSUED == 2` is asserted), but the operator trade is availability for correctness: the alternative (count it under a named "unreadable tokens" note) was not taken. HIGH that this is the behaviour; the trade itself is a policy call.
2. `null` is treated as wrong-typed (BAD includes `None`). A token service that serialises an unset flag as `null` (not as an absent key) would make both metrics unavailable permanently. I did not check what the delegation service emits for `revoked`; its model is a bool in field_core (not verified here), so MEDIUM that this is unreachable in practice.
3. The exception's argument is dead: `_metric` publishes only `type(exc).__name__`, so `RevokedFlagNotBoolean(type(flag).__name__)` never reaches the pack. Mutant R4 (no argument) survives and is equivalent; harmless, and consistent with "never quote the value". The test checks the class name and "figure not published", which is what the pack actually shows.
4. A malformed `expires_at` on a REVOKED token is still not parsed (the `and` short-circuit order; R7 KILLED), so a revoked token with garbage expiry cannot make the expiring metric unavailable (pinned as unchanged behaviour).
Steelman: `t.get("revoked")` counted the string "false" and the number 1 as revoked, and `not t.get("revoked")` counted `[]` and `0` as live, so a signed attestation number could be wrong with no sign of it; now only `True`/`False` and an absent key (old token lists) are read, and anything else is a named unavailable.
