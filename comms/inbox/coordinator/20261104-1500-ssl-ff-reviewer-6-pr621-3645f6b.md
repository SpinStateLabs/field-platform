## Objections first
1. Behaviour change that tightens enforcement (MEDIUM, by design, worth stating): before, a model with even one unpriced row in the window (`MIN(priced)` = 0) had ALL of its priced cost dropped from the total that `/status` and `/totals` fold into the cap (core.py `usage_totals_since`). After, the priced rows count. An agent that was under its cap only because of that undercount will now show a higher `spent_cents` and may trip ESCALATE/BLOCK on the first call after the deploy. The test `test_the_cap_trips_on_the_priced_rows_of_a_mixed_model` pins the intended direction; the rollout effect is not mentioned in the PR text I read (the test docstring says the display choice is "a decision for Don").
2. Display ambiguity (LOW): `ModelBreakdown.cost_units` is now `r["c"] if (r["p"] or r["c"]) else None`; a mixed model whose priced rows cost exactly 0 (a priced zero-cost row plus an unpriced one) still shows `None`, the same as a model with no priced row. `priced` stays False for any mix, so a reader cannot tell "no priced rows" from "priced rows worth zero".
3. The cap total now trusts that every unpriced row stores a NULL/zero `cost_units` (the SQL sums `cost_units`); a code path that wrote a non-zero cost with `priced=0` would now be counted. I saw only the one writer (`record_usage` stores `rec.cost_units`, `int(rec.priced)`); I did not audit every caller.
4. The PR is 1 commit behind main (b963407a, PR 546); disjoint files. PRs 585 and 555 change other lines of the same api.py.
