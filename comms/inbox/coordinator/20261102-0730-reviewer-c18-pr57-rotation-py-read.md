FINDINGS (severity, class, file:line, probe or reason)
F-C18-1 MEDIUM, state machine, unbounded retry after PROMOTE (PROVEN): rotation.py:1566-1577 (_promote) and :1597-1611 (_verify_current) revert to the both-keys file, set the journal phase back to "promote" and stop; the next run promotes again. Journal fields (:586-599) hold no attempt counter, and nothing emits the alert class `rotation_halted` (alerts.py:151-155 on main only defines it; a grep finds no other use). Probe: make 9b answer "next" for the new key on one service, run six times: generation goes 13, 15, 17, 19, 21, 23 (two per run), 6 `keyrotation.failed` and 6 `keyrotation.retired` events, journal still at "promote", and the row still holds `next_key` (both keys valid, the old key never retired). It is lockout-safe (that is the design), but it re-publishes the registry twice per run forever and the alert text "will not retry by itself" has no implementation here. Fix: an `attempts` field in the journal, stop and alert after N, no further retry until a human clears it.
F-C18-2 MEDIUM-LOW, lost update, no compare-and-swap (PROVEN): the operators file is read at :1383 (_do_publish), then `_next_generation` (:1403) makes up to eight service calls (`_states`, :769-776), then `_publish` (:844-863) writes with `os.replace` (:489-508) without checking that the file is still the bytes that were read. Probe: a hook that revokes the operator "don" after diff_guard and before the write: after the run completes the row is "active" again; the human's revocation is gone. Main's operator_keygen.py:35 states that "the format 2 rotator does not take this lock", so keygen `--add-to` and the rotator can overwrite each other the same way. Impact is high (a revoked operator comes back), likelihood low (a concurrent edit inside the window, which is as long as eight service calls). Fix: re-read and compare the sha immediately before the rename and refuse as `foreign_edit`, and take the same `<file>.lock` that keygen takes.
F-C18-3 MEDIUM (operational, PROVEN): any edit of the operators file not made by the rotator stops all rotation. `_check_foreign_edit` (:1114-1144) compares the live sha with `last_written_sha256`; a difference is a skip (exit 4) on every run, and nothing in this slice clears it (the module doc says R9 reconcile will, :91-100); `foreign_edit` appears in no runbook on main (grep of docs). It also applies to a rotation already in flight (:1325): probe: after finding 1's both-keys state, add one ordinary operator row (what `operator_keygen --add-to` does): three runs, three `skipped foreign_edit`, `next_key` still in the row, old key still valid. Keys expire 75 days after creation (:125), so a frozen estate has a clock on it. Fix before arming: an R9 reconcile or a documented manual acknowledgement; and treat "rows appended, nothing else changed" as benign by re-baselining after `diff_guard`-style comparison.
F-C18-4 LOW-MEDIUM, resume bug for kind "self" (PROVEN): `_emit` returns None when the event was already appended in this journal (:736-737); `_confirm_switch` (:1489-1497) reads `result` to confirm the cutover append authenticated with the new key, so a resume at CONFIRM-SWITCH after the cutover event was ledgered but before `soak_started_at` was saved sees None and aborts. Probe: run a self-identity rotation to SOAK, set the journal back to confirm_switch with `soak_started_at` null (the crash state), run again: `aborted confirm_switch switch_not_seen`. Safe (the abort restores the old key) but wrong; narrow crash window. Fix: store the cutover's authenticated fingerprint in the journal, or do not gate on a return value that can be None.
F-C18-5 LOW, availability by naming: `_soak` (:1519-1520) aborts on any refusal event naming the identity since the soak began. The real estate's counter (tools/operator_rotate.py:157-166) counts rows whose `claimed_id` or `operator_claimed` equals the id, and `claimed_id` is the unauthenticated id a caller put in the header (clients.py:39). Anyone who can send a request with that header and a wrong key to a guarded endpoint can abort every rotation of a machine identity; with 75-day keys, repeated aborts become an outage later. Not proven end to end (needs the services); the code path is. Fix: count only refusals that carry the NEW key's fingerprint (`operator_key_fp`, :1495), or ignore claimed-id refusals without a matching key.
