## Objections first (FORCE-O)
1. `registry add` stdout is no longer pure JSON. Measured on the head: a successful `add` prints the record's JSON followed by a line `note: this registration is NOT on the ledger ...` on STDOUT, so `registry add ... | jq` (or `json.loads(output)`) now fails (`JSONDecodeError`). This follows an existing precedent in the same file, `attest`, which also prints its "NOT on the ledger" note to stdout when it succeeds (`typer.echo(note, err=not ok)`), so the CLI is consistent with itself; a script that parses `add` output will still need a change. LOW (stdout contract), not tested either way.
2. The note is correct as far as I checked: `add` goes through `_store(path).add(...)` (direct SQLite), and the module only uses `FIELD_LEDGER_URL` in the attest helper (grep of cli.py lines 34 to 68). It states a negative; if a later change ledgers `add`, the note becomes false, and a test pins the text (W9, W10 killed), which will at least force a visible edit.
3. The tests do not prove the validated values are the stored values. Mutant W12 (`store.add` called with an unvalidated `AgentCreate.model_construct(...)`, so padded names are stored as typed instead of stripped by the PR 684 validators) survives. The new tests check only that the stored id is `good-agent`; no padded name, no over-long name. The old code also built `AgentCreate` before the store call, so this is a guard on the PR's refactor (`body` is built once and reused) rather than a new behaviour. LOW.
4. Field names: `fields` are the first element of each error's `loc` (a name from the model, never the caller's value; W3 killed). Ordering and de-duplication (W4, W5) and the `input` fallback (W6) are unpinned, and the "several bad fields" test asserts only that both names appear. W6 is nearly unreachable (a validation error always has a `loc`). LOW.
5. The stderr/stdout split of the error line (W7) is not pinned: CliRunner mixes the streams (same limit as PRs 663 and 738).
Steelman: before the change an invalid id (`Bad Id!`) or an empty name raised a pydantic traceback out of the CLI, quoting the input, and a successful `add` gave no hint that nothing reached the ledger (unlike the served `POST /agents`). Now an invalid field is `error: invalid <field names>` with exit 2, nothing is written (the database is asserted empty), the input text is never printed (SENTINEL and "Bad Id" absent), and a success states that the registration is not on the ledger and names `FIELD_LEDGER_URL` and `POST /agents`.
