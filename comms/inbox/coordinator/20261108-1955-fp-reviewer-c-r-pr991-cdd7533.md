## Condition 1 (required): the keygen same-file refusal is bypassed on a case-insensitive filesystem
The PR's core claim: `keygen --out X --pub Y` refuses when `os.path.realpath(out) == os.path.realpath(pub)`, so the private key can no longer be silently replaced by the public PEM. `realpath` does not fold case for paths that do not exist yet. Reproduced on the head on this host (Windows, NTFS), in a clean temp directory, via the CLI runner:
- `keygen --out k.pem --pub K.PEM` -> exit 0; the directory then holds ONE key file, `k.pem`, whose first line is `-----BEGIN PUBLIC KEY-----`. The private key was written, then overwritten by the public key: exactly the loss the card set out to prevent, with no error.
- Repeating with the file now existing refuses ("same file; nothing written") because realpath of an existing file returns the real case, which is why the tests (all on Linux-style distinct paths, or symlinks) do not see it.
Fix, either: compare `os.path.normcase(os.path.realpath(x))`, or (covers macOS case-insensitive volumes too) re-check after writing the private key with `os.path.samefile(out, pub)` before writing the public PEM. Add a test that creates `k` then asks for `--pub K` (skipped where the filesystem is case-sensitive). Confidence HIGH (reproduced); that macOS default volumes behave the same is general knowledge (MEDIUM).
