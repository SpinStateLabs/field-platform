## Objections first (FORCE-O)
1. Decommission is act-first (revoke, then kill, then retire), and the point of this PR is that a bad token listing no longer stops the kill and the retire. The consequence is intended and tested: the agent ends killed and retired while one or more of its tokens may NOT have been revoked (the report says `ok: false` and lists the failed steps, and a row without a usable id "was not revoked"). An operator who reads only the final agent status would see "retired" with live tokens outstanding; the report is the only place the failure shows (design; MEDIUM for operational care, not a defect).
2. A JSON `null` listing (a 200 whose body is `null`) is read as "no tokens" with NO failure (`if body is None: return [], []`). That is the old behaviour (`_json(listing) or []`) preserved, but it means an authority that answers `null` for "unknown" decommissions silently. Mutant T4 (treat it as a failure) survives the 17 tests, so the choice is unpinned (LOW).
3. A non-string, truthy `token_id` (for example `7`) would be accepted by a weaker check: T8 (`not tid` only) survives, because the "not a string" test also sends `""` and `None`, which still produce the failure the test looks for. Such a row would then be posted to `/tokens/7/revoke`. LOW test gap with a path-building consequence (the id is interpolated into a URL; the real check does refuse it).
4. Two reporting details are untested: T13 (every failure carries `http_status`, including a 200 whose body is bad) survives, because only the 503 case asserts the status; and T18 (only a 5xx is a failed status, so a 4xx listing would be read as data) survives, because the tests use 503 and 500 only. LOW.
5. `revoked` is now read strictly: only the JSON value `true` skips a token, so a row with `revoked: "false"` (truthy) is revoked again, "the safe side" (revoke is idempotent, per the delegation store I reviewed in MERGE 4). Both directions are pinned (T15, T16 killed). The same strictness is the opposite of PR 692's "unavailable" policy for a metric: here a wrong type causes an action, there it hides a figure; both are consistent with "never trust truthiness".
Steelman: before the change a reachable but wrong token listing (a 5xx with a JSON object, an HTML body, a bare object, a row without `token_id`) escaped `decommission` as AttributeError, KeyError or a JSON error BEFORE the kill and the retire, so a decommission could stop half done with the agent still active. Now each case is a failed `revoke` step, the good rows of a mixed list are still revoked (test: junk row, a row without id, one good row), and the agent is killed exactly once and retired.
