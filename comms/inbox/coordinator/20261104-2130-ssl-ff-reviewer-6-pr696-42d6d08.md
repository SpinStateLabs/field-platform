## Objections first (FORCE-O)
1. The PR adds a behaviour its title does not name: `MAX_USAGE_ROWS = 200` caps the usage rows in `/api/overview` and `/api/stream`. With more than 200 agents that have usage, agents past the 200th silently vanish from the table (the section's `error` says "only the first 200 ... are shown", but the section stays `available: true`). Also the loop `break`s at the cap, so unreadable answers after the cap are never counted. The cap is stated in the test docstring and pinned at the boundary (U5, U6, U7 killed), but it is a scope addition a reviewer of "S5-20" would not expect (MEDIUM for review hygiene; the behaviour is sensible).
2. The cap constant is imported into the test, so the test self-adjusts: a cap one too high (U11, 201) survives the PR's file (the over-cap test builds `MAX_USAGE_ROWS + 5` agents from the module's own value). I did not run U11 against the whole suite (self-adjusting by construction; LOW).
3. Two conditions are unpinned. U14 (an agent whose ONLY non-zero field is `total_output_tokens` is dropped from the table) passes the PR's file and the whole ops-console suite (478 passed): no test gives an output-only row. That would hide spend from the console. LOW, pre-existing condition, but the new test file is the natural place. U15 (the two notes joined without the "; " separator) also survives file and suite (478 passed): no test produces both notes at once. LOW.
4. A readable-but-wrong body is still shown: `{"total_input_tokens": "x"}` is a dict and would be appended as a row; this PR only handles non-objects. Not tested (LOW).
Steelman: before the change `data.get(...)` on a list, string, number or null raised AttributeError, so one bad governor answer turned `/api/overview` and the SSE stream into a 500 for every viewer; now the bad answer is counted, the section says so, the good agents' rows survive, and every other section is untouched (the test checks agents, tokens, escalations, ledger_verify, recent_events).
