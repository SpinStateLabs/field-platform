## Findings

### F1 MEDIUM, confirmed (HIGH confidence, measured): the retired-key memory protects only against a hash REMOVED by a higher generation; a status flip, a shortened expiry or a format-1 downgrade is not covered
Code: `_apply_retired_memory` (operator_auth.py ~1284-1340) retires `st["hashes"] - present`. A revoked row keeps its hash (the file rule is "no hash appears twice, revoked rows included"), so a revocation by `status` never lands in `retired`. The supported revoke procedure IS the status flip (tools/operator_keygen.py l.39 and l.194: "set the old row's status to 'revoked'").
Repro (s2.py, fake keys, clock fixed): the process loads gen 5 (ann active), then gen 6 (ann `status: revoked`, same hash): ann refused. Restore the gen 5 file: ann AUTHENTICATES again (S2b). Same result when gen 6 only moved `key_not_after` into the past (S2c), when a format-1 file (generation 0, no expiry, status active) is restored (S2d), and when a format-1 downgrade follows an expired gen 6 key (S2e). `retired_hash_seen` stays 0 and nothing is logged. Control S2a: a hash REMOVED at gen 6 and restored at gen 5 is refused with the one-line error, as designed.
Impact: a restored backup or stale `.prev` (the exact case design 2.4 item 3 targets) silently re-enables a revoked operator or an expired key for the life of the process; also after any restart (Declared, memory resets: S2f).
Fix direction: when a lower-generation file lists a hash the high file also lists, take the stricter of the two (revoked wins, earlier `key_not_after` wins), or refuse and log any file whose generation is below the highest seen; count it in `operator_retired_hash_seen`.

### F2 MEDIUM-latent, confirmed (HIGH): authn is `@app.middleware("http")`, so a websocket route is served without `x-field-auth`
authn.py `install` (l.41-62). s4.py: with FIELD_SHARED_SECRET set, GET /data and an SSE StreamingResponse without the header are 401 and with it 200 (SSE and streaming ARE covered, including the ops-console stream, which is an http route); a `@app.websocket("/ws")` route accepts the connection without the header and sends its frame.
Exposure today: none. `grep -rn WebSocket` over services, packages and tools (non-test) finds no websocket route. It is a fail-open default for the first one added.
Fix direction: a pure ASGI middleware that also checks `scope["type"] == "websocket"`, and a test that fails if any app with authn installed has a `WebSocketRoute`.

### F3 LOW (confirmed): the operators file has no size cap, no row cap and no cache; every request with both operator headers pays full read, parse and sha256
operator_auth.py l.1221 `Path(path).read_bytes()` (the key-file reader is capped at 4096 bytes, l.80; the registry reader is not). s3.py: 10 rows 0.5 ms; 1,000 rows 20 ms; 20,000 rows (3 MB) 0.3 to 0.46 s; 100,000 rows (15 MB) 1.7 s, single thread, per request. The row count is accepted without limit. Any caller holding the perimeter secret and two syntactically valid headers triggers it; no valid key needed. The designed file (10 rows) is not affected; this matters only if the file grows, by error or by a writer. Code read only, not run: a FIFO or character device named by FIELD_OPERATOR_REGISTRY would block or exhaust memory in `read_bytes`; a symlink is followed (no O_NOFOLLOW) and the retired memory is keyed by `os.path.abspath`, not `realpath`.
Fix direction: cap bytes and rows at load; optionally cache by (mtime, size) with a revalidating stat.

### F4 LOW (confirmed): format 1 silently DROPS a row whose operator_id holds a lone surrogate; format 2 refuses the whole file
operator_auth.py l.1121 `continue  # a lone surrogate can never authenticate: drop the row`, inside `_parse_format1`, whose docstring says "Any problem is RegistryUnavailable ... nothing is partly honoured". A one-row format-1 file with `"operator_id": "\ud800"` LOADS with 0 rows; that row also skips the scopes, names, prefix checks and `validate_rows`. In format 2 `printable_id` refuses the file. Harmless for authentication (the id cannot arrive in an ASCII header), but the file's row count and a hash in it are silently unaccounted for, and the two formats disagree.

### F5 LOW (confirmed): `generation` has no ceiling and no step check; one typo locks out keys until restart
s8.py: gen 8 file (ann, bob); a hand-edit typo `generation: 99999999` that omits bob; the corrected gen 9 file with bob restored: ann works, bob is REFUSED (a higher generation "removed" it and 9 is below the high). A generation of 2**70 is accepted. Recovery: write a generation above the typo, or restart the process. Self-inflicted only (the writer is Don), but the operators file is hand-assembled per the runbook and a kill-switch identity can be the one refused.
Fix direction: `--check` and the loader warn when generation jumps by more than a set step.

### F6 LOW (confirmed): the parser enforces no relation between `key_not_after` and the `next_key` window, and no maximum lifetime
s1.py: accepted by the parser and `_verify`: a next_key valid for 10 years (so `key_not_after` is not a ceiling); a next_key starting after the current key expired (a gap in which nobody can authenticate, 403 for the owner); a next_key window wholly in the past. The boundaries themselves are correct and half-open: current key valid for now < key_not_after (T-1 yes, T no); next key valid for not_before <= now < not_after (A-1 no, A yes, B-1 yes, B no), float now included. Writer-controlled; matters as a writer-error class.

## Checked, no finding
- Key-window arithmetic and `next_key` rollover under a mutated clock (s1.py): nan and +inf deny every key; -inf, 0 and negative clocks re-enable a key past its expiry (a clock stepped backwards re-validates; `clock_synced()` exists for the design's step-0 gate). No sign or overflow error.
- passkey/session paths (INFO): no passkey or session authentication exists on main: `_parse_passkeys` is a shape check only ("never authenticates with them (slice H1)"); a row with `"auth": ["session"]` and no `key` never authenticates (s3.py: False, fail closed). Re-review when slice H1 lands.
- `_apply_retired_memory` under concurrent file replacement (s6.py): 8 reader threads authenticating while a writer alternates, with atomic replace, the gen 6 file (ann removed) and the stale gen 5 file (ann present): 7,059 loads, 0 violations (no request that started after gen 6 was seen authenticated ann); the 428 ann successes were all before gen 6 was first seen. On Windows a reader meeting the replace window got PermissionError (503, fail closed, 503 loads counted); not reproduced on Linux.
- File-read limits other than size (s7.py), all RegistryUnavailable, none a 500 or other exception type: empty file, double BOM, UTF-16, NUL byte, invalid UTF-8, NaN/Infinity generation, bool generation, a 4,400-digit integer, 100,000-deep nesting (RecursionError handled), duplicate JSON key, non-list top level, directory path. One BOM is tolerated (utf-8-sig) as documented.
- `operator_health.guard` and `note_refused` (s3.py, 120 concurrent bad-credential requests with a ledger append that sleeps 3 s): all 403; refused_count 120 = 4 written + 116 dropped (the invariant refused == written + dropped holds); at most 4 appends in flight; slowest refused request 1.67 s (the 1.5 s append timeout), the others about 0.13 s. A flood costs the audit trail (116 of 120 not ledgered, counted in `dropped_refused_records`, which G24 aborts on), not availability.
- Timing of `_verify` (s5b.py, shuffled order, 40,000 calls per case, 10 rows): p10 within +400 ns of the unknown-id case for every hash-matching case (valid, revoked, expired, right-key-wrong-id) and within -100 ns for known-id-wrong-key; p50 differences under 1.1 microseconds against a 20 microsecond median and a 23 microsecond p10-p90 spread. No usable oracle in a local micro-benchmark; a matching hash already requires the key. A missing scope returns the same 403 detail as a bad credential, so the response does not distinguish them either.
- verify-hash oracle: keys are `fok_` + token_urlsafe(32) (256 bits), so a candidate cannot be guessed against it.
