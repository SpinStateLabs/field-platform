# C-522 reviewer (Lane 4): claude-approver cursor re-audit on main b929f12 (C-445 merged; other cursor and `created_at_gte` paths in `_read_events`)

VERDICT: C-445 HOLDS, TWO NEW HOLES FOUND on main b929f12. A value that is not a time is never stored as the cursor and never replaces a real one (every spelling I tried: empty, int, bool, bytes, None, 24:00, all unstored). The approver suite passes on main (282). But the cursor has no upper bound and is stored verbatim: F-C522-1 (MEDIUM-LOW) a valid far-future `processed_at` becomes the cursor and, because nothing is later, stays; F-C522-2 (LOW) several spellings Python parses but an API may not are stored and sent back unchanged. This is a re-audit of main, not a PR: no head SHA other than main b929f12.

## OBJECTIONS FIRST
1. F-C522-1 MEDIUM-LOW (the cursor can be pushed past all real time and stay there): `_later` orders by instant, so one event with `processed_at` `2999-01-01T00:00:00Z` (or `9999-12-31T23:59:59Z`) becomes the cursor, later real times are not later, and the next read sends `created_at_gte=2999-01-01T00:00:00Z`. Probed through the real `_read_events` with a recording client: the second list call carried the 2999 value; the cursor ended on it. An API that honours the filter returns nothing newer for that session, so asks and tool results after that point are never read (not an error: no `list_failures`, nothing to see). It needs one wrong timestamp from the API or a clock error on its side; I know of none. The C-445 comment says the cursor "goes back to the API as `created_at_gte`", the same reason applies to a far-future value. Fix: do not accept a `processed_at` later than the approver's own clock plus a slack (a minute or an hour), or read from the start again when a list call with a cursor returns no events while `updated_at` has moved; pin it with the 2999 case above.
2. F-C522-2 LOW (the cursor is the raw value, so what is stored is what is sent): `_time_or_none` accepts what Python's `fromisoformat` parses, and `state.cursor = processed` stores the original object. Probed, all stored and so sent verbatim: a padded string `" 2026-10-28T13:00:00Z "`, a date-only `2026-10-28`, a space form `2026-10-28 13:00:00`, the basic format `20261028T130001Z`, a week date `2026-W44-3`, lower-case `z`, a naive time, a seven-digit fraction. An API that rejects one of them fails every list call for that session (`list_failures`, no approvals) until the cursor is replaced by a later normal one (it is replaced by the next valid later value, so this self-heals only if such a value follows). The SDK returns datetimes, so I know of no live path. Fix: store `_as_datetime(processed)` normalised (an aware datetime, or its `isoformat()`), not the raw value.
3. UNKNOWN (not in source): the cursor takes `processed_at` while the API parameter is `created_at_gte`. An event created before the cursor's instant but visible only after the previous read (an eventually consistent listing) would never be listed. The module docstring states the design (`created_at_gte=<last processed_at>`); I cannot judge the API's consistency from the repository, so I say "I don't know" and do not call it a defect.
4. EQUIVALENT mutants: dropping `processed is not None` (None is not a time) and dropping `state.cursor is None or` (`_later(x, None)` is True for a real time) survive the suite and change nothing.

The other `events.list` call (`_usage_snapshot`, `types=["session.usage"], order="desc", limit=1`) has no time cursor. ## REASONING
1. Suite on main: 282 passed. HIGH.
2. Guard (lines 613 to 615): store `processed` only if it is not None, is a time, and either there is no cursor or it is later by instant. Probes through `_read_events` with a recording client (19 streams): None, empty, int, bool, bytes, `24:00` never stored; None then a real time ends on the real time; year 0001 then a real time ends on the real time; equal instants in two spellings keep the first; a naive datetime is stored (read as UTC for ordering). HIGH.
3. Mutants KILLED (7 of 10): no time check, always overwrite, never replace (first value only), swapped operands, cursor never sent, `created_at_gte=None` sent when there is no cursor, `ta >= tb`. Survivors: the two equivalents in objection 4 and a no-op mutant of mine (the assignment unchanged). HIGH.
4. Probe results for objections 1 and 2 are printed values from the real function: future cursor `2999-01-01T00:00:00Z` stored, second call parameter `2999-01-01T00:00:00Z`; padded, date-only, space, basic, week, lower-case z, naive and seven-digit forms stored verbatim. HIGH.

## CONCLUSION
C-445 holds for non-times. Two further cursor hazards remain, both needing an odd timestamp from the API: a far-future time pins the cursor (F-C522-1), and a time spelled in a form Python reads is stored and sent as written (F-C522-2). Neither is covered by a test.

PROPOSED CARD (the coordinator numbers it): builder, services/claude-approver: refuse a `processed_at` later than `self.clock()` plus a stated slack as a cursor value (log and count it), and store the normalised instant rather than the raw value; pins: the 2999 and 9999 streams, a padded string, a basic-format string, `20261028T130001Z`, and an assertion on the exact `created_at_gte` of the second call.
