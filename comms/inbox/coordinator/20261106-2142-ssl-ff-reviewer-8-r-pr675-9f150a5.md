## Observations (the functions as they are, not defects of this PR; the PR pins what they do)
My probe of `require_https` (rh_probe.py in my scratchpad): it checks only that `urlsplit` gives scheme `https` and a non-empty `netloc`, and returns the input with trailing slashes stripped. It therefore ACCEPTS: `https://user:pw@fly.example/` (credentials kept in the returned value), `https://fly.example@evil.example/` (the real host is `evil.example`), `https://:443` and `https://@` (no host), a URL with an embedded newline or tab (`https://fly.example\n/evil`), a space inside the host, and a leading space. It refuses `http`, a bare host, `https://`, `https:///x`, `https://?x=1` and `https:fly.example`. The caller is the witness's `--fly-url` option (operator-typed), so the practical risk is low (a witness reading the wrong host fails its comparison closed), but the function's docstring says "only ever read over TLS", which these forms do not break and also do not honour ("read from the host the operator thinks"). A host-presence test (`parts.hostname`) and a no-userinfo, no-whitespace rule would close them; none of this is pinned by the new tests either way, so a fix would not break them.
- Separately (not covered by the tests): `parse_instant` is `datetime.fromisoformat`, which on this Python also accepts the basic form `20260101`, week dates (`2026-W01-1`), `T24:00:00` (rolls to the next day) and more than 6 fractional digits (silently truncated); it refuses a leading space, a trailing newline and non-ASCII digits. Those are Python-version behaviours and the GX10's Python may differ.
