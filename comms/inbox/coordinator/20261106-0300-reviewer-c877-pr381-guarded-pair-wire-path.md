## OBJECTIONS FIRST
1. F-C877-1 MEDIUM-LOW (the pair and the secret can still reach an environment proxy from four clients): `packages/field-core/src/field_core/clients.py:285` and `:368` (`LedgerClient`, `RegistryClient` build `httpx.Client(timeout=5.0)`), `services/kill-switch/src/kill_switch/cli.py:151` (the CLI client), and the lifecycle CLI and the kill-switch `new_endpoint_client` are in `tools/tests/http_env_proxy_allowlist.txt` (lines 14, 15, 40, 41, 42): the proxy-environment lint lists them as "not yet migrated" and the lint's own test makes the list shrink-only. This PR is what makes those clients carry the operator pair (on `POST /events`, `PATCH /agents/{id}`, the kill/revive/drill writes), so a proxy configured in the process environment would see the pair of a guarded write there, which `PerRequestAuthClient` (`trust_env=False`) never allows. Not a regression (before the PR the pair rode every request of those clients) and the PR does not claim to close it; it narrows the exposure from every request to guarded writes. The migration card (C-56) is the fix; say it in the PR text so the narrowing is not read as the closure.
2. F-C877-2 LOW (two real pin gaps; 6 of 58 mutants survive, 2 real): (a) `is_guarded` with the base's `rstrip("/")` removed (G5): a base URL with a path and a trailing slash (`http://gw/ks/`) would then never be guarded, because `startswith("/ks//")` fails; nothing pins `GuardedOperatorAuth` with such a base (the lifecycle client has its own prefix code and its trailing-slash case is pinned). Fail-closed (the write loses its identity), an availability bug if a base is ever configured that way. (b) `services/kill-switch/.../cli.py:151` without `headers=_perimeter()` (K4): the CLI would send no `x-field-auth`; the whole kill-switch suite (165) stays green. Fail-closed (401 under the perimeter), an availability bug; pin one request header.
3. F-C877-3 LOW (the wire-path decision is conservative in one direction): `field_core.clients._request_auth` gives the pair only when the id-built path equals the path httpx would send; probed on 21 agent ids for `PATCH /agents/<id>`: `a`, `a b`, `x;y`, `a\b`, `a+b`, `....`, `a..b`, an id with a non-ASCII letter and a bare `%` keep the pair; `..`, `.`, `%2e%2e`, `%2e`, `a%2fb`, `a%2Fb`, `a%25b`, `x%00y`, `x?y`, `x#y`, `x/y` and an empty id lose it (perimeter secret only, so a guarded write by such an id is refused under ENFORCE). That is the intended fail-closed behaviour for an id that would traverse or re-route; it also means a legitimate id containing `%XX` cannot be written to. Whether the id grammar (PR 371) already refuses those I did not check.
4. LOW (the redirect claim is about this client, not about httpx): `GuardedOperatorAuth` itself is an `httpx.Auth` and does not stop a redirect: a plain `httpx.Client(follow_redirects=True, auth=GuardedOperatorAuth(...))` would copy the custom headers onto the redirected hop (httpx re-runs auth outside the redirect loop). The PR's answer is the client wrapper (`follow_redirects=False`) and its pin (K2 dies); the docstring now says so (C-792 F-C792-4). A future caller that builds its own client with this auth object and follows redirects reintroduces the leak; the module docstring could say that the auth object alone is not enough.
5. NOT A DEFECT (probed, Reasoning 3 to 6): equivalent survivors: `rstrip` of the lifecycle prefix without the slash test (L13) and the guard's `startswith(prefix)` without the slash (G6): the remainder then starts with a non-slash character and cannot match a route; `POST /retention/check` against the ledger table (C9): that route is not in the table either way; the CLI's explicit `follow_redirects=False` (K1): httpx's own default is False, the explicit value is pinned only against `True` (K2).
