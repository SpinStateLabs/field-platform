## OBJECTIONS (before the proposal)
1. "Provable" rests on `<key>.prev`, a file the same unix user can write (reviewer C-71 D-6, citing C-65). A hash match against `.prev` alone proves nothing about what the registries hold. An auto-restore built on it moves risk into the most dangerous code (it writes key files).
2. One wedged journal stops every identity: `_locked` resumes `journals[0]` whenever any journal exists (rotation.py:1086-1089; C-71 D-6). R9 that only fixes the provable cases leaves the unprovable case estate-wide.
3. R9 itself has no cap on writes. The present cap counts failures (`POST_PROMOTE_MAX_FAILURES = 10`, :157) but each failure writes two generations (C-18 F-C18-1; the C-18 delta probe: generation 13 to 31 in ten runs), so 10 is up to ~20 registry generations. A reconcile loop with the same shape repeats the write storm (C-71 D-5).
4. The ledger event for a reconcile is frozen: `keyrotation.reconciled` allows only run fields, `operator_ids`, `generation`, `registry_sha16` (rotation_events.py:118). It cannot say WHICH action (restore / forward / accept / halt). Adding a field is a schema change I did not scope.
5. Foreign-edit "accept" (F-C18-3) widens trust: auto-accepting a changed operators file can launder a hostile edit. A key-slot-only edit is detectable (`key_slots_only`, rotation.py:1147-1160); a roster edit is not provably benign.

Strongest case against R9 at all (steelman): "halt and page a human" is simpler and safer; but it contradicts Don's 2026-10-27 ruling that key rotation is continuous machine work (C-22, MEDIUM: a session note, not a repo file) and strands the other identities (objection 2). So R9 is needed, narrowly.

## REASONING: what exists, what R9 adds
1. Already automatic and correct on PR 57:
   - live current == new key (promoted): abort refuses, journal moves to `promote`, run goes forward (:921-926).
   - live current == sha256(`.prev`) and old fp matches the journal: restore the key file, drop `next_key` from the LIVE document (:931-962).
2. Halting states a human must clear today: (a) abort refused, `.prev` not provably the live current (:938-942); (b) post-PROMOTE cap reached, journal kept, `status.halted` (:1362-1373); (c) foreign edit, skipped every run, no clear (:1120-1167; C-18 F-C18-3, delta F-PR57D-2); (d) unreadable journal (:1082-1096).
3. Alert gap: nothing emits `rotation_halted` (alerts.py:151-155 defines it; delta F-PR57D-4). The cap logs CRITICAL only.

## PROPOSAL (what R9 does, per state)
Reconcile reads, per halted identity: live row current/next hashes L/N (from the LIVE file), key file K, `.prev` P, journal phase and fps, AND each service's `verify_hash` for L, N, P.

| State | Proof required | Action |
|---|---|---|
| R9-a: L == P and every service says `current` for P and `none` for the new key (or `next`) | file match AND all services agree | abort path: restore key file, drop `next_key`, end journal (existing :931-962) |
| R9-b: L == new key (every service `current`) | same | forward: journal to `promote`, resume (existing :921-926) |
| R9-c: foreign edit, `key_slots_only` or roster-only (rows added or revoked; in-flight target row and sealed row byte-equal; parses with the R1 parser; generation above high-water) | diff computed from the kept last-written copy, services report the same generation | accept: `last_written_sha256 = live sha`, clear `foreign_edit`, ledger `keyrotation.reconciled` (generation, sha16) |
| R9-d: anything else (L matches none of K, P, new; services disagree; non-roster foreign edit; unreadable journal) | none | HALT: no write, `rotation_halted` ntfy at max priority once per day, escalating at 14 d before `key_not_after` (C-71 D-5), park that identity |

Rules for the engine:
- Cap WRITES, not attempts: at most 3 reconcile writes per identity per 24 h; probing (reads) continues without limit.
- Park, do not block: a parked identity's journal is skipped by `_locked` so the other identities rotate; the parked one keeps both keys valid. DECISION FOR DON: this changes the "one rotation at a time" estate-lock semantics only for parked identities (design 4.2, 6.3); the other identities' writes still take the estate lock and the generation rule.
- `.prev` is advisory: every restore needs service corroboration (objection 1). If services are unreachable, treat as R9-d (fail closed).
- Never `--accept-roster` automatically for the break-glass (sealed) row or any row's key fields; those stay R9-d.

## Tests-first plan (for the card that builds it; mutants named)
1. Corrupt `.prev` to hash-match L while services say otherwise -> must HALT. Mutant: skip the service check.
2. R9-a, R9-b: restore / forward, key file and `.prev` as expected. Mutant: restore without `live_cur == old_sha`.
3. R9-c: add one operator row mid-soak -> accepted, rotation resumes; change a target key field -> HALT. Mutants: accept without sealed-row equality; accept any diff.
4. Write cap: 4th reconcile write in 24 h refused, reads continue. Mutant: cap on attempts.
5. Park: identity A parked, identity B rotates. Mutant: `_locked` resumes `journals[0]` unconditionally (today's behaviour) goes red.
6. Alert: `rotation_halted` sent once per day per identity, not per run. Mutant: send per run (storm).
