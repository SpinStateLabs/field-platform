## Objections first (FORCE-O)
1. Durability cannot be proven in a cloud run: the tests observe the ORDER of os.fsync/os.replace calls and the inode fsynced, not that bytes reached disk. A crash-safety claim ends at "the right syscalls are made in the right order" (HIGH that this is the limit of the evidence).
2. The `fh.flush()` line is unpinned (mutant F2 survives, also the whole compliance-crosswalk suite, 375 passed). Without it `os.fsync(fh.fileno())` runs while the data is still in Python's buffer; the `with` exit then writes it AFTER the fsync, so the temp file's content is not durable at replace time. That is exactly the failure the PR exists to prevent, and no test would notice. A test fixing it: in the fsync spy, assert `os.fstat(fd).st_size > 0` at call time. LOW as a test gap; the code as written is correct.
3. `_fsync_directory`: swallowing an OSError from os.open (F5) and closing the fd (F7) are untested; F5 matters on Windows (cannot open a directory), F7 is an fd leak per write. LOW.
4. A failing directory fsync is swallowed silently, with no log line, so a durability downgrade is invisible. Design choice, stated in the docstring (LOW).
Steelman: the previous code (write_text then os.replace) could leave an empty store after power loss, which fails load and silently reopens the evidence-pack gate; the fix is the standard write-fsync-rename-fsync(dir) sequence, and the tests pin order, target inode, failure cleanup and the dir-failure tolerance.
