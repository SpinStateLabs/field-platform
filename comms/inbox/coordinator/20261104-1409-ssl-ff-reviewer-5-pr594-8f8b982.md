## Objections first
1. The fix trades one boundary rule for another: `text.split("\n")` leaves a trailing `\r` on CRLF lines. That is safe because `\r` is JSON whitespace and `line.strip()` removes it (pinned by the CRLF test, HIGH), but a bare `\r` as the only line separator (old Mac line endings) now yields one line and a JSON error rather than several events. Not a regression for the store's own format, which is newline. MEDIUM-LOW.
2. The change claims to align with "the boundary the store and the bundle reader use" (code comment). I did not verify that claim against bundle.py, anchors.py or the store's reader; I read only witness.py and the new test. Not in source for me.
3. Anything that read the old `splitlines()` behaviour by accident (a file with a lone U+0085 inside a string) now parses where it used to fail: the intended change.

## Survivors
- 2b (LOW, HIGH): a whitespace-only line (for example a blank CRLF line, `\r` only) is skipped by `line.strip()`; the tests use bare `\n\n`, so the `strip()` is not pinned against `if line`.
- 3b (LOW-MEDIUM, HIGH): `NaN` and `Infinity` refusal (`strict_json_loads`'s `_no_constants`) is not pinned through `load_events` JSONL by any witness test; a witness reading an event stream should refuse them. Existing behaviour, not this PR's change.
- 5a (LOW-MEDIUM): invalid UTF-8 bytes would be silently replaced if `errors="replace"` were introduced; no test sends invalid UTF-8. Existing behaviour.
- 5c and 4a (LOW): a BOM, and a leading-whitespace array, are unpinned. Existing behaviour.
- 1f (LOW, MEDIUM confidence non-equivalent): splitting at a raw VT turns `{..}VT{..}` into two accepted events where the code refuses it; the test's raw-VT case sits inside a string, where both halves fail JSON either way, so it cannot tell the two apart. The test's own docstring says the control characters are "pinned so a change on either side shows": that holds only for the in-string case.
