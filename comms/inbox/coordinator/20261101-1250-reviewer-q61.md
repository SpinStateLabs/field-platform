## Objections first (what is wrong, or could be, with this PR and with my own review)

1. **The builder's header-safety rule is not the rule the HTTP library enforces.** `_header_safe` (`config.py:73-78`) refuses control and non-ASCII characters and allows the space. h11 refuses a header value that starts or ends with a space, tab or newline. So a padded operator id, operator key or service key loads, the process starts, and every guarded write then fails exactly the way F-C1057-380-1 described: nothing sent, reported as "outcome unknown; do not retry". I reproduced it (F-Q61-2 below, numbered F-Q61-1). The builder's own note says "spaces and punctuation load" and the test pins only an inner space, so this was decided, not overlooked, but the decision rests on a wrong premise.
2. **The new backstop does not cover the code after the reply.** The C-1065 note asks reviewers whether "any path still writes an intent row without an outcome row". None does. But there is a path where the row says `ok`, the service acted, and the model is told only "internal error": `envelope()` (`tools.py:217`) runs after the `try`. I reproduced it with a 1,200-level JSON reply (F-Q61-2).
3. **A test that does not test what its name says.** The no-echo assertion in `test_a_header_unsafe_character_in_a_credential_stops_the_write_process` looks for a string that is never the value under test. A mutant that puts the offending credential into the startup error survives all 289 selected tests (H10). That is the one promise ("naming the variable, never the value") that matters for a key.
4. **PR 380 is not the PR the rest of the program thinks it is.** It carries PR 368 only up to 1f7f61f5; PR 368 has since gained five commits (to 1fac649d) that this PR does not contain, and the two PRs now conflict in two files. Four findings I closed on PR 368 in Q-49 and C-790 (path `fullmatch`, literal Tier 2/3 route pins, declared dependencies, wording) are therefore still open at THIS head. The builder note says "PR 368 inside the head untouched", which is true and is the problem.
5. **My own limits.** I could not run Python 3.14 at all, I ran the PR's Tier 1/Tier 2 behaviour against a loopback stub (never a real service, ledger keyring, MCP client or GX10), I read, did not run, the claim that the builder's own script kills 85 of 85, and I built no mutant for the order of the blank-reason refusal against the rate slot (see "What I did NOT do").

Steelman of the opposing case (the PR is fine as it is): the head closes every item its card asked for, with a failing test per item (the note says 28 of 30, 23, 4, 6 and 11 tests failed before the fixes, and I found no reason to doubt that), the field-mcp suite is 305 passed here, the header-safety gap needs an operator to pad a credential, and the deep-reply gap needs a service to answer with more than a thousand nesting levels. Against that: both gaps sit exactly on the property this program cares about for a write path (a retry must never be invited when the service may have acted, and a misreported "unknown" is the same operational outage C-1065 was written to remove), and each costs one test and a few lines.

Failure conditions I looked for (more than three): a half operator pair accepted; the pair sent on a route that does not check it; the pair sent to the wrong service; a credential with a control character reaching a header; a padded credential reaching a header; a write that consumes a rate slot or writes an intent row before it is validated; a lone surrogate anywhere in the arguments (value, key, nested, reason); an id with a trailing newline in the path or body; an id longer than 200; a 5xx reported as a definite refusal; an unexpected exception between the intent and the reply; an exception after the reply; a read process that can name a write tool; the signer dropped from the audit.
