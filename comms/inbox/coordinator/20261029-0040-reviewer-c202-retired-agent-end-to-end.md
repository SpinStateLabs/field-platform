FINDINGS
- F-C202-1 (MEDIUM-LOW, PROVEN): owner, domain, name and manifest_ref of a retired agent are editable (200, `registry.updated`). The store allows it on purpose (test_retired_store_guard_c167.py:43 `...and_other_fields_on_a_retired_agent`), but incident-replay derives "Responsible" from the registry's current owner (engine.py RACI from `record.owner`), so a later edit rewrites who owned the agent at the time of an incident in a post-mortem generated afterwards; the ledger row records the edit but the replay does not read it. Editing `manifest_ref` changes the manifest the replay and the sentinel read for that id. Proposal below (P1).
- F-C202-2 (LOW): `POST /agents/{id}/attest` is accepted for a retired agent (200, `registry.attested`): a decommissioned agent gets a fresh attestation record and ledger row. It does not reactivate.
- F-C202-3 (LOW-MEDIUM, PROVEN): the spend-governor accepts `PUT /caps` and `POST /spend` for a retired agent (200, 201 OK, spend accumulates, no ledger row). A decommissioned identity that still reports spend means something still holds its credential, and nothing says so. It is a meter, not a gate (per its README), so this is not a reactivation; the missing signal is the point.
- F-C202-4 (LOW wording): sentinel clause `R.unregistered` for a registered, retired agent; kill-switch domain kill says "no agents registered in domain" when the domain holds only retired agents. Operators reading the console halt report see counts of null.
- Not findings, recorded: `PATCH status=retired` on a retired agent and a second `decommission` are accepted no-ops that write a row each time.
