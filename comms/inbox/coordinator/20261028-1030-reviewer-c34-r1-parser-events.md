## Findings
1. MEDIUM, PROVEN (probe): the break-glass identity is not forced to be a sealed row. `_parse_format2` applies the sealed rules (scopes subset of SEALED_SCOPES, key-only auth, no next_key, no expiry, no passkeys) only when `rotation == "sealed"`. A row with the literal id `don-breakglass` (operator_auth.py:1288 BREAKGLASS_ID) and `rotation: remote`, scopes `["*"]`, auth `["key","session"]`, a `next_key` and an expiry was ACCEPTED by `parse_registry_doc(require_active=True)`. `is_breakglass()` treats that id as break-glass (verify-hash 403, attempt counters) while the parser treats it as an ordinary row: the break-glass credential can silently expire, rotate or hold `*`. Needs write access to the operators file (so not a privilege escalation by itself) but it breaks design 3.4's invariant that break-glass is sealed and key-only. Fix: in `_parse_format2`, require `rotation == "sealed"` for BREAKGLASS_ID (and refuse `sealed` rows whose id is not the break-glass id, or document that any sealed id is break-glass). Test: that probe row must raise RegistryUnavailable. Also relevant to #57: its diff_guard and migration treat `is_breakglass(id)` as sealed, so a non-sealed break-glass row is protected from the rotator but would still be accepted.
2. LOW (known, declared in #57's body "R2 review ruling 8, ledger half"): `rotation_events.validate` runs in the writer only. The sealed-ledger does not refuse a malformed or key-bearing `keyrotation.*` append from a holder of `ledger_attribute`/`keyrotation.`, so the schema's no-key/no-hash guarantee is as strong as the rotator's honesty. Track it as a condition before the rotator identity is armed.
3. LOW (not tested): no size bounds in the parser: number of rows, `passkeys` per row, `names` per row and file size are unbounded (only per-name length is capped); a large file raises parse cost on every authentication (each auth loads the file). Needs host write access; availability only. I did not measure.
4. INFO: `key_not_after` is only required to parse, not to be after `key_created_at`/`issued_at`; a past expiry is a valid (inert) row. Rotation tooling must not assume ordering. `keyrotation.reconciled` carries no `operator_id` by design.
5. INFO (carried): the 16-hex `old_fp`/`new_fp` are sha256 prefixes of the key hash; fine for high-entropy machine keys, weak evidence for human-chosen keys (design S11 already says 16).
