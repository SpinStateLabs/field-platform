## Objections first (FORCE-O)
1. The PR adds belt and braces: a catch-all `except Exception` around the whole read, AND the specific `UnicodeDecodeError` branch AND `OverflowError` in the inner tuple. Any one of them gives the same outcome for the four test inputs, so the specific branches are redundant (mutants U1, U2, U16 are equivalent) and the catch-all, the only part that matters for an UNFORESEEN exception, is not exercised by any test (U3, U4, U9, U10 survived).
2. The tests run the corrupt cursor through two ticks, which is the right end-to-end check, but a corrupt cursor is a one-way door: posting stays disabled until a human repairs the file. That is the SPEC's stated behaviour ("a corrupt cursor disables posting rather than starting from zero", quoted in the test docstring) and is the safe direction for a billing-adjacent counter; I did not verify SPEC.md.
3. Counters are accepted when they are floats or numeric strings (`int(1.9)` is 1, `int("7")` is 7); the PR neither changes nor tests that, and a float that truncates silently is a different class of corruption (not claimed).
Steelman: the fix closes the hole that matters (tick 1 failing, tick 2 seeing an empty, error-free cursor and re-posting every session's whole history), the four named bad inputs each have a test case that runs two ticks and asserts no usage post, the error string and zero tick errors; five behavioural mutants die.
