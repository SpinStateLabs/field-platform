## OBJECTIONS FIRST
1. (Agrees with Lane 10's F-C546-1, MEDIUM-LOW in my reading.) `if grep ...; then fail; fi` treats grep's exit code 2 (a pattern or file error) like "no hit": the step passes. The new pattern is 240 characters of nested brackets, quotes and shell escaping, so an edit that breaks it would silently disable the guard in CI. The PR's tests would catch a broken pattern on the next run, so it is a second line of defence, not a hole today. Fix: `grep ...; rc=$?; [ "$rc" -eq 1 ] || fail` (0 hit, 2 error).
2. Real external references that the shipped pattern does NOT catch (all measured, GNU grep 3.11; the PR calls the guard an accident guard, so these are scope notes, ordered by how plausible they are in this page): an `srcset` or `imagesrcset` attribute (`srcset=` is not `src=`), a JavaScript dynamic `import("https://...")`, `new WebSocket("wss://...")`, `new EventSource(...)`, `XMLHttpRequest.open("GET", "https://...")`, `navigator.sendBeacon`, `window.open`, `location = "https://..."`, `importScripts`, a `fetch(u)` whose url sits in a variable, a bare `"https://..."` string, `ping=`, `background=`, `cite=`, `manifest=`, an attribute value with a leading space or on the next line (grep is line-oriented), a CSS `image-set("https://...")` or `@import "https://..."` string form (the `@import` form IS caught), a `ws:`/`wss:`/`ftp:` scheme in an attribute, entity-encoded or backslash-spelled schemes. A line-regex cannot see most of these; a better design is to extract every absolute URL and protocol-relative `//host` literal from the page and fail unless it matches a short allowlist (for example the `www.w3.org` namespaces and the text strings the page prints), which is how the C-453 bind rule was fixed.
3. Two FALSE POSITIVES (the `-i` plus the bare word `data` in the attribute list): prose `data = https://example.org` and a JavaScript line `let data = // a comment` both match (`data` followed by `=` and `//`), so a future harmless script line could fail the smoke job. Neither is in the shipped page. The `data` alternative is there for `<object data=...>`; anchoring it (`<object[^>]*data`) removes the false positives.
