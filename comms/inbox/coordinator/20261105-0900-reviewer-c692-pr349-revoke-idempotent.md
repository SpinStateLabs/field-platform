# C-692 reviewer (Lane 4): PR 349 head 1e3dea5 (the card names 50c87b9; one commit later), delegation-authority idempotent ledger-first revoke and exact introspect (C-625, C-725; closes reviewer C-527 and C-701 findings)

VERDICT: PASS WITH CONDITIONS on 1e3dea5a7fac517757e31290e125652930d6568c. Every scenario the card names behaves as the code comment states: a revoke retried after a ledger failure (502, 502, 200: one event, one stable id), a crash between ledger and store (the retry completes, the token ends revoked with the same id), 32 concurrent revokes of one token (one ledger append), two apps on one sqlite file (same id in both events and in the store), an unknown token (404), and exact-match introspect. The whole CI-equivalent set is green on the merged state. Conditions: (a) the guarantee is at-least-once, so the ledger can hold two `delegation.revoke` events for one token, and during the crash window the token introspects ACTIVE while the ledger already says revoked (F-C692-1); (b) the unknown-token 404 and the loser-of-a-race response are not pinned by the suite (F-C692-2); (c) a ledger answer of 401/403/422/500 is reported as "ledger unreachable" (F-C692-3).

## OBJECTIONS FIRST
1. F-C692-1 MEDIUM-LOW (at-least-once has a visible window and a visible duplicate): `api.py` revoke appends to the ledger BEFORE the conditional store write. Probed with `save_revoked` made to raise once: the first call fails, the ledger holds one `delegation.revoke` event, the token is NOT revoked, and `POST /introspect` and `POST /oauth/introspect` both return `active: true` for it. The ledger (a stop-type event, `sealed-ledger store.py:131`) and the token store disagree until somebody retries. A retry heals it (200, token revoked, same id; the ledger then holds TWO events with ONE distinct revocation id). Two processes racing on one file also leave two events (probed: events 2, distinct ids 1). The code comment says so in so many words, so this is not a hidden defect; what is not stated or built is (i) any reconciliation that finishes a revoke whose ledger event exists and whose row is not revoked, and (ii) that a reader of the ledger must treat `delegation.revoke` as "revoke requested", not "token inactive". Consumers: `compliance-crosswalk engine.py:163` uses `n > 0` for the pass decision and prints the raw count ("N revoke event(s)", so a duplicate inflates the printed number only); `incident-replay engine.py:267` prints one line per event (a repeat is a second "revoked" line). Neither breaks. Fix or state: document the event as "requested", or add a startup/periodic sweep that revokes tokens named by an unmatched revoke event. NOT a regression: the previous code had the same ledger-first order and a worse id story.
2. F-C692-2 LOW-MEDIUM (two behaviours are not pinned; 2 of 19 mutants survive): (a) `raise HTTPException(404, ...)` for an unknown token replaced by a bare `raise` (the exception then escapes as a 500) is not caught by the delegation-authority suite, although the behaviour is right (probed: 404, also for `a%2Fb`); (b) `return stored` replaced by `return revoked` survives. (b) is nearly equivalent: `revoked` and `stored` carry the same id, because the id is a function of the token id and the in-process lock serialises the process; they differ only in `revoked_at` for a loser of a CROSS-process race (the loser would return its own timestamp, not the stored one). Pin both: a test for revoke of an unknown id, and a two-app race that compares the two responses' `revoked_at`.
3. F-C692-3 LOW (a ledger refusal reads as an outage): any `LedgerUnreachableError` is a 502 "ledger unreachable". Probed with a stub ledger answering 401, 403, 422 and 500: all four give revoke 502 and the token stays unrevoked. Fail-closed and correct for the token (it is not revoked without evidence), but an operator looking at "unreachable" for a bad ledger credential loses time. Not a security defect.
4. F-C692-4 LOW (dead value): `_won` is returned by `save_revoked` and discarded by the only caller, so the "did this call win" bit has no consumer (its mutant `rowcount != 1` is killed by a store-level test, so the value is pinned, just unused). Drop it or use it (for example to count repeats in a metric).
5. LOW (scope, from the code): the lock is per process. Cross-process safety rests entirely on the stable id and on `AND revoked=0`, which is sufficient for the id guarantee (probed) but not for "one event" (objection 1). A second worker process is therefore a supported, observable source of duplicate events, not an error.
6. NOT A DEFECT (probed): different tokens revoke in parallel (8 revokes with a 50 ms ledger each: 0.11 s wall, serial would be at least 0.4 s) and the lock table is empty afterwards (0 entries after 32 contenders); a second revoke of a revoked token returns 200 with no new event; expired, revoked and unknown ids give `{"active": false}` on both introspect endpoints; a padded id, a trailing newline, an upper-cased id, a one-character prefix, a 100 000-character id and an id with a NUL are all inactive on both endpoints (exact match); an empty `token` field is a 400 on `/oauth/introspect` and `active: false` on `/introspect` (the two endpoints differ for the empty string by design in the diff: RFC 7662 form field required vs a JSON body).
