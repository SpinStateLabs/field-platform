## OBJECTIONS FIRST
1. A 4xx is not always "duplicate". After a 5xx the next tick's 4xx (400 "already confirmed", but equally 401/403 from a revoked console key, 404, 422) is counted `confirm_duplicate`, the ask is marked answered and never re-sent. Probe (real `_answer` path, fake API: first send 503, second 403): `confirm_duplicate 1, confirm_rejected 0`, ask answered, not stale. A permanent refusal is therefore reported as success-like and the session stays blocked with no `confirm_rejected` count (before the PR it was counted). F-C404-1 MEDIUM (design; the builder flagged the fresh-sentinel decision only, not this one).
2. The stored result is never used. `possibly_sent[eid]` keeps "allow" or "deny" but the code only tests presence (`pop(...) is not None`). Probe: allow send lost (503), sentinel then says BLOCK (kill), deny send gets 400: decisions list shows `('allow', sent False)` and `('deny', sent False, rejected True)`, counters `allowed 0`, `confirm_duplicate 1`. The API may have applied the ALLOW, the kill's deny was refused, and nothing in the record says the effective answer might be the earlier allow. The kill still wins for every later tool use (the sentinel is asked again), so no new authority is granted; the gap is audit clarity. F-C404-2 LOW (put the remembered result on the duplicate record, or count `confirm_duplicate_conflict` when it differs from the new verdict).
3. Eviction forgets the oldest of 64. An evicted event whose earlier send really was applied then reads a 4xx as terminal `confirm_rejected` and goes stale (the pre-PR behaviour), so the failure mode is the old one, not a worse one. Pinned (bound 63, 64, 65 and evict-newest mutants all red). Noted, no finding.
4. The mark can outlive a kill or a revoked token only as a flag: the retry takes a fresh `_check` every tick, so a kill still produces a deny and no allow is replayed (the probe above shows the deny send). `_check` is not skipped by the mark (mutant below). Session mixing: the dict lives on `SessionState`, keyed per session; a second session with the same event id does not see it (state objects are separate; not separately tested). F-C404-3 LOW (add a two-session test).
