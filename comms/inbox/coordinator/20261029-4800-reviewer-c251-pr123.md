## OBJECTIONS FIRST
1. F-C251-1 MEDIUM-LOW (the card's "what state?" question): the order is prepare, key output, registry write. A failure in the LAST step (the registry write) leaves the key behind. Probe on the unmutated head: registry file in a read-only directory, key to a file elsewhere. `prepare_entry` succeeds, the key file is written (mode 0600), `atomic_write_text` raises PermissionError out of `main()` as a traceback (not an `error:` SystemExit, exit status non-zero), the registry is unchanged. State left: a key file whose sha256 is registered nowhere, and the operator holds a key that authenticates as nobody. In the printed-key mode the key has already been shown. The PR narrows the window (every logic refusal is now before the key); it does not close it, and no test pins the surviving state. Not a regression: before the PR the same failure existed plus every logic refusal.
2. F-C251-2 LOW (race, not run): `prepare_entry` reads the registry and `write_registry` writes the computed document at the end, with the key file written in between. A concurrent edit of the same file in that window is overwritten (read-modify-write, last writer wins). The window was microseconds in `add_entry`; it now spans the key-file write and the prints. Same class as before; the PR does not claim to fix it. I did not run a concurrent writer.
3. F-C251-3 LOW (test gap): `json.dumps(out, indent=2)` is unpinned. Mutant `indent=4` survives all four keygen suites (75 passed); the success tests read the file back as JSON. Harmless for loaders, but "the success path is unchanged" is not byte-pinned.
4. The card's wording "`write_registry` runs last" holds only because the key file is written before it; a failure between the two is objection 1.

## CONCLUSION
PASS on 9eea074. A refused `--add-to` leaves no key file, prints no key and does not touch the registry, for every refusal `prepare_entry` knows; the success output and file modes are unchanged and PR 113's pins still pass. What a pass does NOT prove: that a failure after the key is written (the registry write, a disk error) leaves a consistent state (F-C251-1), that a concurrent writer is safe (F-C251-2), or that the registry file's bytes are unchanged in format (F-C251-3).

PROPOSED CARD (the coordinator numbers it): builder, tools/operator_keygen.py plus tests: either write the registry first and the key second (a failed key write then leaves a registered hash nobody holds, which a revoke of the row clears) or make the registry-write failure a `SystemExit("error: ...")` that names the key file as unregistered and removes it when `--key-file` created it; add a test that forces `write_registry` to raise and asserts the chosen state; pin the indent. Done when: that test is red on the current head. This is a design choice for Don (which half-state is safer); I recommend registry first, key second, because an unheld registered hash is inert and an unregistered key is the case that confuses an operator.
