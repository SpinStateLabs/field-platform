## Objections first (FORCE)
1. Over-refusal: any host made only of `0-9 a-f x . ` characters that `socket.inet_aton` accepts is refused, including legitimate-but-unusual spellings (a leading-zero IP such as `010.0.0.1`, a single-label numeric service name such as `1` or `0`). Observed: `http://0/`, `http://1/` and `http://0x7f.1/` are refused. Intended by the PR; a compose service literally named `1` would break (LOW).
2. Spellings this PR does NOT cover, measured on this head (Python 3.14 venv, httpx 0.28.1): `http://169.254.169.254./` (trailing dot) BUILDS a client with host `169.254.169.254.`; `http://[64:ff9b::a9fe:a9fe]/` (NAT64) BUILDS. Whether either reaches the metadata endpoint depends on the resolver and network; I did not test a connection (MEDIUM-LOW, unverified, outside the PR's stated claim: hex/decimal/short/octal and mapped IPv6).
3. `socket.inet_aton` is libc-dependent: the refused set could differ between the Windows run here and the Linux CI/estate hosts (not measured on Linux by me).
4. `test_mapped_is_unwrapped_explicitly` never calls the guard (it asserts a stdlib property), so it pins nothing; the real pin of the unwrap is the `http://[::ffff:169.254.169.254]/` entry in BAD, which only has teeth on Python versions whose stdlib does not already flag the mapped form (see mutants M1/M7).
