## Facts (HIGH, from the files)
1. Only the proxy publishes a port: docker-compose.yml:152 `ports: ["8080:8080"]`; GB10 overlay `ports: !override ["18080:8080", "18443:8443"]`. No service has `ports:`.
2. Every service listens on 0.0.0.0 INSIDE its container (`command: <svc> serve --host 0.0.0.0 --port 80xx`, docker-compose.yml:158-300), so any container on the same compose network reaches `http://registry:8001`, `ledger:8002`, `delegation:8003`, `killswitch:8005`, `governor:8006`, `fedbroker:8010`, `console:8011`, `lifecycle:8012` directly. The R2 Caddy block (refuse `/operator/verify-hash`, `/operator/rotation-state` unless loopback and no X-Forwarded-For) is on the proxy only; it is not in the path.
3. The eight operator-block services (the ones that serve the two routes): sealed-ledger, agent-registry, delegation-authority, kill-switch, spend-governor, federation-broker, ops-console, lifecycle-manager (rotation_events.SERVICES). The routes answer only when the operator layer is armed (mode != OFF) AND a perimeter secret is set (`internal_routes_enabled`, operator_health.py ~448). So the ONLY remaining control on a direct call is the perimeter secret `x-field-auth`.
4. That secret is one estate-wide value: `FIELD_SHARED_SECRET: ${FIELD_SHARED_SECRET:-}` in the shared `*env` anchor (docker-compose.yml:146), so every service, the approver (profile `approver`, gets `*env`) and the canary-agent hold the same secret.
5. GB10 overlay: docker-compose.gb10.yml comment ~140-150 and `networks:` at ~250, 262, 274, 285, 305, 372: sentinel, ledger, delegation, killswitch, governor, forcegw are `[default, agents]`; `canary-agent` is `[agents]` only (~482) and its environment carries `FIELD_SHARED_SECRET: ${FIELD_SHARED_SECRET:-}` (~478). `agents` is `internal: true` (no route to the internet). So the canary-agent (the test "untrusted agent" container) can call, directly and with the estate secret, four operator-block services: ledger, delegation, killswitch, governor.
6. Fly: not exposed. integration/fly/entrypoint.sh:6-7 and :233-273 start every service on `--host 127.0.0.1`; only Caddy is 0.0.0.0 (fly.toml:58 `internal_port = 8080`, `force_https = true`). The Caddy block is the only way in from outside; anything INSIDE the one machine can still call 127.0.0.1:80xx (the in-machine rotator, R7, by design).

## What a holder of the perimeter secret on the compose network can do
a. POST /operator/verify-hash on any of the eight (or the four from `agents`): learn, for a candidate sha256 and an operator id, `matched` current/next/none, `matchable_now`, `retired`, plus registry format, generation and file sha prefix. A candidate-hash oracle: harmless for a random 256-bit machine key (not guessable), meaningful only for a human-chosen key. Never ledgered, never counted, no rate limit (C-20 finding 3).
b. GET /operator/rotation-state: every row's 16-hex slot fingerprints (the sealed row shows `(sealed)`), validity windows, next-key presence, expiries, retired-slot counts, own identity fp, counters, `clock_synced`. That is the whole key schedule and which identities are mid-rotation: reconnaissance for timing an attack on a rotation window.
c. Beyond those routes (not new, but the same enabling condition): while Phase G is LOG-ONLY (current state), the perimeter secret is the sole control on guarded writes, so a container holding it (canary-agent today) is not constrained by operator keys at all. Under ENFORCE the operator key is the second factor.
d. From the GX10 side (MEDIUM, NOT a repo fact): per my session notes of the GX10 self-hosted runner (2026-10-25), the Managed Agents sandbox containers are attached to the estate's docker networks. If that is the compose `default` network, those containers also reach all eight services directly; they do not hold the secret unless it is given to them. I did not verify the network membership.

## Not affected
Callers outside the host reach the services only through Caddy (refused). Fly outsiders likewise. A container without the perimeter secret gets 401 on both routes (the authn middleware demands it; `/health` is open and reveals only the operator block counters).

## Mitigations, in order of value for cost
1. Do not give agent containers the estate-wide secret. canary-agent needs it only for killswitch heartbeat and sentinel/governor/ledger calls: mint a per-agent derived secret (HMAC of the estate secret and the agent id) and let the services accept either, or at least a distinct secret for the `agents` network. This also closes (c) for LOG-ONLY. Biggest single reduction.
2. A second, internal-only secret for the two routes: `internal_routes_enabled` additionally requires `x-field-internal` equal to `FIELD_INTERNAL_SECRET`, held only by the rotator and the observer (the ledger). Cheap (operator_health.install_routes), default-off compatible, and it keeps working when a service or agent container is compromised.
3. Segment the network: put the eight services, the rotator and the ledger observer on a `control` network that no agent or sandbox attaches to; services that agents must reach (sentinel, killswitch, governor, delegation, ledger, forcegw) stay dual-homed, so the four operator-block services on `agents` still need (2). Pure network separation alone does not close it for those four.
4. Count every call to the two routes and ledger a row when the caller is not the rotator (C-45 f3 asks only for a count); log `request.client.host`. Cheap detection.
5. Runbook: declare that `/operator/*` internal routes are protected by the perimeter secret and network position, not by the Caddy block, on the GB10 compose network (C-46).
Decision for Don: whether (1)/(2) are Phase G Stage 2 prerequisites (they alter ENFORCE assumptions: today ENFORCE adds the operator key but the oracle and rotation-state stay secret-only).
