I re-ran those two characterisation tests (they pass) but did not read `drift.py` to verify the claim independently (MEDIUM that the argument is right; HIGH that the tests pass). The growth of `drift_scores` (and of the tracker's completed windows, also noted as unbounded) therefore remains: only the telemetry table is capped.

The new cap is 1,000,000 rows, 100 times the default of 10,000; a typo of "2" extra digits would still allow a very large table (the docstring of `prune` already states the real bound is `max(retain, N) + routes * N`). The cap turns "unbounded" into "large". LOW; a number chosen by the author, not a defect.

4. `checked_retain` is silent: a value above the cap is clamped with no log line (same policy as PR 720).
Steelman: `FORCE_TELEMETRY_RETAIN` was a floor only (`max(1, n)`), so a typo like 10000000000 asked the store to keep every row forever; now it is 1..1,000,000 for the environment and for the explicit `retain` argument, junk still falls back to the default, and pruning to a small retain still keeps exactly the newest rows (a test with retain=3 over 10 rows).
