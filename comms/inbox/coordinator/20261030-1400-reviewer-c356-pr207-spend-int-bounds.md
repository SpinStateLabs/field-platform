OBJECTIONS FIRST
1. F-C356-1 MEDIUM-LOW (PROVEN): the policy clamp loosens a burst limit. `get_policy` (core.py:659-664) serves any row whose window is above `MAX_RATE_PERIOD_SECONDS` (366 days) with the window clamped down to 366 days. A window is a look-back: a shorter one counts fewer tokens, so the check is looser. Probe (GX10, in-process app, row written by hand as an old governor could have: a limit of 100 tokens per two years, with 100 tokens recorded 400 days ago, then one more token reported): without the clamp (the PR 208 tree, which has no policy clamp): `rogue_burst` "101 tokens in the last 63244800s >= limit 100"; with the clamp (PR 207 merged onto 208): the `rogue` list is empty and `GET /policies` shows the window as 31622400. Lowering the LIMIT (the other half of the clamp) is the safe direction; lowering the WINDOW is not. [HIGH, run]
2. F-C356-2 LOW: the policy clamp's warning (core.py:660-662 area) is not pinned: mutants "log removed" and "log also prints the value" both survive the new file. The cap clamp in PR 208 has both pinned (both die there). [HIGH, run]
3. F-C356-3 LOW: the clamp block can be forced always-on (`if` to True at core.py:659) and no test notices (in-bound rows would then log a spurious warning on every read). [HIGH, run]
4. A policy row stored before the bounds with a window between 366 days and the point where datetime arithmetic overflows is valid and working today; after this PR it is silently shortened. Safer than clamping to 366 days: leave the stored window alone below the overflow point (about 8.6e13 seconds for `timedelta`), and clamp or refuse only above it; or read the stored values unvalidated and say so. [MEDIUM on the exact overflow point, I did not measure it]
5. The library layer is not bounded: `SpendRecord` (core.py:156-158) and `GovernorStore.record(...)` still take any int; `record(agent, 2**63, ...)` raises `OverflowError` (probe). The service validates before it reaches the store, so no 500 at the service; a library caller gets the exception. LOW. [HIGH, run]
6. Accepted but odd inputs (unchanged by the PR, from Pydantic's lax mode): `True` is accepted as 1, `1.0` as 1 and the string "5" as 5 on every integer field; `1.5`, "1e3", negatives and anything above the bound are 422. LOW. [HIGH, run]
