## OBJECTIONS FIRST
1. The refusal is check-then-write, not atomic. `commit_registry` compares the file's bytes with the earlier snapshot, then runs `write_registry` (a temp file, `fsync`, `os.replace`): the window between the compare and the rename includes the fsync, so a second writer that commits in it is overwritten. Measured: two real `operator_keygen` processes started together against one registry, 200 trials: 151 both registered; 2 one refused (the designed outcome); 47 LOST UPDATES, in which both processes exited 0 and printed "registered sha256 ...", both key files exist, and the registry holds only one of the two rows (47 of 200, 23.5%; the loser's key authenticates as nobody, exactly the state this PR set out to remove). The PR body says so honestly ("narrows the window, does not close it (no lock)"); the card asked for more. F-C354-1 MEDIUM. HIGH.
2. "No key is left behind" holds for a refusal but not for every exit: a key file stays on disk after a Ctrl-C or an unexpected exception during the registry write, and after a SIGKILL. The cleanup is `except SystemExit` only. F-C354-2 LOW to MEDIUM. HIGH.
3. In stdout mode the row is committed before the key is printed, so a failure of the print itself (a closed pipe, SIGKILL between the two) leaves an ACTIVE registry row whose key nobody ever saw (and the operator id is burned, since a retry is refused as a duplicate). The inverse of the old defect, and a deliberate trade, but undocumented. F-C354-3 LOW.
4. A failed write of the key file itself (disk full) is still a traceback and leaves an empty 0600 file, which then makes a retry with the same path fail. Unchanged from main, not claimed fixed. F-C354-4 LOW.

## REASONING
1. (1) The order and what is on disk after each boundary, by fault injection in a driver (marker key; `disk` = registry rows, key file, stray temp files). Stdout mode (key printed) / key-file mode:
   - duplicate id refused in `prepare_entry`: registry unchanged, no key, no temp file; both modes. 
   - key file already present (key-file mode): `FileExistsError` (a traceback naming the path only); the pre-existing file is intact (`PRE-EXISTING`), registry untouched: the refusal comes before the registry is touched. 
   - registry unreadable (mode 000): `error: cannot read ...`, nothing written, no key, both modes.
   - read-only directory at the commit (stdout mode, a real 0555 directory): `error: cannot write ...`, registry unchanged, no key printed, no temp file. (The key-file variant of this case failed earlier for a trivial reason, the key file was in the same read-only directory, so I rely on the PR's own test, which puts the key elsewhere and passes: 4 real read-only-directory tests ran on this non-root Linux user.) 
   - registry write fails with ENOSPC (simulated): `error: cannot write ...`, no traceback, registry unchanged, key file absent in key-file mode, key not printed in stdout mode.
   - SIGKILL at the start of the commit: stdout mode: nothing on disk, no key shown (clean). Key-file mode: the key file REMAINS (29 bytes, mode 0600) and the registry is unchanged: an orphan key (F-C354-2). 
   - SIGKILL at the first print, after the commit: stdout mode: registry row present, key never shown (F-C354-3). Key-file mode: row and key file both present (consistent). 
   - stdout closed (EPIPE) when the key line is printed: exit 120, `BrokenPipeError`; row committed, key lost in stdout mode (F-C354-3); consistent in key-file mode. 
   - Ctrl-C (KeyboardInterrupt) and an unexpected `RuntimeError` inside the registry write: stdout mode: registry unchanged, no key shown; key-file mode: the key file REMAINS, the registry is unchanged (F-C354-2).
   - concurrent edit (bytes appended after `prepare_entry`): refused, `error: ... changed while the key was being made; nothing was written`, key file removed, the other writer's bytes kept; both modes. 
   - success control: row present; stdout mode prints the key once; key-file mode writes 0600 and prints only the path. 
   HIGH.
2. (2) Two writers. Forced interleave (A pauses after its read, B runs to completion, A resumes): B exit 0; A exit 1 with the `changed while` error; final rows `[don, writerB]`; A's key file removed; B's key file present. So the compare does catch a completed concurrent write. HIGH. Stress with two real simultaneous processes: see Objection 1 (47 of 200 lost updates; 2 of 200 refused). HIGH. A second narrow hole: an edit that changes the file and changes it back before the compare is invisible to a byte compare (my A-B-A case passes, harmless there because the bytes equal the original). LOW.
3. (3) Mode from creation. `os.open(key_file, O_WRONLY|O_CREAT|O_EXCL, 0o600)` (flags 0o301, mode 0o600 captured at the call). Observed through `fstat` at the first moment the file exists (size 0, before any byte is written): mode 0600 under umask 000, 022 and 077, and 0400 under umask 277 (a umask only narrows). So there is no window with a wider mode, and no secret is in the file before it is 0600. A new registry file keeps the previous behaviour (0666 masked by umask; it holds hashes only). HIGH.

## FINDINGS
- F-C354-1 MEDIUM (PROVEN, 47 of 200): serialise the whole read-modify-write: take `fcntl.flock` on a lock file beside the registry (or `O_EXCL` lock) from the snapshot to the rename, and re-read under the lock. Cheaper partial fix: after `os.replace`, re-read the registry and require its own row; on a miss, remove the key file and exit with an error (turns a silent loss into a visible one). Done when two simultaneous writers never both succeed with one row (the same 200-trial run shows 0 lost updates); mutant: drop the lock must go red in a two-process test.
- F-C354-2 LOW to MEDIUM (PROVEN): replace `except SystemExit` with `except BaseException` (or `try/finally` with a `committed` flag) so Ctrl-C and unexpected errors also remove the key file; SIGKILL cannot be handled, so also write the key file to a temp name and rename it after the commit (then a kill leaves a temp, not a usable-looking key). Mutants: `KeyboardInterrupt` and `RuntimeError` in the commit must leave no key file.
- F-C354-3 LOW (PROVEN): stdout mode registers the row before showing the key; a failed print leaves an active row with no key. Document the recovery (revoke the row and re-run under a new id) in the tool's docstring and the runbook, or print the key first to a buffer and commit only after a successful flush (still racy but narrower).
- F-C354-4 LOW (PROVEN, unchanged from main): a key-file write failure (ENOSPC) is a traceback and leaves an empty 0600 file; convert it to an `error:` exit and unlink the file.
- F-C354-5 LOW: the byte compare cannot see an edit that is reverted; compare `st_mtime_ns` and inode together with the bytes, or use the lock of F-C354-1.

## CONCLUSION
PASS on 80658bd for its stated scope: the order is prepare, key file, registry commit, print; a refused or failed registry write leaves no key file and shows no key (the common failures: read-only directory, full disk, unreadable file, duplicate id, concurrent edit already committed); the key file is 0600 from the first instant; the stage 0 tests keep their assertions; the new tests and my mutants go red; nothing leaks. It does not make concurrent writers safe (23.5% silent lost updates under a simultaneous start), nor remove the key file on Ctrl-C or SIGKILL. Take the merge, queue the follow-up (F-C354-1 and -2), and until then treat "refused" as best-effort and run one keygen at a time per operators file.
