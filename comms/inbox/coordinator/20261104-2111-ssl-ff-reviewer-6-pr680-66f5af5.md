## Objections first (FORCE-O)
1. The claim is "JSON of the wrong shape is HeartbeatUnreachable", but `Heartbeat.killed` is validated in pydantic's lax mode, so a wrong-TYPED field is accepted and coerced. Measured on the head with an otherwise valid body: `killed: "false"` is ACCEPTED as live (killed=False), `killed: 0` ACCEPTED live, `killed: 1` and `"true"` and `"yes"` ACCEPTED as killed; only `"maybe"` (the test's case) is refused. A kill-switch answer whose `killed` is the string "false" is therefore read as "alive". The server is trusted and normally sends a JSON bool, so exploitability needs a broken or tampered server answer, but the module's stated rule is "liveness unknown, halting" for anything not understood. Outside this diff (the model is unchanged); MEDIUM for a follow-up (`strict=True` or a `StrictBool` on `killed`).
2. `RecursionError` and `TypeError` are caught but neither branch is exercised: H2 (RecursionError dropped) and H3 (TypeError dropped) survive the PR's file and the whole field-agent suite (239 passed). I measured separately that a 100000-deep JSON array ("[" repeated) reaches the head's handler and is refused as `HeartbeatUnreachable(RecursionError)`, so the code is right today, but no test would notice if that clause were removed. TypeError: I did not find a body that raises it (possibly unreachable; LOW). LOW test gap.
3. The message carries the exception type name only; the cause is dropped (`from None`), both pinned (H5, H6 killed). The fixed text "heartbeat answer unreadable (ValidationError)" does tell an operator the server's answer was wrong, not the status. Fine.
Steelman: before the change a 200 with an HTML error page (a proxy, a wrong host) raised a raw JSONDecodeError or pydantic ValidationError out of the heartbeat, which `ensure_alive` did not treat as "halting"; now every unreadable answer is the fail-closed `HeartbeatUnreachable` (a subclass of AgentKilled), for both heartbeat and checkin, and `ensure_alive` halts with AgentKilled.
