# C-185 reviewer report: tools/operator_keygen.py read, `--check` vs the service, key handling, partial writes (main 7b4d6f7 + PR 94 tests)

VERDICT: `--check` agrees with the service on everything the shared parser decides; the only disagreement is at the JSON layer (F-C181-1, still open). The key file's permission mode is untested: widening it to world-readable passes all 54 keygen tests. 93 mutants run, 77 killed, 16 survived.

OBJECTIONS FIRST
1. "Same parser" is true of `parse_registry_doc`; the service also applies runtime state (retired-hash memory, generation monotonicity) that a static `--check` cannot know.
2. File-mode findings are POSIX; on Windows the 0600 request is advisory (the docstring says "where the OS has it").
3. I mutated operator_keygen.py only, against its three test files.

ASSUMPTIONS
1. Main 7b4d6f7 with PR 94 test change (2518d1d); `tools/operator_keygen.py` 303 lines; tests `tools/tests/test_operator_keygen.py`, `_format2.py`, `_stage0.py` (54 tests, 0.2 s). Generator v1 39 mutants (34 killed), v2 sample 60 of 267 (54 run: 43 killed; 6 syntax skips). [HIGH]

REASONING
1. `--check` vs service: `check_file` (:146-190) decodes `utf-8-sig`, then calls `parse_registry_doc(doc, require_active=True)`: the same function `load_registry_snapshot` uses, so format 1 vs 2, BOM, aliases (shared, equal to an id, break-glass), scopes, windows, `status`, sealed rows are decided identically; `require_active=True` is stricter than a LOG-ONLY service. They differ only where the service adds state or a different JSON read: (a) duplicate JSON keys and (b) 50,000-deep nesting: service refuses, `--check` passes / crashes (F-C181-1, proven in C-181); (c) retired-hash memory and generation ordering are per-process service state (Declared, design section 11). [HIGH]
2. MEDIUM, F-C185-1 (PROVEN): the key file's creation mode. `os.open(a.key_file, O_WRONLY | O_CREAT | O_EXCL, 0o600)` (operator_keygen.py:284). Unmutated: a generated key file is mode 600. Hand mutants of the constant: `0o644`, `0o666`, `0o777`: all three leave the suite green (54 passed each); the generator's `0o601` mutant survives too. So the one property the docstring promises ("created exclusively, mode 0600") for the file that holds a bearer key has no test. [HIGH]
3. LOW, F-C185-2: usage errors can exit 0. Survivors L276 and L279 (`return 2` -> `return None`): `main` then returns None and `raise SystemExit(main())` exits 0 on a bad `--event-prefix` / a missing `--event-prefix` for `ledger_attribute`; L251 (`--check takes no other option` text) and L274 (`--add-to needs --operator-id`) also survive (the registry check after it still refuses, so the outcome is a different message). Exit codes 1 and 2 are the documented contract ("Exit 0 = valid"). [HIGH]
4. LOW, F-C185-3: the key file content is not pinned: L286 `fh.write(key + "\n")` with the string emptied survives; the script entry `if __name__ == "__main__":` (L302) forced False survives (tests call `main()` in process; running the file as a program is untested; my direct runs worked). [HIGH]
5. Partial writes (read): `add_entry` validates the WHOLE new document with `parse_registry` before writing, then `atomic_write_text` (:67-96): temp file in the same directory, flush and fsync, `chmod` to the old file's mode (umask default for a new file), `os.replace`, temp unlinked on any failure (`except BaseException`), directory fsync on POSIX: a reader sees old or new content, never a partial file. The key file itself is written non-atomically after `O_EXCL` creation: a failed write leaves an empty or partial file at that path (the next run then fails on `O_EXCL`). Order matters: the key is generated and written/printed BEFORE `add_entry`; if `--add-to` then refuses (duplicate id, invalid registry), the operator holds a key whose hash was not registered (harmless, but the stdout already showed "key_sha256: ..."). [HIGH on the code; the partial-write cases were read, not injected]
6. Key printing: with no `--key-file` the key is printed once on stdout by design ("shown once"); with `--key-file` it is "(not printed)"; the key never appears in error messages (every error names ids, rows and field names; `_shown_fields` / `printable_id` hide key-shaped ids). New operators files get `0o666 & ~umask` (L63, a hash-only file, not secret); an existing file keeps its mode (:75). [HIGH]
