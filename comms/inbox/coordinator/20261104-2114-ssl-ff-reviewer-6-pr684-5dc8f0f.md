## Objections first (FORCE-O)
1. The test named "the limit is accepted and one over is 422" does not test one over. For name, owner and domain the over-limit value is `MARK + "y" * limit` (about 223 or 87 characters), so a limit that is one too high survives: Q5 (MAX_NAME 201), Q7 (MAX_DOMAIN 65) and Q25 (MAX_OWNER 201) all pass the PR's file AND the whole agent-registry suite (354 passed). The at-limit side is pinned (a limit one too LOW is killed: Q6, Q9), so the bounds can drift upward by one unnoticed. The attested_by test does use a true 201 (Q9 killed). LOW, easy fix (use `"x" * (limit + 1)`).
2. The request bounds and the stored data now differ: `AgentRecord` stays lenient so legacy rows (5000-character name, blank owner) still read, which the last test pins. A PATCH of any other field on such a legacy row is fine, but re-sending the legacy name unchanged in a PATCH is now a 422 (not tested; reasoned from the models, LOW).
3. `manifest_ref` is bounded at 512 but not stripped by design (a whitespace ref is SET and the resolver refuses it). Mutant Q14 (stripped) passes this PR's file but is killed by the existing D3b test in the whole suite (1 failed), so the rule is guarded elsewhere (HIGH, measured).
4. The ENVIRONMENT.md anchor for FIELD_DATA_DIR moved from api.py:121 to :115; `python tools/environment_anchors.py --check` on the head reports 0 wrong anchor row(s) (HIGH).
Steelman: before the change name, owner and domain accepted arbitrary length and `attested_by` landed unbounded in the ledger's `registry.attested` event; whitespace padding made two names that looked identical distinct. Now text is stripped first, then bounded, with a 422 that never echoes the input (MARK test), on POST, PATCH and attest.
