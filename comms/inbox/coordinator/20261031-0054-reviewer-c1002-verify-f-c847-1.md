## Reproduction at file:line (packages/field-core/src/field_core/operator_auth.py, _apply_retired_memory)
- :1252-1257: a key absent from a file with a higher generation than the previous one is recorded as retired at THAT generation (`retired[h] = max(generation, ...)`).
- :1262-1266: the high-water generation and hash set are then updated to the current file.
- :1267: the refusal test is `h in retired and generation <= retired[h]`. A key retired at 42 returns in a file at generation 43; 43 > 42, so it is NOT refused, even when 43 is the highest generation already seen (the current file).
- Probe with the real function (synthetic hashes A, B, C): generations 41 [A], 42 [B], 43 [C]: A retired at 42, B at 43. A generation-43 file holding A: ACCEPTED (bug). Generation 43 holding B: refused. Generation 42 holding A: refused. Generation 44 holding A: accepted (declared design: a higher generation may re-admit) (HIGH, run).

## Is it real, and what is the impact?
Real: a retired key can come back at the same generation as the highest ever seen, without a bump. Impact: a hand edit or a merge that forgets to raise the generation, or a restore that re-issues the high generation with an older key list, silently re-admits a retired key; the PR's own docs and C-847 say the memory should catch stale restores. It does not help an attacker with file write access (they can bump). MEDIUM-LOW.
