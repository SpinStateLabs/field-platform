## OBJECTIONS FIRST
1. The doc-pin failure above (F-C736-0, blocking).
2. F-C736-1 LOW to MEDIUM: bytes are bounded, TIME is not. Both clients use `urllib` with a per-operation socket timeout, so a server that sends one byte every 0.4 s defeats a 1.0 s timeout: my probe with `urllib_call(..., timeout=1.0)` against a 40-byte drip returned after 16.0 s with the full (bad) body; with a 64 KiB cap a dripping server could hold the caller for about 65,536 x the per-byte delay (hours at 0.4 s). The canary is a health probe against estate services and FieldClient runs inside the agent's own request path, so a stalled or hostile peer can hang the caller well past its `timeout`. Fix: a wall-clock deadline around the read loop (read in chunks and check `time.monotonic()` against one deadline), the same cap on the total, not per operation.
3. F-C736-2 LOW: other read paths in `field_agent` are still unbounded: the `httpx` clients in `bootstrap.py` (:58, :59, :92, :93), `federation.py` (:154, :157), `liveness.py` (:68, :70) and `usage.py` (:109 to :154) call `resp.text` and `resp.json()`, which read the whole body into memory. They talk to the same estate services as the canary (a misbehaving service is the threat the PR cites, C-102 F-C102-3), so the cap is applied to two of the clients and not to these. The card asks "any read path still unbounded": yes, those. The inbound side is bounded (`canary.py:197`, `_drain`: `MAX_BODY_BYTES`, refused above it, a chunked request closes the connection).
4. When a reply is over the cap the two clients answer differently, both fail closed: the canary returns `(status, {"response_too_large": 65536})` (an explicit marker the probes can show), `FieldClient` returns `(status, None)` with the body dropped, so `check()` treats a 200 with no verdict as BLOCK (rule 1: "anything but a well-formed 200 verdict is BLOCK"). Not a defect; noted so nobody reads one as the other.
