## Objections first
1. THE CENTS CONVERSION IS UNPINNED FOR REAL PRICES: the limit is converted with `round(limit * 100)` and then a sub-cent check `abs(cents - scaled) > 1e-9`. The good-limit tests use 500.0, 0.01, 1234.56 and 1e10, none of which is sensitive to the choice of rounding. On the unmutated head `0.29`, `1.15` and `4.35` convert to 29, 115 and 435 cents (probed). If the `round` is replaced by `int()` those three limits are REFUSED as sub-cent (probed), and with `math.ceil` the limit `0.07` is refused (probed); no test fails in either case. Correction of an earlier note of mine: I first assumed truncation would silently mint 28 cents; the sub-cent check turns it into a refusal instead, so a wrong rounding makes valid caps unusable rather than silently mis-metered. Still a regression no test would catch. MEDIUM.
2. The CLI error line is built from pydantic's error list; the code takes field paths and messages and drops the input, which is the point (a pasted secret can sit in a manifest field). The test asserts only that the literal text `input_value` is absent; it does not look for the offending value itself. A change that prints `e["input"]` passes (mutant s). MEDIUM-LOW.
3. `exc.errors()[:5]` caps the lines; the tests only ever produce one error, so the cap is unpinned (mutant t), and a manifest with many problems prints at most five with no "and N more" hint. LOW.
4. The model already refuses NaN and negative limits when `FieldManifest` is built (the probe shows `ValidationError` before `from_manifest` runs), so the new `isfinite` guard in `core.py` is reached only by the infinity and overflow cases; for NaN and negatives the new code is defence in depth. Mutants d and p are therefore not behaviour changes through the manifest path.
