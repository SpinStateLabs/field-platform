## Objections first
1. SLOW-DRIP READS ARE UNBOUNDED IN WALL-CLOCK TIME. `urlopen(timeout=T)` is a per-socket-operation timeout. Probe (cap patched to 40 bytes, one byte every 0.4 s, timeout 1.0 s): `canary.urllib_call` returned after 16.0 s and `FieldClient.check` returned after 16.0 s, both well past the 1.0 s timeout. At the real cap of 65536 bytes with a gap just under the timeout (10 s default in FieldClient, 20 s in urllib_call) the read takes days. Worse for FieldClient: the dripped body can be a complete valid verdict, and the probe's FieldClient returned ALLOW. So a hostile or broken service can stall a governed action indefinitely, and a check that "should have timed out" eventually answers. HIGH (observed at small scale; the day-scale figure is arithmetic: 65536 x ~9.9 s). Fix: a monotonic deadline around the read loop (read in chunks, check the clock).
2. THE CANARY'S OWN SERVER HAS NO SOCKET TIMEOUT. `_drain` (canary.py:184-197) reads `Content-Length` bytes up to MAX_BODY_BYTES (64 KiB) with `rfile.read(length)`; the handler class sets no `timeout` and the server is a ThreadingHTTPServer (canary.py:251; grep shows no timeout attribute near the handler). A peer that declares 60000 bytes and sends none holds a thread forever. Memory is bounded; threads are not. I did not run this inbound case. MEDIUM (reasoned from the code, not observed).
3. OVER-CAP IS "BLOCK" IN ONE CLIENT AND A SENTINEL BODY IN THE OTHER. `FieldClient` discards the whole body (field_client.py:161-163); `urllib_call` returns `{"response_too_large": 65536}` with the real status (canary.py:366-367). Different shapes for one rule; callers of the canary must handle the extra key. Not a defect. LOW.
4. THE CAP IS APPLIED TO BYTES, NOT TO DECODED CONTENT. No Accept-Encoding is sent and urllib does not decompress, so there is no inflation path. HIGH (read; not probed with a gzip reply).
5. HEADERS: http.client bounds each header line (64 KiB) and header count (100) by itself; the PR does not touch this. Not probed. LOW.
