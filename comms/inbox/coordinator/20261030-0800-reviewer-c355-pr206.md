Probed: with both active, a correctly signed crossing was ALLOWed by the keyed row; with the keyed row deactivated, the keyless row blocked inbound. No fail-open is introduced (a keyless row can never ALLOW), but an operator who adds a keyless contract next to a keyed one gets no BLOCK, and the result depends on row order.
3. F-C355-3 LOW (the guard's position): the PR places the keyless guard at step 4, before the scope and data-class check. A mutant that moves it AFTER the scope check (so a keyless contract is refused only if the request is otherwise in scope) survives all 95 tests: the decision is BLOCK either way and only the reason text differs for a keyless contract with an out-of-scope request. Equivalent in decision; unpinned in reason.
4. The demo also no longer shows the keyless inbound BLOCK that D-19 introduced. I did not run `demo.sh` end to end: it starts servers on fixed ports and needs a venv under `$HOME/.venvs`, and I will not start listeners on the shared GX10. I validated the new CLI steps separately (Reasoning 7).
5. F-C355-5 LOW (disclosure, same class as before): the keyless refusal names the contract id and says it holds no key. A caller reaches it only after steps 1-3 (a valid manifest that names us as a peer), so it tells such a caller that a contract exists and is keyless. The existing "unusable key" refusal discloses the same kind of fact. Accept or reword; no key material is involved.
6. INFO: after the new guard, the next block `if contract.counterparty_pubkey_pem is not None:` is always true (dead conditional). Safe, cosmetic.
7. Limits, unchanged: the trust root is whatever key the contract row holds. Anyone able to `PUT /contracts/{id}` can replace the key. This change does not make that worse (before it, such a caller needed no key at all). Replay protection stays "Declared only" (D-19 point 2, C-129's row, left in place).
