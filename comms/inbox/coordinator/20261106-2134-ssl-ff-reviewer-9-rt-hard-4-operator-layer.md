FINDINGS

F1 (MEDIUM, HIGH confidence on the behaviour): kill-switch POST /heartbeat/{agent_id} has no operator guard and no bound on what it stores.
- Code: services/kill-switch/src/kill_switch/api.py `checkin` (line 782 on this head) records every id, including an unregistered one ("so a shadow agent nobody registered still surfaces"), into the heartbeat store; the store (store.py, `record`) has no row cap, no id length cap, no pruning; `/liveness` calls `_hb_store().all()` which reads every row.
- Reproduction (no secrets; in-process, a registry stub that raises AgentNotRegisteredError, a tmp sqlite path): POST /heartbeat/ghost-0 .. ghost-299 returned 200 for each, 300 rows; POST /heartbeat/<50000 x "a"> returned 200 and stored an id of length 50000; POST /heartbeat/%00x returned 200. 300 posts took 132 s on a loaded box (0.44 s each); that is a measure of this box, not a rate limit.
- Impact: any perimeter-secret holder can grow the sqlite file without bound and make every /liveness read heavier; it can also check in for a REAL agent id and mask a stale or dead agent. The second half is the documented one-trust-domain limitation (authn: "one trust domain, not identity"); the unbounded rows and ids are not documented anywhere I read.
- Suggest: cap id length to the registry's agent-id rule, refuse or cap unregistered ids (count and total), and decide whether a check-in should need the agent's own token.

F2 (MEDIUM, HIGH): agent-registry's 422 for an unresolvable manifest_ref echoes the caller's text without a bound and discloses the server's manifest directory.
- Code: services/agent-registry/src/agent_registry/api.py `unresolvable_manifest_ref` (line 125) returns {"manifest_ref": <as sent>, "manifest_dir": os.environ.get("FIELD_MANIFEST_DIR"), ...}; used by POST /agents and by the armed-mode PATCH.
- Reproduction (no secrets; FIELD_MANIFEST_DIR set to a made-up path, in-process): POST /agents with manifest_ref "nope.yaml" returned 422 whose body names the made-up directory; manifest_ref of 100000 characters returned 422 with a 100258-byte body echoing it; a key-shaped string as manifest_ref is echoed back verbatim.
- Impact: a server filesystem path to any caller that can reach the route (an operator identity under ENFORCE, a perimeter-secret holder otherwise); caller text and a key-shaped value reflected into a response and into whatever logs record bodies. The same class PR 750 and the 422 no-echo handler removed elsewhere.
- Lint gap: tools/tests/boundary_echo_allowlist.txt lists one agent-registry site (`run_discovery`) and none for this helper, so the boundary-echo lint did not flag it (I did not run the lint against a mutation; read the allowlist only). MEDIUM confidence on the lint-gap statement.
- Suggest: return only {"error", "reason"} and a fixed hint; if the path is wanted, put it in the operator log.

F3 (LOW, MEDIUM confidence: read, not run): renew_token passes the new delegation token id to the verify command on its argv.
- Code: tools/renew_token.py line 1329 `argv = [part.replace("{new_token}", new) ...]`, started with subprocess.Popen (line 1340, no shell). The command line (token UUID) is therefore visible in the host's process listing for the life of the command (--verify-timeout up to 3600 s). Output is redacted; argv is not.
- Impact: a local user on the host can read a live token id. The token id is a reference, not the operator key, and the runbook runs this as the operator, so LOW. Suggest an environment variable or stdin for the verifier.

F4 (LOW, HIGH): inconsistent cleartext control: estate_probe.py has `--allow-plaintext` (line 954, used at 1000) that lets x-field-auth and an operator key go over http to a non-loopback, non-private host; renew_token.py refuses the same case with no override (validate(), line 1580). A script that adds the flag sends the perimeter secret in clear. Suggest dropping the flag or requiring a second confirmation.

F5 (LOW, MEDIUM): operator_keygen --check prints an 8-hex key-hash prefix per row (lines 341, 379, 381, 386) while rotation_events.py states that 8 hex is grindable and uses 16 hex elsewhere (S11). Not a secret leak (a 32-bit prefix of a hash cannot recover a key) but the display length is inconsistent with the stated policy; it matters if the fingerprint is used to tell two keys apart.
