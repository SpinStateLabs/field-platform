# C-641 reviewer (Lane 4): PR 346 @fb9dc61, commit-identity guard (C-564; closes reviewer C-562 F-C562-1)

VERDICT: PASS WITH CONDITIONS on fb9dc612fbdbcfaafdc9879d990872c91ef93f9f. The guard does what it says for the accident it targets: an email address in `user.name` or `user.email` of a commit. It never printed an address in any run I made (full value and every 6-character slice absent from stdout and stderr), it fails closed on a bad range, a bad line and a missing base (exit 2), and the whole CI-equivalent set is green on the merged state. Conditions: (a) it can block a legitimate commit (a GitHub bot author, an Enterprise Managed User handle) and the name rule misses disguised spellings (F-C641-1, -2); (b) a `--range` that starts with `-` is passed to `git log` as an option and can make the tool report "clean" while git writes elsewhere (F-C641-3); (c) it is not wired into CI or a hook, so it guards nothing until someone runs it (F-C641-4); (d) pins that would catch a regression that echoes an address are missing (F-C641-5).

## OBJECTIONS FIRST
1. F-C641-1 MEDIUM-LOW (it can block a legitimate commit): the email rule is a strict allowlist (`fullmatch` of four forms), so anything else is a finding. Probed through `email_problem`: refused, and legitimate on GitHub: a bot author `41898282+github-actions[bot]@users.noreply.github.com` (the brackets), an Enterprise Managed User handle with an underscore (`12345+octo_acme@users.noreply.github.com`). Confirmed end to end in a throwaway repository: a commit with the bot author email is reported `author email is not an accepted no-reply form` (exit 1). Also refused, correctly: an upper-case domain, a trailing dot, a doubled id, a `+tag`, angle brackets, an empty value. Accepted: the four forms, and a whitespace-padded one (the value is stripped before the match; git does not store padding). A squash merge made in the GitHub web interface carries `noreply@github.com` as committer (accepted). If bot or EMU commits can land on a branch this guard runs on, allow the bracketed suffix `[bot]` and the underscore.
2. F-C641-2 MEDIUM-LOW (the NAME rule is a denylist of one shape and misses disguised and spaced forms): a name is flagged only when it holds non-space text, an `@`, then non-space text (`[^@\s]+@\S+`, `search`). Probed: flagged: a plain address, `Name <address>`, `@@`, an address with a zero-width character in the local part, `mailto:`, an upper-case address, `user@HOSTNAME` (the common machine-derived name). NOT flagged (PASS): a space before `@` (`someone @mail.example.invalid`), spaces around `@`, `@` followed by a space, a trailing or leading `@` (`someone@`, `@mail.example.invalid`), a tab or a no-break space before `@`, the fullwidth `@` (U+FF20) and the small commercial at (U+FE6B), `[at]`, `(at)`, "at ... dot ..." spellings, `%40`, an HTML entity, a literal `@`, a bare local part. Most of these are deliberate obfuscation, not an accident (the accident is `user.name` set to the address, which is caught); the cheap hardening is to also flag Unicode `@` lookalikes and a name whose first or last character is `@`. A personal name that is simply a Windows or Unix username (no `@`) cannot be detected by any such rule.
3. F-C641-3 MEDIUM-LOW (`--range` is passed to `git log` as an argument that may be an option; a "clean" can be false): `git log --format=... <range>` has no `--` and the range is not validated. `--range=--output=<path>` made git write the log to that file and the tool printed `commit identities: clean` and exited 0 (probed in a throwaway repository: the file was created, the tool reported clean). The caller supplies the range, so this is not remote, but a hook or CI step that builds the range from a variable (a base ref name) would silently pass on a value that starts with `-` and would overwrite a file. Fix: reject a range that starts with `-`, or pass `--end-of-options` before it, and treat empty output from a non-empty range as an error only if the range is expected non-empty (an empty range legitimately prints "clean", so I do not ask for that).
4. F-C641-4 MEDIUM-LOW (nothing runs it): the tool is documented as a pre-push hook and as a CI step, and the PR says it is not wired into `ci.yml` or a hook installer. `.git/hooks` is not versioned and no `core.hooksPath` is configured, so the guard protects no commit until each lane sets the hook up by hand. A decision for the coordinator (wire it into CI with `fetch-depth: 0`, or a versioned hooks directory), not a defect of the code.
5. F-C641-5 LOW-MEDIUM (pins that would not catch a regression that leaks): the malformed-line error path (`a log line does not have five fields`) currently carries no value. The mutant that adds the offending line to that message SURVIVES all 36 tests: a future edit could echo a personal address from a malformed log line into CI output and nothing would go red; the only no-echo test covers the finding message. Related: the finding message prints the first 12 characters of the "sha" column of whatever log it was given; with `--stdin` and a log in the wrong column order (an address first) the first 12 characters of an address are printed (probed: `someone.exam: ...`). Validate that the column is 40 hex characters before printing it, and add a no-echo test for the error path.
6. LOW (pins that stop short; 15 of my 44 mutants survive): the dots of the built-in forms are not pinned (a mutant with an unescaped `.` in `users.noreply.github.com`, `noreply@github.com` or `noreply@anthropic.com` survives: `noreply@githubXcom` would be accepted); an empty id (`+handle@...`, `[0-9]*`) is not pinned; the name regex without its local part or domain part (flags `@handle`, `someone@`) and with a space allowed in the local part are unpinned (and are the behaviours of objection 2); a log line with six fields (a name holding the 0x1f separator) would be accepted by a `< 4` mutant; the count in the summary line (distinct commits, not findings) is unpinned; `--allow-domain` whitespace and a blank domain are unpinned (a blank domain matches nothing useful, equivalent).
7. NOT A DEFECT, checked: no shell is used (a list argument to `subprocess.run`); a non-ASCII legitimate name (a UTF-8 "José Muñoz" committer) passes under `LC_ALL=C` (Python coerces the C locale to UTF-8); an unknown base (`origin/main` removed) is exit 2 with a generic message; a malformed `--stdin` line is exit 2; merge and GitHub web identities are accepted; the default range is the new commits only, as stated, so existing history is not judged. The tool reads author and committer only: commit-message trailers (`Co-Authored-By`, `Signed-off-by`), tags and signatures are outside it (say so in the docstring; I did not test them).
