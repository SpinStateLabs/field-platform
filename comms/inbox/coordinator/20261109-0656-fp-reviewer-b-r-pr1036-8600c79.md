## Condition C1 (HIGH, measured on the head and on main): a regression in the "never an error" contract
Both new parsers call `int()` outside the `try` that used to catch `ValueError`. Python's default limit on integer text is 4300 digits (`sys.get_int_max_str_digits()` = 4300 here, Python 3.14.2), so a value of 4301 or more digits now matches the digit regex and then raises. Measured with the environment variable set to that many nines:
| Variable | Digits | Head | Main (347b72089) |
|---|---|---|---|
| FIELD_LEDGER_RETENTION_DAYS | 4300 | returns a (huge) day count | same |
| FIELD_LEDGER_RETENTION_DAYS | 4301 and 20000 | **raises `ValueError: Exceeds the limit (4300 digits)`** | returns `(None, "...is not an integer")` |
| FIELD_REPLAY_MAX_EVENTS | 4300 | returns 5000 | same |
| FIELD_REPLAY_MAX_EVENTS | 4301 and 20000 | **raises `ValueError`** | returns 5000 |
The ENVIRONMENT.md rows and the function docstrings promise a fallback ("never an error, value not echoed" for the replay cap; a reported problem for retention). The new tests do not try a long value. Fix: put `int()` back inside the `try`, or bound the regex (for example `[0-9]{1,9}`), and add a 4301-digit test for each.
