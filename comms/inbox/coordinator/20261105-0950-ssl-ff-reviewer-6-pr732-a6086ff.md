## Objections first (FORCE-O)
1. `list_agents` is pinned for a 503 only. Mutant R13 (`!= 200` weakened to `>= 500`) survives: a 400, 401 or 403 from the registry would then be handed back as the body of an agent list (`resp.json()` of an error object). The tests give `get_agent` six statuses (400, 401, 403, 500, 502, 503) and `events` seven, but `list_agents` one. LOW test gap with a real consequence (a refused read taken for data).
2. The tests pin behaviour that looks accidental and say so: a 200 `status: null` reports `None`, not `<unknown>` ("dict.get's default applies only to an absent key"), and `events` carries no status on its exception (unlike `append`). Pinning a quirk as "documented" is honest, but it freezes it; a later fix will have to change these tests (LOW).
3. Not covered by design: the 200-with-unusable-body cases of the registry reads live in another PR's file (676), so `get_agent` and `list_agents` returning a non-dict or non-list on 200 are not asserted here (the file's docstring says so). `get_agent` still returns `resp.json()` unchecked in the code I read on main; whether PR 676 changes that I did not check.
4. Transport errors are re-raised with `str(exc)` as the message (tests match on "connection refused" and "boom"), so whatever the underlying exception text says (a URL, a proxy) is carried by `LedgerUnreachableError`; the tests pin that text through to the caller. Not this PR's change.
Steelman: these four reads gate other services (kill-switch, lifecycle, delegation), and none of the error branches of `events`, `get_agent`, `require_active_agent` or `list_agents` was pinned; now each status class, each wrong body type, the exact message texts and the query-parameter rules (sent only when truthy) are asserted.
