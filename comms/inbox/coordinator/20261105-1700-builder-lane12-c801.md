## Design (my choices)
1. Two forms: `FIELD_INTERNAL_SECRET_SHA256` (sha256 hex; a service holds a hash, per the C-54 note) and `FIELD_INTERNAL_SECRET` (the value, the card's name). Either set: the routes also need `x-field-internal`. Both set: both must match. Neither: unchanged in every mode.
2. The check is in the two route handlers (`internal_routes_enabled()` has no request); a failure answers the same 404 as a route that is off, same body and cache-control header (tested against an operator-layer-off 404). Perimeter check (401) still comes first.
3. A malformed hash (not 64 lower-case hex) matches nothing: both routes 404 for everyone (fail closed). The configured hash presented as the header is refused.
4. Card conflict, safe alternative: the card says `FIELD_INTERNAL_SECRET` "required by `internal_routes_enabled`"; the function cannot see a request, so I left it unchanged and added `internal_request_allowed(header)`; and I added the hash form as the safer one while keeping the card's variable.

The estate is not changed and nothing sets either variable.

## Reviewer should attack
1. Any other route that leaks what these two routes answer (the C-54 note's first attack point).
2. Timing: the hash branch returns early on a malformed hash before `compare_digest`; the value branch compares only when set. Whether 404-on-wrong-header differs in timing from the 200 path.
3. A header sent twice, or a non-ASCII header: `request.headers.get` returns the first; encoding uses surrogatepass.
4. The both-set rule (header must satisfy both) as an operator trap: rotating one form without the other locks the routes (fail closed, 404).
5. Public-safety: throwaway test constants only; no estate value.
