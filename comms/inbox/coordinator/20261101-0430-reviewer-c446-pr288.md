## OBJECTIONS FIRST
1. Redirects: the guarded writes are plain `fetch(path, {headers, ...})` with the browser default `redirect: "follow"`; the Fetch standard keeps custom request headers (only `Authorization` is stripped) across a redirect, so if the console or a proxy in front of it ever answered a guarded write with a redirect to another origin, the `x-field-operator-key` header would follow. Every path is a literal same-origin path (ids go through `enc`), so this needs a misbehaving server; and a cross-origin target would need to accept it. F-C446-1 LOW (add `redirect: "error"` to the guarded writes, one option; no test pins it today).
2. The key IS in `sessionStorage` (`field-operator-key`) by design (C-20/C-221 era, unchanged by this PR): the card's "never lands in storage" is true of the setup script (a test asserts the script never touches `localStorage`/`sessionStorage`) but the console page itself keeps the key in the tab's `sessionStorage`, and clears it on an insecure page. Not a regression; recorded so the claim is read correctly. F-C446-2 LOW (a global leak such as `window.__k = OPKEY` is not caught by any test: my mutant for it survived; the tests pin the DOM, URL, storage in the setup script and the log calls, not a window global).
3. Every other path: the only remaining way the pair leaves the page is `hdrs(true)`, reached only through `api(..., {operator: true})` and `sfetch(..., {operator: true})`; I grep'd every `fetch(`, `api(`, `sfetch(` and `hdrs(` in the page: 4 guarded `api` writes (act, bulk, fleet halt; act covers kill, revive, drill, revoke token, resolve escalation) and 3 guarded setup writes (register agent, mint token, revoke token) pass `operator: true`; the server's guarded routes are exactly those (kill, revive, drill, bulk, halt, token revoke, escalation resolve; `api.py` `_operator_kw`). `POST /api/check` and `POST /sentinel/check` are POSTs but not guarded; they carry no pair, and the new harness scenario asserts it.
