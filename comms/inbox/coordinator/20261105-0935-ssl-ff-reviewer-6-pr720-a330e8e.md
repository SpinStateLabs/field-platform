## Objections first (FORCE-O)
1. The two operator-facing doc rows were not updated for the new limits. In docs/ENVIRONMENT.md the "Accepted values" cell for FORCE_GATEWAY_SENTINEL_TIMEOUT still reads "float seconds > 0; non-numeric or <= 0 falls back to 30.0" (no mention of the 600 s cap or that inf/NaN fall back), and FORCE_TELEMETRY_WINDOW still reads "int clamped to >= 1" (no 10000 cap). The PR changed only the anchor numbers in those rows (api.py:274 to :283 and :244 to :248). An operator reading the doc would not learn that 700 becomes 600 or that 1,000,000 becomes 10,000. LOW (documentation).
2. Silent clamping, two different policies: a timeout above 600 is CAPPED (601 gives 600.0), but infinity, NaN and non-positive are the DEFAULT (30.0); a window above 10,000 is CAPPED, junk is the default. Neither logs. A mis-set value that is quietly replaced is a trap the other way (an operator setting 900 for a slow judge, per the comment "set FORCE_GATEWAY_SENTINEL_TIMEOUT >= 60 on a judge-on sentinel", gets 600 with no warning; 600 is above the 60 the README asks for, so no conflict today). LOW.
3. The explicit `create_app` arguments and `SentinelClient(timeout=...)` get the same check as the environment (F7, F15, F16 killed), so the two entry points cannot disagree.
Steelman: `FORCE_GATEWAY_SENTINEL_TIMEOUT=inf` was accepted, put into `/health` and made `/health` a 500 (JSON cannot encode infinity), and a huge `FORCE_TELEMETRY_WINDOW` made every `/telemetry` read an OverflowError at SQLite's LIMIT bind; both are now 200 under every bad value tested (`inf`, `1e999`, `nan`, 0, negative; windows up to 10**30).
