## Objections first (FORCE-O)
1. The docstring promises that "a structure nested past the recursion limit" is a ReleaseRecordError, and the code catches `RecursionError`, but no test sends deep nesting: mutant C6 (RecursionError not caught) survives. The behaviour is real: measured on the head under Python 3.13.18, nesting of 900, 1500 and 5000 levels still encodes and VERIFIES (the C encoder does not hit the interpreter's limit there), while 50000 and 300000 levels raise RecursionError and are refused as ReleaseRecordError. So the clause is live and correct, but unpinned (LOW). Python's limits differ by version (not tested elsewhere).
2. `except (TypeError, ValueError, OverflowError, RecursionError)` is an allow-list: C5 (OverflowError dropped), C9 (`except Exception`) and C10 (NotImplementedError also swallowed) all survive. C10 matters for the design: `refuse_all_verifier` raises NotImplementedError from `_accepts`, not from `_canonical`, so catching it there would not change the pinned test. Equivalent for these tests; the risk is a future edit that widens the net and hides a NotImplementedError from the encoder path. LOW.
3. The second call site (`_canonical(body, drop=())` for the ADR override approval) is not distinguishable: C2 (back to `canonical_payload`) survives, because `body` holds only the 40-hex sha, the override string and the approver, which the earlier checks have already constrained to strings. Probably unreachable (not proven; I did not trace the validation of `override_approval["approver"]`). Meanwhile the approval dict inside the record IS exercised through the first call (test with `extra: {1,2}` inside `override_approval`).
4. C8 (`drop` ignored inside `_canonical`) survives: the only caller that passes a non-default `drop` is the `drop=()` call in objection 3, which the tests cannot tell apart (same root cause).
5. NaN and infinity are not errors: measured, `extra=float("nan")` and `float("inf")` VERIFY (json.dumps writes `NaN` and `Infinity` by default, which are not canonical JSON). The PR title says "a record json cannot encode"; json can encode these, so they pass through into the signed bytes. Not a regression and not this PR's claim; mention only (LOW; MEDIUM if a verifier elsewhere parses the same bytes strictly).
Steelman: `verify_release` documents "return a VerifiedRelease or raise ReleaseRecordError"; an extra key holding a set, bytes, a date (what `yaml.safe_load` yields for a bare timestamp), mixed-type keys or a cycle raised TypeError or ValueError out of the verifier, so a malformed signed record crashed the caller instead of being refused. Now all six pinned shapes are one named refusal with no chained cause.
