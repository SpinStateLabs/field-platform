# C-54: design note, a second secret for the two internal operator routes (builder Lane 13). PLAN ONLY: no code, no PR, no GX10 run.

Card: C-54 (reviewer C-48 mitigations 2 and 4; D-12 in tasks/DECISIONS-FOR-DON.md:41). Read on main 5808a5c and PR 57 @30ac1e1. No secret value read or printed.

## CORRECTION to the card (first)
The card says the second secret is "held only by the rotator and the ledger observer". The ledger observer does NOT call these routes and sends no perimeter secret (services/sealed-ledger/src/sealed_ledger/operator_observer.py:66-69). The only caller is the rotator (PR 57, tools/operator_rotate.py, unmerged; its probes carry `x-field-auth` only). So there is ONE holder today, the rotator. HIGH.

## OBJECTIONS (before the proposal)
1. A second secret held by the same processes adds nothing (C-71 D-12). If `FIELD_INTERNAL_SECRET` lands in the shared `*env` anchor (docker-compose.yml:167 pattern) every container holds both, including canary-agent. The boundary is who HOLDS the secret, not how many exist.
2. The verifier must know the secret to check it. A service that checks an `x-field-internal` equal to an env value therefore holds the very value a compromised service could replay to its seven siblings.
3. "Default-off compatible" means an estate that does not set it stays exposed silently (C-71). A control nobody turns on is a decoration.
4. It does not touch the larger exposure: while the operator layer is LOG-ONLY the perimeter secret is the only control on guarded writes, and canary-agent holds it (C-48 fact 5, c). Per-agent secrets (C-48 mitigation 1) stay the bigger reduction and are not in this card.
5. The routes are reachable by anything that can reach a service port with the perimeter secret; network position (C-48 mitigation 3) is a separate control. This card does not segment anything.
Steelman for "do nothing": the oracle only confirms hashes of random 256-bit keys, and the state route shows 16-hex fingerprints; exposure is reconnaissance, not compromise (C-48 a, b). Valid, but it leaks the rotation schedule to any perimeter-secret holder, and C-71 wants the boundary closed before Stage 2.

## ASSUMPTIONS
A1. Modes are OFF / LOG-ONLY / ENFORCE (`oa.mode()`, operator_health.py:452-460). HIGH.
A2. `x-field-auth` is checked by middleware with `hmac.compare_digest` on every path but `/health` (packages/field-core/src/field_core/authn.py:19-62). HIGH.
A3. The rotator runs on a host or container that can hold a file the eight services cannot read. MEDIUM (compose layout not re-read this session; C-48 facts 1-5 are from 2026-10-28).

## PROPOSAL
1. Verify by HASH, not by value. Each service holds only `FIELD_INTERNAL_SECRET_SHA256` (a hash is not a credential; it may sit in the shared env anchor). The rotator holds the secret itself, as a file mount in the rotator container only (never an env var, never the anchor, per C-71). The routes then require `x-field-internal: <secret>` and compare `sha256(header)` to the configured hash with `hmac.compare_digest`. A compromised service or canary-agent holds the hash and cannot present the secret. This answers objections 1 and 2.
2. Where: `internal_routes_enabled()` has no request in scope (operator_health.py:452); the check moves to the two route handlers (operator_health.py:694 and :705) before the body is read, answering 404 as for an absent route (the existing fail-closed shape, `_absent()`), so a wrong or missing header is indistinguishable from "route off".
3. Mode policy (objection 3): OFF or LOG-ONLY: if the hash is unset, today's behaviour (perimeter secret only) plus a once-per-process WARNING saying the routes are secret-only. ENFORCE: if the hash is unset, the two routes answer 404 (disabled, fail closed). Decision for Don: whether ENFORCE-disables is acceptable before PR 57's rotator is deployed (without the rotator nobody uses the routes, so the cost is low).
4. Mitigation 4, count and surface (reuses a pattern already on main): each service counts calls to the two routes that fail the internal check as `operator_internal_route_denied` in its operator block of the open `/health` (a counter, like the break-glass counters; operator_health.py:48-50 allows counters, never hashes). The ledger observer already turns a changed break-glass counter into an event (operator_observer.py:405-411); the same loop emits `operator.internal_route_denied_changed`. Log `request.client.host`, class and count only, rate-limited. I did not check whether the frozen operator event set permits a new type: `admit_ledger_event` and the observer's event list must be read before building (I do not know).
5. Rotation of this secret: it is a second long-lived credential and Don's ruling is that key rotation is machine work (key-rotation-automated). Hard part, NOT in v1: services read a hash FILE holding up to two hashes (current, next, the same two-slot idea as the operator keys), and the rotator replaces it. I recommend v1 = static secret, rotated by the same rotator in a later slice; flag it so it is not forgotten.

## Tests-first plan (for the build card; mutants named)
1. Route with only `x-field-auth`: 404 in ENFORCE when the hash is set; 200 with a correct internal header. Mutant: skip the internal check.
2. Wrong header, empty header, header equal to the hash itself (not the secret): all 404. Mutant: compare to the hash directly (replay of the hash works).
3. ENFORCE with the hash unset: 404 on both routes; LOG-ONLY with it unset: 200 plus one warning. Mutant: treat unset as allow in ENFORCE.
4. Counter rises by one per denied call, not for a valid one; `/health` carries a count only, never the header or the hash. Mutants: count valid calls too; include the hash in the health block.
5. Constant-time compare: a swap of `compare_digest` for `==` is behaviourally equivalent; pin it with a source check (the C-57 lint pattern) or record it as an unkillable mutant.
6. Compose: a test that the hash may appear in the shared env anchor but the secret value appears in NO service's environment block (the compose-key lint shape of C-617).
Files a build would touch: operator_health.py (handlers, counter), operator_auth.py (counter next to `note_breakglass`), operator_observer.py (event), integration compose files (hash in the anchor, secret mount on the rotator only), tools/operator_rotate.py (PR 57: send the header), runbook. Roughly three small PRs; order: field-core handlers plus counter, then observer event, then compose and rotator.

## WHAT A REVIEWER SHOULD ATTACK
1. Is hash-verification really better than a value check, given a compromised service can still call the other seven with ONLY the perimeter secret (they then 404)? Confirm no other route leaks the same data.
2. Does 404-on-wrong-header leak route existence through timing against the 200 path?
3. The warning-only LOG-ONLY default leaves the exposure in place for the estate that matters today (LOG-ONLY). By design: does Don accept that until per-agent secrets exist?

## CONCLUSION
Build it as a hash-verified header held only by the rotator; ENFORCE fails closed; denied calls counted and surfaced through the existing observer pattern; correct the card (the observer is not a holder). It closes the reconnaissance exposure for a compromised service, not the LOG-ONLY write exposure (needs per-agent secrets, a separate card). Decision for Don: D-12 items 1 and 3 remain open; I recommend scheduling per-agent secrets rather than leaving them awaiting a ruling.
