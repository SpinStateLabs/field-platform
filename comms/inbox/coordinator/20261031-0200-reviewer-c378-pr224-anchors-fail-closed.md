OBJECTIONS FIRST
1. F-C378-1 MEDIUM-LOW (design): every anchors-file failure exits 1, the same code as a REAL tamper finding. A script that alerts on exit 1 cannot tell a typo'd `--anchors` path from "history was REWRITTEN"; only the message differs (`ANCHOR FAILURE — anchors file X does not exist: nothing can be checked` against `ANCHOR FAILURE — anchor 0: hash ... — history was REWRITTEN`). The same command already uses exit 2 for "cannot check": `no ledger at PATH` (README lines 34-36 and 86) and typer's own refusal of an unreadable `--anchors` path, which I observed exits 2 before this code runs (a mode-000 file: "Invalid value for '--anchors': Path ... is not readable", exit 2, on base and head). So after this PR a missing path exits 1 while an unreadable one exits 2. The PR and its README chose 1 for all; I think "cannot check" (missing, directory, empty, no valid record, unparseable) should be exit 2 and a real mismatch stay 1. A pass here does not prove the codes are what an operator needs. [HIGH, run]
2. F-C378-2 LOW: no test pins that the failure message carries no anchor or file content. The code prints the exception TYPE only (`JSONDecodeError`, `UnicodeDecodeError`, `OSError`), never the text or the line (checked in the probes), but my mutants that add `raw[:60]` or `{exc}` (pydantic quotes `input_value`) to the message survive every anchors test. Anchor hashes are not secrets, but the card asked for it to be held. [HIGH, run]
3. F-C378-3 LOW: the strict rule the PR chose is all-or-nothing: ONE invalid line makes the whole file a failure, valid lines before or after notwithstanding (probe: valid-then-garbage and garbage-then-valid both exit 1). That is the right rule for an integrity file, and the base crashed on those inputs anyway (traceback, exit 1); but a crash-truncated last line (`append_anchor_line` writes a line, flushes, fsyncs; a power loss mid-write leaves a partial line) now fails the whole verify with a clean message instead of a traceback; the operator has to repair the file by hand. A UTF-8 BOM (what a Windows editor adds) fails too, as it did before. Neither is a regression; neither is documented. [HIGH, run]
4. `load_anchors` (anchors.py:94-103) is unchanged and still returns `[]` for a missing file. It has no caller in the repository now (grep: only `verify_anchors` was changed to bypass it, and the tests), so nothing is open-failing today, but a future caller would get the old behaviour. LOW. [HIGH, run]
