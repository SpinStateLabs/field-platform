## OBJECTIONS FIRST
1. The new CI health step can pass while the approver is dead. It lists `docker compose --profile approver ps --format '{{.Service}} {{.Health}}'` (ci.yml, step "Container health", added after the `wait_health` step) and fails on any line that is not `... healthy`. `docker compose ps` without `-a` lists running containers only (general knowledge of compose, MEDIUM). A container that exits is therefore not a bad line: the step shows `approver` missing and passes. The approver has no proxy route, so `wait_health` does not cover it either. My emulation of the step (real step text, bash `-eo pipefail`, a fake `docker`) gave: all healthy exit 0; starting then healthy exit 0; stays starting 45 polls exit 1; unhealthy exit 1; empty health exit 1; and `ps` printing nothing exit 0. F-C331-1 MEDIUM. Fix: use `ps -a`, and assert the set of expected services (for example compare against `docker compose --profile approver config --services`), and fail when the list is empty.
2. The hardening of the six services is verified by CI only for the approver, and only inert. `witness` (profile `witness`), `canary-agent` (profile `x3`), `manifests-admin`, `keys-admin` and `attest-keys-admin` (profile `admin`) live only in `docker-compose.gb10.yml`, which compose-smoke does not use. The approver comes up inert in CI with no key file, so its write under `/data` (`claude_approver/core.py:240-243`, temp file then `os.replace`) is not exercised under the read-only root. So the claim "no service here needs a writable root" rests on reading, not on a run. I read it (reasoning 5) and it holds on paper. F-C331-2 LOW, with a scratch-project run as the close.
3. The new pins can be satisfied while a hardened service is re-escalated. The test checks `cap_drop == [ALL]`, `no-new-privileges`, `read_only` and the healthcheck port; it does not look at `cap_add` beyond what is present, `privileged`, mounts, or `tmpfs`. Mutants proved it (below). F-C331-4 LOW.
4. The pin test does not cover every pinned reference its docstring names. "every `FROM` is digest-pinned" is true and tested, but `COPY --from=caddy:2-alpine@sha256:...` (`integration/fly/Dockerfile:58`) is an image reference too: removing its digest keeps every test green. F-C331-3 LOW.
5. The constraints test asserts names only. `anthropic==2.3.0` can become `anthropic==2.9.9` or `anthropic>=2.3.0` and stay green. F-C331-5 LOW.
