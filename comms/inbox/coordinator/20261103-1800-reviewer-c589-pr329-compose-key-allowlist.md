## OBJECTIONS FIRST
1. F-C589-1 MEDIUM (C-506 closes one spelling; the same shape stays GREEN): `${K:-}<root>/x` is refused because it passes the allowlist on its default while a set K prepends anything. The identical shape with a non-empty default is accepted. Probed through `_binds_forbidden_host_path` (volume and file kinds both GREEN): `${K:-/}home/spinner/.field-local/caller-keys/x` (the default supplies the leading slash); `${K:-/home}/spinner/.field-local/caller-keys/x`; `<root>${K:-/x}` (the variable is the tail: K set to `/../../../etc` escapes the root); `<root>/${K:-x}` and `<root>/${K:-x}/y` (K set to a `../..` chain escapes); `${K:-<root>}/${J:-id}.key`. (`<root>/${K:-..}` and `${K:-<root>/a}/../../x` ARE refused: the default itself escapes.) So the rule "an unresolved variable cannot be resolved statically, refuse it" is applied only when the default alone is not an allowed path; any `${VAR:-default}` whose default is allowed passes whatever VAR is. That is a design choice the PR text states for `${FIELD_CALLER_KEYS_DIR:-<root>}` (the estate's `.env` decides) but it is not limited to that variable. The complete static rule would be: a variable expression may appear only as the whole head of a source, only for variable names on a short allowlist (the ones the compose files use), and its default must itself be a complete allowed root or relative root; any variable in the tail is refused. With that, `${K:-/}home/...`, `<root>${K:-/x}`, `<root>/${K:-x}` and the C-506 four are all refused by one rule instead of one spelling each. Even then a SET variable cannot be judged statically (`FIELD_CALLER_KEYS_DIR=/etc`): only the resolved check on the deployed model (PR 328) closes that, so 329 must not be read as the closure.
2. F-C589-2 LOW-MEDIUM ("refused anywhere in a source" is not pinned): every test source for the unstable forms starts with the variable (`${K:-}<root>/x`). The mutant that anchors the regex at the start (`^\$\{...`) SURVIVES all 703 tests, so `<root>/x${K:-}` and `<root>${K:+/x}` would be accepted by a future edit without a red test (today they are refused, probed). Pin a tail and a middle position for each of the four forms. Also surviving: the regex without lower-case names (`[A-Z_][A-Z0-9_]*`) and without digits in names: a lower-case or digit variable (`${k:-}`, `${K1:-}`) is refused today only through that regex and no test uses one.
3. LOW (readings of "allowed" that Compose may not share; I did not run Compose): `build.context: github.com/x/y` is GREEN (kind build-context: no scheme, no colon, so it is read as a relative path inside the repository). From training data (MEDIUM-LOW confidence, not verified, no docker run) Docker and Compose read a context beginning `github.com/` as a remote git repository, so this would pull code from outside; refuse a context whose first segment contains a dot and is not `.` or `..`, or one that starts `github.com/`. `docker-image://` as an additional context is accepted by design.
4. LOW (top-level volume definitions: only `device` is read): `volumes: {v: {driver: local-persist, driver_opts: {mountpoint: /etc}}}` is GREEN (another driver names its path in another option), as is `external: true` (a volume made outside the file, which a static check cannot see) and a `device` that looks like a volume name (`device: etc`). Real files use only the local driver; restrict `driver` to absent or `local` and `driver_opts` keys to `type`, `o`, `device`. A service that is `null` (`services: {s: null}`) raises a `TypeError` instead of a finding (red, but unhelpful).
5. LOW (a pin that does not bite, one redundant block): the `~` refusal (`startswith("~")`) survives its mutant because only the volume kind is pinned, and for kind `file` a source `~/x` is read as a relative path (whether Compose expands `~` for `env_file` or `secrets.file` I do not know). In `NAMESPACE_OPTIONS`, the entries for `ipc` (`container:`), `userns_mode` (`host`) and `cgroup` (`host`) survive their mutants because the older `check_compose` lines (`ipc: container:`, `!= "host"`) already refuse the same values: a redundant block, not a hole.

Both PRs are one commit on main b929f12 and both edit `tools/tests/test_compose_static_pins.py`; they conflict in ONE hunk of six lines (lines 293 to 300): 329 turns `ALLOWED_ABSOLUTE_ROOTS = (...)` into `CALLER_KEYS_ROOT` plus `ALLOWED_ABSOLUTE_ROOTS = (CALLER_KEYS_ROOT,)`; 328 deletes the same line because it moves it, with every host-path list, into `tools/compose_bind_rules.py` and imports it. The danger is the resolution, not the size: if the conflict is resolved by keeping 329's side, the test module defines its own `ALLOWED_ABSOLUTE_ROOTS` after importing the shared one, and the deploy gate (328, which reads the shared module) and the static pins (329) then hold two definitions that can drift, which is exactly what 328 exists to prevent; no test compares them. Recommended order: 328 first (it only moves code, and 329 is a test-file edit), then 329 rebased so that `CALLER_KEYS_ROOT` and `ALLOWED_ABSOLUTE_ROOTS` are defined once in `compose_bind_rules.py` and imported by the test module, with its `CALLER_KEYS_ROOT` test reading the shared name. If 329 merges first instead, 328 must carry `CALLER_KEYS_ROOT` into the shared module in the same edit. Either way run the whole tools suite after the second merge.
