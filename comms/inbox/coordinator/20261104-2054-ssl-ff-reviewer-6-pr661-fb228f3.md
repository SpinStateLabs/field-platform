## Objections first (FORCE-O)
1. The 200-character cap applies BEFORE the strip. Pydantic v2 checks `min_length`/`max_length` first and runs the `after` validator second, so " " + "a"*200 (201 chars) and "a"*200 + "  " (202 chars) are refused with 422 although the stripped name is exactly 200 (measured with ResolveRequest directly: 201 REFUSED, 202 REFUSED, 200 accepted). The test docstring says the stripped value is what counts ("stripped, never blank, at most 200"); the code bounds the raw string. Harmless in practice, but the tests do not pin which of the two is meant: mutant N9 (validator in `before` mode, so the bound applies to the stripped value) passes the PR's file and the whole spend-governor suite (306 passed). LOW; a decision for the builder, not a defect.
2. `extra="forbid"` on ResolveRequest is untested (N11 survives, also the whole suite). Pre-existing, outside this diff.
3. First-resolver-wins identity is now compared on the stripped value, so " alice" and "alice" are the same human; two humans whose recorded names differ only in surrounding whitespace can no longer be told apart. That is the stated intent (LOW to note: any existing stored padded name is not migrated; not checked here).
Steelman: before the change "   " passed `min_length=1` and became the recorded human of record and the ledger note's `resolved_by`, which makes a blank approver legitimate; now a blank body is a 422, padding is normalised and the CLI shows one error line.
