## Objections first (FORCE-O)
1. Exit 1 now means three different things: BLOCK, "sentinel unreachable / unreadable / unknown decision" and a non-200 status. A caller (script, CI step) that treats exit 1 as "blocked by policy" cannot tell an outage from a verdict; the stderr line is the only difference. That is the intended fail-closed shape (an outage must not allow), but it is not distinguishable by exit code (design; LOW).
2. The non-200 branch is unchanged and still prints the response body: `error {status}: {resp.text}` (read from the head, not run). A proxy or server page of any size reaches stderr there, while the new 200-with-bad-body branch is careful not to echo it. The PR's test only asserts "error 503". Pre-existing, outside the diff (LOW).
3. For an unknown decision, up to 40 characters of the server's own string are printed (`repr`, so control characters are escaped; tested with ESC). Bounded and escaped, but still server text on a security CLI's stderr (LOW).
4. `_HTTP_ERRORS = (httpx.HTTPError, httpx.InvalidURL)`: any other exception (for example a non-httpx error from the URL builder) still raises a traceback; Python's uncaught-exception exit status is also 1, so the gate still fails closed, only noisily (not tested; reasoned).
Steelman: before the change `verdict["decision"]` on a body without that key raised KeyError, a transport error raised a traceback, and, most importantly, any decision string other than the exact words BLOCK and ESCALATE fell through to exit 0, so `"allow"`, `"banana"`, a missing key in a JSON object that had one, or a decision of an unknown future type all passed. Now only the exact string ALLOW exits 0; BLOCK exits 1, ESCALATE exits 2, everything else is a named one-line refusal.
