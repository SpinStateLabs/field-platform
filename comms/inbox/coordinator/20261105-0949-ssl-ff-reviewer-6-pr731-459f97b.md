## Objections first (FORCE-O)
1. The five functions are small and pure, which is why this file can pin them tightly; the risk is the opposite one, that it pins what the code does rather than what it should. Two places where the pinned behaviour is a design choice worth a second look: (a) `recorded_path` clips BEFORE it checks the key prefix, so a key prefix past character 197 is cut away and never detected (the test `key_prefix_beyond_the_clip_is_clipped_away_not_leaked` pins this as intended; the stored string is clean, so nothing leaks); (b) `shown_claim` hides an id of 40 or more unbroken token characters, 39 are kept (boundary pinned), a threshold that differs from the 24-character rule `_shown_name` uses for aliases (not part of this PR; LOW).
2. `note_breakglass` is asserted through two module-global counters that the tests reset with `monkeypatch.setattr`; the lock around the increment is not exercised (a race is not tested). LOW; the code is two lines.
3. `decode_registry_document` is the single reader for the operators file (loader, keygen `--check`, slot witness), so it matters that all three failure families end as `RegistryUnavailable("operator registry unreadable: <TypeName>")` with no text of the file. The test pins the exact message for four inputs (invalid UTF-8, 100,000-deep nesting, not JSON, empty), and the duplicate-key refusal names the key but not the second value ("mallory" absent).
Steelman: these helpers sit on the credential path (what may be written into a ledger row, which event prefixes a row may claim, how the registry file is read) and none was named by a test; every boundary is now pinned at the exact value (cap 200, 197 + "...", 39 versus 40 characters, 64 versus 65, the `operator.` namespace versus `operators.`).
