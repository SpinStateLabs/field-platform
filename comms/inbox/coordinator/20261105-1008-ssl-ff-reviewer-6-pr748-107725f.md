## Objections first (FORCE-O)
1. Policy differs from the sibling PRs: here a value ABOVE the ceiling falls back to the DEFAULT (3601 for the poll gives 2.0; 601 for the halt wait gives 20.0), while PR 720 (force-gateway timeout and telemetry window) and PR 721 (telemetry retain) CLAMP an over-ceiling value to the ceiling. An operator who sets a 2-hour poll (7200) gets a 2-second poll, which is faster than asked, against the org rate limit the floor comment worries about (600 RPM). The README and ENVIRONMENT.md rows say so explicitly ("over 3600 falls back to 2.0"), so it is documented; the inconsistency across services is the point (LOW to MEDIUM; the clamp-or-default choice is Don's).
2. Unlike PRs 720 and 721, this PR DID update the accepted-values cells in docs/ENVIRONMENT.md and the README (finite float 0..600; finite up to 3600, floored at 0.5; the fallback rule). `python tools/environment_anchors.py --check` on the head: 0 wrong anchor row(s) (HIGH).
3. The reason is real and the test reproduces it: `threading.Event().wait(float("inf"))` raises OverflowError (asserted in `test_the_overflow_the_guard_exists_for`), which would kill the poller thread; non-finite values and values past the ceiling can no longer reach it. 1e308 is below `inf` but far past the ceiling, so it too is the default (tested).
4. The two environment variables share one helper with different ceilings; mutant M15 (the poll uses the halt ceiling) is KILLED by the 601 and 3601 cases, so the wiring of each ceiling is pinned.
Steelman: a mis-set `CLAUDE_APPROVER_POLL_SECONDS=inf` (or `1e999`) previously went straight into `Event.wait`, killed the poller thread with an OverflowError and silently stopped approving sessions; now it is the default, and the stated ceiling bounds the slowest legitimate poll (one an hour) and the longest halt wait (ten minutes).
