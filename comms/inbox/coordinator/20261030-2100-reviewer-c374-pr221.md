## OBJECTIONS FIRST
1. Fail-closed on a governance component can turn a typo into an outage. A deploy whose `.env` carries a value that silently meant "log-only" yesterday now crashes at start; under `restart: unless-stopped` that is a restart loop with a traceback, and everything that calls the sentinel fails closed (the gateway in enforce mode answers 503). This is the intent (D-23), but nobody should roll it before the estate `.env` value is checked. I cannot see any estate `.env`; I can only vouch for the repository (Reasoning 4). F-C374-3 LOW (a deploy precondition for the coordinator).
2. The refusal message echoes the value. `FIELD_SENTINEL_MODE={raw[:40]!r}`: up to 40 characters of whatever was set, lower-cased. If an operator points the variable at a secret by mistake (`FIELD_SENTINEL_MODE=$SOME_KEY`), the first 40 characters of it land in the traceback and the service log. My probe with a 45-character secret-shaped value shows the first 40 lowercased in the output. The card asked for a message that names the variable and the accepted values "but not a secret"; the message is correct for any sane typo and wrong for this one. F-C374-1 LOW.
3. The validation only runs when the app builds its own engine. `create_app(engine=...)` (used by tests) skips `resolve_mode`, as before. By design; noted.
4. The doc `docs/runbooks/token-renewal.md:1146` still says the sentinel "defaults to [log_only] when `FIELD_SENTINEL_MODE` is not `enforce`", which is now untrue for a typo. F-C374-2 LOW.
