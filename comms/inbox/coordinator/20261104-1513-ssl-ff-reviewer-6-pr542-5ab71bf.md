## Objections first
1. Main is covered by the same rule (MEDIUM). The workflow triggers on `push` to `main` and on `pull_request` (ci.yml lines 7-10). The group `${{ github.workflow }}-${{ github.ref }}` is `ci-refs/heads/main` for every push to main, so a second fast-forward of main while the first main run is in progress cancels that run. The main run of the earlier commit then ends "cancelled", not green or red; the merge evidence in STATUS is taken from the PR or batch head before the fast-forward, so it is unaffected, but a post-merge failure on an intermediate main commit would never be reported. The usual form that keeps queued runs on main is `cancel-in-progress: ${{ github.ref != 'refs/heads/main' }}`; whether the coordinator wants every main commit tested is a decision, not a bug.
2. For `pull_request` the ref is `refs/pull/<n>/merge`, so the group is per PR (general knowledge): every push to a PR branch cancels that PR's previous run. Reviewers and the coordinator already re-read heads that move; a run cancelled mid-way by a builder's push needs a re-run, and "CI SUCCESS 7/7 on the exact head" must be read from the run of the final head.
3. No other workflow files exist (`git ls-tree` lists only ci.yml), so no cross-workflow cancel and no `workflow_dispatch` or `schedule` trigger shares the group.
