## Conditions
### C1 (MEDIUM, confirmed by running): a record whose every line is the single word "ok" passes 24/24, exit 0
Probe (gg_probe.py in my scratchpad): `Step 1: ok` ... `Step 12: ok`, `CI: ok`, `Record G16..G27: ok`, `Armed: a | disarm: ok`, `Forward-only: ok`, `Not-live: ok`, `Don inputs: ok` under `## PHASE G GATE <sha>` gives `24/24 checks passed` and exit 0. The script says it "never judges whether that line is true", and the PR body says the same, so this is the stated design. The risk is the word "gate" on a script that prints PASS: Step 4 does not have to contain the SHA, CI does not have to name who confirmed, no Record line has to name where the record is. Minimum structure I would require so a PASS means something: Step 4 and the CI line must contain the first 8 hex of `--sha`; the CI line must contain "confirmed by" followed by a name; each `Record Gnn` value must contain a path or an `@ <sha>` reference; reject one-word values.
### C2 (LOW-MEDIUM, confirmed): the section selection can pick the wrong section
- The heading test is `sha in heading_text`, so `## PHASE G GATE (superseded; the real one is for <sha>)` is taken as the record for that SHA (probe C: 24/24).
- Two sections for the same SHA: the FIRST wins and the second is never read. A good section above a stale one passes 24/24 (probe E); the reverse fails 1/24 (probe D). A duplicate section should be its own FAIL.
- Lines inside a fenced code block count as record lines (probe F): a filled example quoted under the heading passes.
Fix: exactly one section per SHA (fail on two); the SHA must be the heading's whole argument (`^## PHASE G GATE <sha>\s*$`); ignore fenced blocks.
