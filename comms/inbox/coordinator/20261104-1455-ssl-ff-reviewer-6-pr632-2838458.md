## Objections first
1. Regression (MEDIUM, measured). `Governor.__init__` builds its client with `headers=auth_headers()` (governed.py:75 on this head), so the perimeter secret and operator headers are read ONCE, when the client is built. Before this PR a new Governor, and so a new `auth_headers()` read, happened on every call; now it happens on the first call of each decorated function and never again. I ran the same script on main and on this head: it sets `FIELD_SHARED_SECRET=first-secret-value`, calls a `@governed` function, changes the variable to `rotated-secret-value`, calls it again, and records the `x-field-auth` header each request carried. Main: `['first-secret-value', 'rotated-secret-value']`. This head: `['first-secret-value', 'first-secret-value']`. After a perimeter-secret rotation, a long-lived process using `@governed` keeps sending the old secret until restart, the sentinel refuses it, and `Governor.check` fails closed (`ActionBlocked`, clause `E.kill_switch`) for every governed action. The repository states the opposite rule elsewhere (lifecycle-manager `killswitch_client` docstring: "Its auth headers are read on every request (R3), never captured here"; field-core C-4 `_request_auth`). The PR's docstring says only the token stays late-bound. Survivor V6 shows no test pins auth headers at all.
2. The thread-safety the PR adds (double-checked lock around the first build) is untested (L5, L6): a race could still build two clients; the cost is one extra pool, not a wrong decision.
3. `Governor.close()` also closes a client that was passed in ("the Governor is its user"): a caller sharing one client between Governors would find it closed under them. Stated in the docstring; not a bug, a contract to note.
4. The PR is 0 commits behind main b963407a; 1 ahead.
