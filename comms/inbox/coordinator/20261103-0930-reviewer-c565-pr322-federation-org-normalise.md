## OBJECTIONS FIRST
1. F-C565-1 MEDIUM-LOW (the transaction is not pinned where it is the only protection): on a database without the index (the legacy-duplicate case the PR creates on purpose), `BEGIN IMMEDIATE` is the only thing that stops two processes both passing the check. Probe, 40 rounds of 6 spawned processes registering variants of one new org on a legacy database holding two active rows for another: real code, 40 winners in 40 rounds and 0 rounds with two active rows; the same code with the `BEGIN IMMEDIATE` line removed: 39 of 40 rounds with two or more active rows (146 successes, 94 conflicts). The PR's suite does not see it: the mutant that drops the line SURVIVES all 130 tests, because the one two-store test runs on a clean database where the unique index catches the second writer. Pin it with the legacy-duplicate database and two processes, or two connections with a barrier between check and insert.
2. F-C565-2 MEDIUM-LOW (a deactivated contract is not tested as a blocker): `for_org` filters `active=1` and the engine has no other `.active` check (engine.py:537 to 543 only tests `is None`; nothing else reads `contract.active`). The mutant that drops the filter (an inactive contract answers `for_org`) SURVIVES the whole federation-broker suite. A deactivated contract would then authorise a crossing. The behaviour today is right (the query has `active=1`); no test asserts that an inactive row is not returned, nor that a crossing under a deactivated contract is BLOCK. The old query had the same untested filter, so this is carried, not new, but the PR rewrote the query and added tests around it.
3. F-C565-3 MEDIUM-LOW (re-registering an id: scopes and the org key are not pinned): the upsert lists every column. Mutants that omit `allowed_scopes` and that omit `org_key` from the `DO UPDATE` SURVIVE. The first means a re-registration that narrows the scopes would silently keep the old, wider scopes (security relevant; correct today). The second leaves a stale key: `Acme` re-registered under the same id as `Beta` keeps key `acme`, so a new `Acme` contract would get a 409 from the index although no active `Acme` exists. (`active`, `pubkey` and `contract_ref` omissions ARE killed.) Pin: re-register the same id with narrower scopes and a different org, then read both back.
4. F-C565-4 LOW (index creation is not pinned for the normal rotated database): the mutant that counts INACTIVE rows in the duplicate check (`GROUP BY org_key HAVING count(*) > 1` without `active=1`) SURVIVES. The documented procedure is "deactivate the old contract, register a new id", which leaves an inactive and an active row for one org; that mutant would skip the index on every such database, silently. Pin: an old database with one inactive and one active row of one org gets the index.
5. F-C565-5 MEDIUM-LOW (the normaliser does not merge invisible characters): probed against `Acme Corp`: zero-width space U+200B, soft hyphen U+00AD, left-to-right mark U+200E, byte-order mark U+FEFF, Mongolian vowel separator U+180E, a trailing dot, the Turkish dotted capital İ, and the Cyrillic letters in `Аcme` / `Acmе` all stay DIFFERENT. Those are format characters (category Cf) or confusables, not NFKC. Which matter: inbound, a request naming `Acme<ZWSP>Corp` simply matches no contract and is BLOCKed (fail closed: no harm). At registration an operator can still create a second active contract for a name that looks identical (invisible character), which is the bug class this PR is about; `for_org` then resolves to the lowest id as text. The operator is authenticated, so this is a mistake or insider case, not a remote one. Cheap fix: drop characters of Unicode category Cf (and the dot) before comparing; Cyrillic and other confusables cannot be fixed by normalisation and should be stated as a limit in the README. Merged and fine: case, NBSP, ideographic space, tab, newline, line separator, thin space, fullwidth letters, ligatures (ffi), `ß` and `SS`, final sigma, composed against decomposed é, superscript digits (`Acme²` equals `Acme2`: a false merge, fail-safe for registration, and not a realistic org name), Kelvin sign.
6. LOW (smaller): (a) `_lists_org` normalises the needle in the code, but the mutant that goes back to `org.lower()` for the needle SURVIVES (the test normalises only the peer side); (b) on a legacy-duplicate database `for_org` logs a warning on every call, so every inbound crossing for that org writes one; (c) any `sqlite3.IntegrityError` is reported as "another writer registered one first", which is wrong for a NOT NULL or primary-key error (none reachable: the id is the upsert key); (d) a name that is only whitespace saves (key empty, `for_org("")` returns None) and so registers a contract nothing can ever resolve, one per database because of the index; harmless and the PR pins the read side; (e) a row written by an OLD process after migration has `org_key` NULL and the index ignores NULL: during a rolling deploy an old and a new process can race (the new process's check still sees the row by its Python comparison, the old one's does not look at it).
7. EQUIVALENT survivors: the second NFKC pass after casefold (the result is already normal for every input I tried; it matters only for characters whose case fold is not NFKC-stable), and the backfill rewriting every `org_key` instead of only NULL ones.
