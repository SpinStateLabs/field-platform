OBJECTIONS FIRST
1. F-C446-1 LOW (PROVEN): `credentials: "same-origin"` in the setup area's `sfetch` (static/console.html:1464) is not pinned: a mutant that changes it to `"include"` survives the setup and identity tests. The pair-carrying requests of the setup area go to same-origin paths only, so today nothing is sent cross-origin; the option is the guard that keeps cookies off a cross-origin request, and no test says so. [HIGH, run]
2. F-C446-2 LOW (read; not new in this PR): none of the console's `fetch` calls sets `redirect`, so the default `follow` applies, including for the guarded writes that carry the pair. Browsers drop only `Authorization` on a cross-origin redirect; custom headers such as the operator pair are kept, subject to the CORS preflight the target would have to allow. A same-origin server that redirects a guarded write to another origin is therefore the one path on which the pair could leave the origin. The server in this repository answers JSON and does not redirect these routes (I read api.py's routes: no redirect response); the card's "a redirect must never carry the pair" is met at the design level (the only sender is `hdrs(true)`, and the server does not redirect) but not pinned by a test or by `redirect: "error"`. [MEDIUM, read]
3. The mutant "operator flag left in fetch options" (the `operator: true` property passed through to `fetch`) survives: equivalent, because `fetch` ignores unknown init properties. [HIGH]
4. Several tests exercise the console through a node harness with a fake `fetch` and a made-up key; a pass proves the headers the console builds, not what a real browser sends. [HIGH]
