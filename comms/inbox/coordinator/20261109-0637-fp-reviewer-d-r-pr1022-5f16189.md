## Objections first (FORCE)
1. New behaviour not in the PR text: `field_core.http.client()` also applies `FIELD_EGRESS_PROXY` (packages/field-core/src/field_core/http.py:118-120), so the five SDK default clients now route through that proxy when it is set, and a malformed value now raises at construction. Measured on this head vs main with `FIELD_EGRESS_PROXY="not a url"`: `UsageClient()` and `FieldAgent('a')` raise `ValueError: FIELD_EGRESS_PROXY must be an http or https URL with a host` (value not echoed); on main `UsageClient()` builds. Fail-closed and in the same family as the PR's goal, but no test pins it and no doc says an SDK embedder's constructor can now raise (MEDIUM).
2. Certificate environment: with `trust_env=False` the clients stop reading `SSL_CERT_FILE` / `SSL_CERT_DIR` (http.py:9, the module's own doc). An SDK user who reached an https estate through a private CA via those variables must now pass a client (a caller-built `ssl.SSLContext`) of their own; the PR does not mention it (MEDIUM, not exercised: I did not test against a private-CA https server).
3. The test pins the 302 itself, not each client's typed failure (a stated deviation from the card); it also never exercises `FieldAgent(..., sentinel_client=...)` (mutant W13).
4. Sequencing: the PR body lists conflicts with 927 (1) and 902/904 (3 each, stacked on #372). My `git merge-tree` of this head against current main is clean; I did not test it against those PRs (not in source for me).
