## Objections first
1. The new sealed-ledger sentence is wrong under Don's five-minute soak rule: services/sealed-ledger/README.md:445 now says the witness interval of 3600 is "already shorter than a soak, so the witness needs no override". True only for a 25 h soak. A five-minute soak is shorter than 3600 s, so the witness's scheduler-written timestamp cannot exceed start + interval inside it (the first tick is at start; the next an hour later). The tasks/todo.md row (:674) lists witness with lifecycle and crosswalk under "timestamp > start + interval" and gives only lifecycle and crosswalk an override. For a short soak the witness check is unreachable as written (HIGH, read; the witness default 3600 is at docker-compose.gb10.yml:459 and README text).
2. Can the override weaken a production safety interval? Yes, by mistake; nothing in code prevents it. Both variables are read as plain integers with no floor and no ceiling: lifecycle in lifecycle_manager/api.py:371-378 (`create_app`: a non-numeric value from the environment silently becomes 0 = scheduler OFF; the CLI path rejects non-integers through typer) and crosswalk in cli.py:351 and api.py:72-75 (negative becomes 0 = OFF, with a warning). So (a) a value larger than the default weakens the sweep or the source-watch cadence; (b) a typo in the environment path turns the lifecycle scheduler off without a word; (c) the text "for the run only" is a convention: the compose and Fly files read the variable from the operator's environment with a default of 86400 (docker-compose.yml:128 and 132, docker-compose.gb10.yml:414-415, integration/fly/entrypoint.sh:64-65), so an override left in an estate `.env` persists past the soak (HIGH, read). The doc should say to remove the override after the run and to confirm the default is back.
3. The crosswalk tick is not a harmless timer: each scheduled tick runs a full `regwatch check`, a live HTTPS fetch of every cited source (compliance_crosswalk/cli.py:351-355 help text; regwatch.py scheduled_check at :688-701). A short override such as 60 s means every cited third-party page is fetched every minute for the run, with no rate floor, and a changed page flags a framework stale (a state that "only a named CLI re-review clears", api.py description). A soak override of the crosswalk interval has an outward-facing and state-changing effect the new README sentence does not mention (HIGH, read).
4. Evidence strength: a run with a 60 s interval proves that the scheduler fires, not that a 86400 s cadence holds; both services' own CLI help says so ("it proves the interval fires, not that a cadence held"). The new text does not repeat that limit, so a reader could take a short soak as evidence of the production cadence (HIGH, read).
5. The soak-length rule itself: lines todo.md:477 and :624 still read "≥ 1 h soak with C0 every 15 minutes" (PR 290 / batch BZ carry the five-minute change and their own open note about C0 cadence); this PR leaves them, so the todo file after merge says both "≥ 25 h" (:674, :512, :601) and "≥ 1 h" (HIGH, grep). Not this PR's fault, but "Don's rule that soak periods are five minutes" is not met by any of its wording; the 24 h soaks stay by Don's own exception.
