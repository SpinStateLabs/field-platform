# C-783 reviewer (Lane 4): PR 369 @f685e08, field-core authn: per-tier perimeter keys, a read key never authorises a write (C-772; Don ruling D5)

VERDICT: PASS WITH CONDITIONS on f685e08900a26ee872645055694887ae72b6d6a7. The control the PR claims holds everywhere I could test it: with `FIELD_READ_KEY` set, a write attempted with the read key is refused 401 on every non-safe route of all 14 service apps (probed route by route), a request with no key is refused on every route except `/health` and the console page, the install refuses a read key equal to the full key with a fixed message that holds no key, and the whole CI-equivalent set is green on the merged state. It is infrastructure only: no service passes `service=` or `write_only_paths`, and no client uses the read key, so nothing changes in any deployment until `FIELD_READ_KEY` is set. Conditions: (a) `write_only_paths` is matched on `request.url.path` and fails OPEN behind a `root_path` prefix (F-C783-1); (b) it can only list exact paths, so a future state-changing GET with a path parameter cannot be protected (F-C783-2); (c) one generic read key opens every service's reads, with no per-service default (F-C783-3); (d) seven pins are missing, including that the install error carries no key (F-C783-4).

## OBJECTIONS FIRST
1. F-C783-1 MEDIUM-LOW (the write-only list is bypassed behind a path prefix): the middleware tests `request.url.path not in write_only`. When a server presents `scope["path"]` WITH the `root_path` prefix (uvicorn `--root-path`, a proxy that does not strip), `request.url.path` is `/api/w` while the router, which strips the prefix, serves route `/w`. Probed on Starlette 1.10 and FastAPI 0.162: a state-changing GET `/w` listed in `write_only_paths={"/w"}`: with scope path `/w` and `root_path=/api` the read key is refused (401); with scope path `/api/w` and `root_path=/api` (the form a prefix-keeping server sends) the read key is ACCEPTED and the handler runs. (The same prefix makes `/api/health` not an open path, which fails closed.) No compose file, Dockerfile or script in the repository sets a root path, so this is conditional on a deployment choice; but the failure direction is the unsafe one. Fix: compare `get_route_path(request.scope)` (Starlette's helper that strips the root path) or strip `request.scope["root_path"]` before the membership tests, and pin both scope shapes.
2. F-C783-2 LOW-MEDIUM (exact strings only): `write_only_paths` is a set of exact paths. A route with a path parameter cannot be written down (`{"/items/{i}"}` matches nothing: probed, a read key reached `GET /items/a`), and a trailing-slash spelling is a different string (`/w/` is not `/w`: the read key passes the middleware and the router redirects 307 to `/w`, where it is then refused; no data, but the guard is not the router). Twelve GET routes already have path parameters (registry `/agents/{agent_id}`, delegation `/tokens/{token_id}`, kill-switch `/heartbeat/{agent_id}`, six spend-governor reads, two ops-console reads, force-gateway `/presets/{name}`), so the first state-changing GET of that shape cannot be protected by this API. I found none today: an AST scan of all 51 GET, HEAD and OPTIONS routes for writing calls flagged only `/liveness` (reads a list, no write: I read the handler), `/telemetry`, `/contracts` and ops-console `/api/platform` (all reads). Add prefix or pattern entries (`{}` as one segment, `/*` suffix) and the same normalisation as objection 1.
3. F-C783-3 LOW-MEDIUM (one generic key, no default scoping): all 14 services call `install_authn(app)` with defaults, so a generic `FIELD_READ_KEY` set in a shared environment file opens EVERY service's reads at once: the whole ledger chain (`GET /events`), the token records (`GET /tokens`, `/tokens/{id}`: ids that the gateway's identity check accepts, though its write path needs the full key), the registry, spend and cap data, the board pack and the console's API. The per-service variable (`FIELD_READ_KEY_<SERVICE>`, which replaces the generic one for that service) exists but nothing passes `service=` so nothing can use it yet. Whether token records and the chain belong in the read tier is a decision for Don (D5 says reads and writes are separated; it does not say which reads); adoption should pass `service=` in each `install_authn` call so a per-service key is possible, and each service should state its write-only GETs.
4. F-C783-4 MEDIUM-LOW (pins; 7 of my 41 mutants survive as real gaps, 4 more are equivalent): (a) the install message never holds a key is a docstring claim only: the mutant that puts the read key into the `TierKeyError` text SURVIVES all 1150 field-core tests; (b) the constant-time comparison is not pinned: `==` instead of `hmac.compare_digest` for the read key, for the full key and in `_same` all SURVIVE (no behavioural test can see timing; a spy on `compare_digest` can); (c) `OPTIONS` as a safe method is not pinned (dropping it survives), and an unlisted method such as `TRACE` is not pinned as refused (adding it survives); (d) a blank service-specific variable (`FIELD_READ_KEY_KILL_SWITCH=`) falls back to the generic key and nothing pins whether blank should disable the tier for that service (the ENVIRONMENT.md row says "unset or blank = no read tier"). Equivalent survivors: dropping `.upper()` (servers send upper-case methods; lower-case `get` passes the middleware and gets a 405 from the router), dropping `surrogatepass` (a latin-1 decoded header holds no surrogate), the runtime "read key equals full key" reset (an equal key adds no power), and `FIELD_READ_KEY=""` counting as a key (falsy either way).
5. LOW (what to expect on migration, both asked by the card): a deployment with only `FIELD_SHARED_SECRET` is unchanged (the read key is none, auth and clients behave as before; `auth_headers()` still sends the full key and the operator pair); a deployment with neither key is unchanged (open demo mode, probed: a POST without a key succeeds); a deployment that sets ONLY a read key now enforces authn (previously open): every GET and HEAD needs the read key, every non-safe request is refused 401, so it is a read-only service and not the demo mode ("fails closed", as the docstring says). A read key set equal to the full key refuses to start (`TierKeyError`, at app creation, fixed text); making them equal later in the same process leaves the full key working and the equal "read" key adds nothing.
6. LOW (outside this PR, noted because the card asks about writes): the middleware is `@app.middleware("http")`, which does not run for WebSocket connections; none of the 14 apps registers a WebSocket route or a mount (checked), so nothing is open today. SSE (`/api/stream` in ops-console) is a GET and is a read.
