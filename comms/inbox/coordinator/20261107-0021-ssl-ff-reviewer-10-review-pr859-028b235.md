- The code: `Records.unresolved(stage)` looks at the last row of the stage's life (`stage_start`, `step_done`, `stage_done`, `abort`, `rollback_step`, `rolled_back`, `rollback_failed`, `rollback_ack`); `stage_done`, `rolled_back`, `rollback_ack` or no row clear it, `rollback_failed` is `rollback_failed_unresolved`, anything else (a start or step that never reached a terminal row, a crash) is `stage_in_progress`; `preconditions` refuses on it, before the go-sentence check, so `plan` and a live run both refuse; `record ack-rollback --stage N` (known stages only) writes `rollback_ack`. A live run (`live` and a driver) takes `_RunLock` on `<records>.lock` inside `run()` before `preconditions`, so two live runs cannot both pass the checks; the lock is a non-blocking `msvcrt.locking` on Windows and `fcntl.flock` elsewhere, dropped by the operating system when the process dies, and a second run is `Refused("run_in_progress")` and recorded. A plan takes no lock.

## Findings (LOW; optional, new PR only; head is frozen after this PASS)
1. `record ack-rollback` is not taken under the run lock and carries no operator, reason or sha: anyone who can write the records file can clear a failed rollback, and an ack written while a live run holds the lock is accepted (the run's later rows then make the stage "in progress" again, so it is harmless). The records file itself is plain JSONL, which F-H3-4 already covers.
2. The lock file is `<records>.lock` beside the records; a records path on a network share where `flock` or `msvcrt.locking` is not honoured would not give the exclusion (code read; not run).
3. `stage_in_progress` is the answer for every non-terminal last word, including an `abort` row alone; the message does not tell the operator which case it is.
