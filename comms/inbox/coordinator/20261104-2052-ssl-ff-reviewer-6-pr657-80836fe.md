## Objections first (FORCE-O)
1. The bound is applied in three places (API model `le=`, CLI check, store check). A fourth caller that reaches the store directly is still guarded by the store check; a caller that reaches `archive_closed_segments` with an oversize `days` now gets a ValueError, which the API route does not catch, so a future route that skips the pydantic model would turn it into a 500. Today the model rejects first (422), so this is latent (LOW, not tested end to end).
2. 36500 days (about 100 years) is a policy number, not a technical limit (timedelta allows 999999999 days; `now - timedelta` overflows far past 36500). Anyone who wants "archive nothing, ever" uses 36500: harmless. The comment in store.py says "Above timedelta's range ... raises OverflowError"; the bound is much lower than that range, so the comment overstates the reason (LOW wording).
3. Mutant S9 (cutoff computed late again) survives: with days already capped at 36500, `now - timedelta(days=...)` cannot overflow for any realistic `now`, so moving it back is behaviourally equivalent today. The "before anything is created" ordering is defence in depth only; no test can pin it without a `now` near datetime.min.
4. The NUL case relies on `Path.resolve()` raising ValueError, which is a CPython behaviour (here: this environment's Python); a different version could raise something else (not verified on other versions; LOW).
Steelman: before the change `days=10**12` raised OverflowError after the archive directory had been created (a 500 with a side effect), and a NUL in archive_dir was a 500; now both are 422 (CLI exit 2) with fixed text, nothing is created, and archive semantics for valid input are pinned unchanged (days=0 still archives segments 1 and 2).
