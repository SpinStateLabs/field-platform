## OBJECTIONS FIRST
1. F-C427-1 MEDIUM-LOW (the same bug survives one type over, unchanged by this PR): two ISO STRINGS still compare as text. `_later("2026-10-28T14:30:00+02:00", "2026-10-28T13:00:00Z")` is True although 14:30+02:00 is 12:30Z, earlier than 13:00Z; `_later("...Z", "...+00:00")` for one instant is True. The fix covers mixed types only (as the card words it), and `a > b` for two strings is the old behaviour the card asks me to confirm unchanged. If the events API ever returns strings with differing offsets, the cursor can move back. In production the SDK returns datetimes, so I do not know of a path; stated because the commit message and docstring read as if instants are always compared.
2. F-C427-2 LOW-MEDIUM (mixed offsets are not pinned): every aware value in the new tests is UTC. The mutant that overwrites the timezone with UTC even for an aware value (`moment.replace(tzinfo=utc)`) survives all 259 tests. Behaviour today is correct (probed: aware +02:00 14:00 equals the string `...12:00:00Z`; `...14:30:00+02:00` against UTC noon is later; `...08:00:00-05:00` against UTC noon is later), but the card named "mixed offsets" and nothing pins it.
3. LOW (small pins that stop short): the int-versus-datetime assertion is `in (True, False)`, which can never fail except by an exception, so the mutant that reads a number as an epoch time survives; surrounding whitespace on the string (`strip()`) and a lower-case `z` suffix are untested; the same-type string comparison is not pinned as "direct", so the mutant that always converts (which would change the same-type behaviour of F-C427-1 for the better) survives.
4. EQUIVALENT: the `Z` branch of `_as_datetime` (Python 3.11 and later, which `requires-python` demands, parse `Z` themselves; the mutant that drops the branch survives, the mutant that reads `Z` as +01:00 is killed); `>=` instead of `>` on the direct and fallback paths (an equal time assigns the same cursor value); `except Exception` for `(TypeError, ValueError)` and an outer `except (TypeError, ValueError)` (no ValueError can come from the first comparison).
5. Behaviour change worth knowing: a naive datetime against an aware one used to raise inside `a > b` and fall to text; it is now compared as UTC. That reads a naive time as UTC, an assumption (the same one the docstring states). If the API ever returned naive local times this would mis-order them; I do not know of such a case.
