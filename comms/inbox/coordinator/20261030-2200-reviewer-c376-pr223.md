Correct fail-closed direction, but the only symptom outside the gateway is that error at request time; there is no startup message in the sentinel, the crosswalk or the hygiene judge. F-C376-5 LOW.
3. The refusal message echoes the value: `{name}={os.environ.get(name,'').strip()[:40]!r}` (up to 40 characters, case preserved). A secret pointed at the flag by mistake lands in the traceback. Same class as my C-374 F-C374-1. F-C376-2 LOW.

Three semantics for an unrecognised posture value now coexist: the ledger reads it as OFF (`FIELD_LEDGER_REQUIRE_SIGNING`, `FIELD_LEDGER_REQUIRE_CALLER_SIGNATURE`, both still documented as "any other text leaves it OFF" in the overlay), `FIELD_OPERATOR_REQUIRE` reads it as ON, the gateway and (PR 221) the sentinel refuse to start. F-C376-4 LOW.

## METHOD NOTE (affects earlier reports of mine)
My first mutation pass in this review gave 30 "kills" that were all caused by a stale `__pycache__`: the original file restored within the same second as a same-size mutant was served from the mutant's cached bytecode, so even the unmutated baseline failed. I caught it because the baseline failed, deleted the caches and re-ran with `PYTHONDONTWRITEBYTECODE=1`; the numbers above are from that valid run (one mutant, "no lower", gave 6 passes before and 4 passes after, the visible difference). My earlier harnesses (C-374, C-354, C-360, C-351 and others) did not set that variable: a same-size mutant run within a second of another could have used a stale cache. Their baselines were green afterwards and the kills were plausible, so I do not believe a verdict changed, but the same-size mutants in those reports (for example the mode-bit mutants `0o600` to `0o644` in C-354) are lower confidence. I can re-run any of them with bytecode off on request.

## FINDINGS
- F-C376-1 MEDIUM-LOW (PROVEN): before any estate takes this change, read its effective `FORCE_GATEWAY_ENFORCE` and `FORCE_GATEWAY_TOOL_CHECK` (the GB10 `.env`, the Fly environment). `1` or unset or `0` or a recognised false: no change. `true`, `yes`, `on`, a padded `1`: the gateway becomes ENFORCING at the next restart (with `FIELD_SENTINEL_URL` unset that means 503 on every call); an unrecognised text: the gateway will not start. Put the check in the deploy runbook (the A10 and A11 steps).
- F-C376-2 LOW: do not echo the value in `InvalidPostureFlag` (length and the first 8 characters at most, or only values matching a plain-word shape).
- F-C376-3 LOW (stale text and a traceback): the comment in `create_app` ("never a process exit", about line 810) and `docs/runbooks/v1.2-deploy-rollback.md:75` ("FORCE_GATEWAY_ENFORCE read it as OFF ... exactly 1 for the gateway") are now wrong; and `forcegw serve` should turn `InvalidPostureFlag` into a one-line `error:` exit with code 2.
- F-C376-4 LOW: bring `FIELD_LEDGER_REQUIRE_SIGNING` and `FIELD_LEDGER_REQUIRE_CALLER_SIGNATURE` (still "any other text leaves it OFF") onto the same helper, and decide the library-versus-service rule once (a card).
- F-C376-5 LOW: log one warning at first use when field-core reads an unrecognised `FORCE_GATEWAY_REQUIRE_TLS_UPSTREAM` as armed, so a judge client failing with `InsecureBaseURLError` points to the cause.
