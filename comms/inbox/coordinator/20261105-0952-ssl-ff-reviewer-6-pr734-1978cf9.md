## Objections first (FORCE-O)
1. The ValueError and RecursionError clauses are live but unpinned. Measured on the head with `FederationClient.request_body`: a set and bytes give the new ValueError (TypeError inside); a self-referencing mapping gives it with "ValueError: Circular reference detected"; a 60,000-deep nested mapping gives it with "RecursionError: maximum recursion depth exceeded". Yet S3 (ValueError not caught) and S4 (RecursionError not caught) both survive the five tests, which exercise only a date and a datetime (both TypeError). LOW test gap; the code is right.
2. `json.dumps` is a weak definition of "serialisable" for what the broker needs: `float("nan")` and mixed-type keys (`{1: "a", "b": 2}`) both pass the check (measured: OK for each), although the former is not valid JSON and the latter becomes a string key. Not this PR's claim (it fixes the date case); worth knowing for the S6-18 neighbourhood (PR 718: NaN verifies there too). LOW.
3. The message carries the exception's own text. For these cases that text names a TYPE (`Object of type date is not JSON serializable`), not the value, so nothing from the manifest leaks; S12 (drop the text, keep the class) survives, so the wording is unpinned (LOW). The path of a manifest file IS echoed (`the manifest at <path>`), which is the caller's own argument.
4. `raise ... from None` is not pinned (S8, chaining kept, survives): the original traceback is hidden, which matches "a caller error, not an unreachable broker".
Steelman: YAML turns an unquoted `expiry: 2027-01-01` into a `datetime.date`; the JSON body could not carry it, the post failed inside the transport wrapper, and the caller was told "federation-broker unreachable" although no request had been made. Now it is a ValueError that names the manifest (path or "the manifest"), the exception class and the fix ("quote dates and timestamps"), raised before any request (the recorder shows zero posts), the CLI prints one `error:` line with exit 1, and it is not a `CrossingBlocked`.
