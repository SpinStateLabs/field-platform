## Objections first
1. ANY 8-DIGIT SUFFIX IS A "DATE": the fallback is `re.fullmatch(r"(.+)-(\d{8})", key)`. I probed a book priced `acme-1`: `acme-1-20260101`, `acme-1-99999999`, `acme-1-00000000` and `acme-1-20261399` (not a calendar date) all resolve to the `acme-1` price. A build number or an id with eight digits that is not a snapshot date is priced as its base. The test pins "not an 8-digit date" only for `acme-1-2026`. For a spend meter this is "price it somewhere" rather than "unpriced and escalate"; the PR's reason (the live outage of 2026-09-14, in the code comment) is real, but the rule is wider than the reason. MEDIUM.
2. THE OLD SAFETY NET IS WEAKER BY DESIGN: a model id not in a custom book used to be unpriced, which opened a `usage:unpriced` escalation (the comment says so); a dated variant of a priced base now silently takes the base price. If a dated snapshot has a different price from its base (providers sometimes price snapshots differently), the meter under- or over-counts without an alert. I do not know any such case for the models in the default book. MEDIUM-LOW.
3. THE EXACT KEY WINS: an exact dated key in the book is used before the base (pinned by `test_an_exact_dated_key_in_the_book_wins_over_its_base`, mutants f6 and f7 killed). Good.
4. KEYS ARE NORMALISED AT CONSTRUCTION, so a book written with `claude-haiku-4.5` is stored as `claude-haiku-4-5`; any code that reads `book.prices` by the original spelling now misses (the default book is unchanged, pinned). I did not search the other services for such readers. LOW.
