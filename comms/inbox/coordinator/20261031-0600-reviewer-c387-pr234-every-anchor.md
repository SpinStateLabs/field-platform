OBJECTIONS FIRST
1. F-C387-1 MEDIUM-LOW (design consequence, PROVEN with a fake fetcher): a page that is a reading but lacks one cited identifier flags the framework stale on EVERY run, and after a named `clear` the next check flags it again; evidence packs are blocked while the flag stands and the pack generator has no override by design. So a source that merely spells one identifier differently ("Articles 12 and 14", "Art. 12", an identifier inside another word such as "Article 12a") puts pack generation into a loop that only a change to the mapping's cited identifiers (a code change and re-ingest) ends. The README says this ("flagged again after a `clear` until the mapping is re-ingested"; "the first live check ... can flag a page that spells a cited identifier differently"); it gives no operator procedure. I would require one sentence in the README or runbook before an estate takes this: what to read (`regwatch check` without `--fetch` lists the anchors per URL; the reason names the missing identifiers), and that the fix is changing the identifier in the mapping, not clearing. [HIGH, run]
2. The alternative the builder rejected is not as bad as the PR body says. With "all or unreachable" a page missing one identifier would read `unreachable (anchor missing)`: no flag and no block, the last good hash kept; the drop is not invisible (the check exits 2 and names the URL on every run) but it does not stop packs, which is the whole point of the card ("a page that drops cited articles raises the staleness flag"). So the builder's reading of the card is the one that does what it says; the cost is finding 1. [HIGH]
3. The first reading is no longer a clean baseline when an identifier is missing: it flags at once (README and PR body say so). A fresh estate whose first check meets a differently spelled page starts with a blocked pack. [HIGH, read]
