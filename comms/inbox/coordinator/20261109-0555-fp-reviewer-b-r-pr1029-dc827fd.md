## Optional LOWs (new PR, not conditions)
1. The docstring says a file written by PowerShell `Out-File` (or `>`) carried the BOM. Windows PowerShell 5.1 writes UTF-16LE with `Out-File` and `>` by default (general knowledge, MEDIUM-HIGH; I did not run PowerShell here), and that file is still refused (measured above). `Set-Content -Encoding utf8` in 5.1 does write a UTF-8 BOM. Correct the docstring, and decide whether UTF-16 should be read or refused with a clearer message.
2. G8: no CRLF test; Windows-written files end in `\r\n`, and `.strip("\n")` would leave a `\r` in the header. The code is right; the test does not pin it.
3. G5: the invalid-UTF-8 path of direction 2 has no new test (existing tests may cover part of it).
4. The CLI error line prints `{exc}` for decode errors (it names one byte value and position, no secret text). Pre-existing, unchanged by this PR.
