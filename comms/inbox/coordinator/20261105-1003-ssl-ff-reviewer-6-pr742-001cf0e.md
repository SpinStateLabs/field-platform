## Objections first (FORCE-O)
1. The PR does more than bound text: it also narrows two VALUES. `currency` must match `^[A-Z]{3}$` and `on_breach` must be `halt` or `escalate` on PUT /caps (it was any string). A client that stores another currency spelling or another breach action is refused (422) from now on. The code comment says the two breach values are "the two the manifest schema documents"; I checked the repository's manifests: every `on_breach:` in manifests/ and the shipped templates is `halt` (nine hits, one with a trailing comment), so no shipped manifest breaks; `FieldManifest.on_breach` itself is a free `str | None` (field_core/manifest.py:109), so a manifest can still carry any value and `set-cap --from-manifest` would then be refused by the governor. That is stated nowhere in the PR (MEDIUM for compatibility; the rule's source, "the manifest schema documents", I did not find as a written schema).
2. The blank-id test is vacuous. `test_blank_agent_id_refused` sends `put_cap(client, "x", agent_id=agent)`: the path id is `x` and the body id is blank, so the request is refused by the pre-existing rule "agent_id in path and body must match" (422) whether or not the new bound exists. Mutants Y5 (id not stripped) and Y6 (`min_length=0`) both survive the 17 tests and the whole suite (308 passed). The 128/129 boundary is tested properly (Y1, Y2 killed). LOW test gap.
3. The read side stays lax on purpose (a stored 300-character id and a lower-case "usd" still load and are served; the legacy-row test pins it, including `/status`). That keeps old data readable but means a row that PUT would now refuse can still be GET and be acted on (`on_breach: ignore` stays `ignore`); stated in the docstring ("stored and returned but no code path acts on it today").
4. A 422 for a too-long id does not echo it (the test asserts the 129-character id is absent from the response text); with the no-echo handler this holds for the three routes.
Steelman: the three PUT bodies accepted unbounded ids, actions and currency, so one request could store an arbitrary long string in the caps, policies and rate-limits tables; now the ids are stripped, non-blank and at most 128, actions at most 200, and a legacy row is not locked out.
