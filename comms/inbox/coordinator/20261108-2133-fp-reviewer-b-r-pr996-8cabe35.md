## Condition C1 (HIGH, measured on the head)
The validator message and the commit text say action and token_id "must be one line with no control characters". The check is `ord(c) < 32 or ord(c) == 127`. Probe of POST /api/check on the head, all forwarded to the sentinel with 200:
| Input | Result |
|---|---|
| action `a\u2028b` (LINE SEPARATOR) | 200, forwarded |
| action `a\x85b` (NEL, a line break) | 200, forwarded |
| action `a\x9fb` (C1 control, Unicode category Cc) | 200, forwarded |
| action with U+200B zero width, U+202E bidi override | 200, forwarded |
Rejected as intended: DEL (0x7f), TAB, newline, bell, CR/LF in token_id, empty token_id.
Sibling code in this repo uses Unicode categories for the same job (attestation-reporter org.py, crosswalk evidence_pack.py / regwatch.py / staleness.py use `unicodedata.category`, with Zl/Zp/Cc/Cf refused). Fix either by refusing categories Cc, Zl, Zp (and Cf if wanted) or by correcting the message and commit text to "below 0x20 and DEL only". A test for U+0085 and U+2028 is needed either way (mutant D19, which rejects C1, survives).
Not a security hole by itself: the ledger stores JSON, so these characters are escaped there (MEDIUM, I did not trace the ledger write path in this review).
