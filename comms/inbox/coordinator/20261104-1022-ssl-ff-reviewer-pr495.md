## Objections first (FORCE-O)
1. Falling back silently is a policy choice: a typo in FORCE_GATEWAY_LATENCY_BUDGET_MS or FORCE_HYGIENE_BAND now runs the default and says nothing. The sibling settings in this file refuse to start on a typo (FORCE_GATEWAY_ENFORCE, C-180). Nothing is logged on fallback in the diff (api.py:250-270), so an operator who mistyped will not learn it (F1). Steelman for the PR: a hygiene or budget knob is a tuning value, not an authority switch, and the scout's own failure was a crash or a NaN that disabled drift detection; falling back to a safe default matches FORCE_GATEWAY_SENTINEL_TIMEOUT and FORCE_TELEMETRY_WINDOW, which already behave this way. I accept the choice.
2. A band of 0 or a budget of 0 may be a deliberate setting ("alert on any drift", "always bypass"); both now silently become the default. The tests pin this refusal on purpose ("0" is in the cases). It is a documented-by-test behaviour change; C1 makes the docs say so.
3. No upper bound: FORCE_HYGIENE_WINDOW=1000000000 is accepted. I did not check what DriftTracker allocates for a window (not in source), so I do not know whether that is a memory risk. LOW.
