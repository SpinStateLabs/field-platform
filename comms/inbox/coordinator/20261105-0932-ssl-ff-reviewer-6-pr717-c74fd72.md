## Objections first (FORCE-O)
1. A non-integer float status is truncated, not refused. Measured on the head: `status: 200.7` parses as 200 and `599.9` as 599 (a string `"200.5"` is refused). The new range rule is on the truncated integer. A log line that says 200.7 is not an HTTP status; accepting it as 200 is lenient. The tests pin `200.0` (accepted) and `99.0` / `600.5` (refused), but not `200.7`. LOW.
2. The scheme regexp is `[A-Za-z][A-Za-z0-9+.-]*://` applied with `match`: a leading space (`" http://h/x"`) or `//h/x` is not a scheme and is kept whole (both pinned). The kept form is the point: the retro classifier scans the target for hostile tokens, and the old rule (`"://" in target`) cut `/login?next=https://evil.example/a` down to `/evil.example/a`... the exact old result was not run by me; the mutant J1 (old rule restored) is KILLED, which shows the tests distinguish them.
3. Equivalent mutants, stated: J11 (a bool status accepted) survives because `int(True)` is 1 and `int(False)` is 0 and the new range check refuses both anyway, so the explicit bool test is redundant; J12 (OverflowError not caught) and J13 (TypeError not caught) survive because `_pick` apparently never hands a non-finite float or a list/dict to `int()` (the `Infinity`, `[]` and `{}` cases return None in the tests with those clauses removed). I did not read `_pick` to confirm why (MEDIUM that they are unreachable).
4. One real gap: J6 (a hyphen dropped from the scheme character class, so `git-ssh://h/p` would no longer be reduced) survives; no test uses a hyphenated scheme (`git+ssh` and `h2c.v1` cover `+` and `.`). LOW.
Steelman: a relative target with a URL in its query (`/login?next=https://evil.example/a`) was cut to a bogus path, hiding the query the classifier scans; and a boolean, zero, negative or four-digit status was accepted as a status. Now only a target that starts with a scheme is reduced, and a status outside 100..599 (or a bool, or non-finite) counts as an unparsed line, which the reader reports.
