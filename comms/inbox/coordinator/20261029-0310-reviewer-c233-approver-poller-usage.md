# C-233 reviewer report (Lane 5): services/claude-approver poller, cursor, usage guards and map-shape validation on main 10fb197

VERDICT: no path approves a tool call without a sentinel call: the only producer of "allow" is `Approver._check` (core.py:372-418, the one place that posts to the sentinel), every other branch of `_answer` produces a deny, and an unmapped agent, an unreadable secret, a missing tool name and every sentinel failure deny. Two paths can check an event twice (a retried send that the API had already applied; a rejected batch split) but the second send is rejected by the API and no second approval lands. The mutation round (140 mutants) kills 83; the 57 survivors are 11 equivalent, 19 return values that only feed summary counters, and 27 real test gaps, the ones that matter being the two layers that decide which open asks are answered (L530, L588), the cursor-advance rule (L555), the usage clamp (L765) and the map-shape validators in config.py. The approver is a pilot service that is not part of a plain `up` (its README); I looked at no estate.

OBJECTIONS FIRST
1. The mutation sample is mechanical and random (140 of 250-odd candidates, seed 233005) over core.py 196-232, 440-640 and 740-800 and config.py 140-270; the heartbeat, `halt` and the rest of the module were mutated by C-156 or not at all. The tests use the repo's fake Console API (`approver_fakes.py`); the real Managed Agents API semantics are not in the repository, so anything that depends on them is marked "I do not know". [HIGH]
2. The cursor (core.py:555) stores each event's `processed_at` and the next read asks `created_at_gte=<cursor>` (core.py:515-516). Whether an event created before the cursor can become visible later (created earlier but processed later) is a property of the platform's ordering that I cannot read here: I do not know. If such an event exists it would be skipped for good. [LOW: unknown]
3. The whole suite is 101 tests in one second; surviving mutants in a module this small are cheap to kill, which makes each gap below easy to close. [HIGH]

ASSUMPTIONS
1. main 10fb197, services/claude-approver suite 101 passed; Python 3.12. [HIGH]

REASONING
1. Approval only through the sentinel. `Verdict("allow", ...)` appears once in `core.py`, inside `_check` (:418), after a `POST {sentinel}/check` and only when the sentinel's decision is ALLOW. `_answer` (core.py:608-650) builds a deny for each of: an agent entry with a problem ("unmapped"), a tool map error, a missing tool name, an unreadable estate secret (`headers is None`), a sentinel timeout, an HTTP error, a malformed answer. The confirmation `result` is `verdict.result`. Nothing else sends `"result": "allow"`. [HIGH, read]
2. Processed twice, case 1 (retry after an unknown outcome): `_send` (core.py:668-700) returns "retry" for a 5xx, a transport error, 408 or 429; the confirmation might have been applied server-side. The next tick has the ask still open (`state.answered` is set only after an observed success), so `_answer` calls `_check` again (a second sentinel `/check`, its ledger row, and for the metered case a second metered row) and sends again; the API then rejects the duplicate with a 4xx, which the approver treats as terminal (`confirm_rejected`, the ask is stale). Result: two sentinel checks and one effective approval. The existing test pins the 4xx path (6 ticks, 1 check); the retry-then-already-applied sequence is not tested. LOW-MEDIUM. [HIGH on the code, MEDIUM on the API behaviour]
3. Processed twice, case 2 (re-reading the boundary event): the read uses `created_at_gte` (inclusive) so the newest event comes back on the next read; `state.seen` (core.py:523) prevents reprocessing. The mutant that weakens that test (L523 `or` to `and`) survives: no test delivers a duplicate event id. Effect if it broke: `state.seq` and `ask_seq` would advance on a re-read, which could let a stale ask escape `_drop_superseded` (:605). LOW-MEDIUM. [HIGH on the survivor, MEDIUM on the effect]
4. Skipped: (a) the `fresh` shortcut (core.py:560-570) skips reading events when `updated_at` is unchanged, there are no open asks and the last read was under 60 s ago; a new ask that does not move `updated_at` waits up to 60 s (stated as Declared in the README). Mutant L567 `<` to `<=` survives (a boundary that cannot matter). (b) the cursor question in objection 2. (c) `elif etype == "user.custom_tool_result"` (L541) forced False survives: without it `state.customs` is never cleared, so a session that had a custom tool use never gets its asks answered again (the code returns 0 while `customs` is non-empty): a fail-safe stall, not an approval. [HIGH]
5. Which open asks are answered: two independent layers decide it. Layer 1 (`_read_events` :528-531) adds an event to `state.asks` only when `evaluated_permission == "ask"` and it is neither answered nor stale; layer 2 (`_approve_session` :586-594) answers only asks the latest `requires_action` idle lists in `stop_event_ids`, or all open asks when that field is absent. Mutating either layer alone survives (L530 `and` to `or` in layer 1; L588 `if stop_event_ids is None` forced True in layer 2) because the other still holds; both together would answer a tool use the platform already allowed or denied, or one the session is not yet blocked on. Each answer still goes through `_check`, so this is an ordering and noise risk, not a sentinel bypass. Two tests exist for the first layer (`test_allow_and_deny_events_are_never_confirmed`) and none distinguishes the layers. MEDIUM-LOW test gap. [HIGH]
6. Cursor advance (L555 `if processed is not None and (cursor is None or later)` with `and` to `or`) survives: the cursor could move backwards or take None; effect is re-reading older events (deduplicated by `seen`), so LOW. [HIGH]
7. Usage guards (core.py:748-800): `_usage_snapshot` normalises each counter with `int(v) if isinstance(v, (int, float)) and v >= 0 else 0` (L765). The mutant `and` to `or` survives: a negative counter would pass through as a negative value and the delta posted to the governor would be negative, which the governor refuses (`UsageRequest` bounds): a failure counted every tick (`usage_failures`), not a wrong figure. The `if snap is None` guard (L774, forced False) and the return values of the snapshot and post helpers (L758, L761, L771-798, 19 mutants) survive: the helpers' return values feed only the `usage_posts` summary and the next guard. LOW. [HIGH on the survivors, MEDIUM on the governor behaviour]
8. Cursor file (UsageCursor, core.py:200-262): a missing file starts empty; an unreadable file sets `error` and disables posting; an unparseable or wrongly shaped file sets `error` and disables posting rather than starting from zero. The persist-then-advance order in `set` (write temp, `os.replace`, then assign) is what the README states. L198 mutants are docstring words. Survivors there: none of substance. [HIGH]
9. `client is None` (core.py:471-472, `if client is None: return`): killed; with no client the tick records nothing and posts nothing. `archived_at` (:493): `if _get(session, "archived_at") is not None: continue` killed (an archived session is never touched). [HIGH]
10. config.py map-shape validation (140-270): survivors are 11 gaps: `read_secret_file` returning None for an unreadable or empty file is not distinguished from False/True/1 (L151 three, L155 two); an `estate_base_url` that is not a string (L180) or is None (L183); a top-level agent map that is not a JSON object (L215); a blank key (L221); the leading-brace test for a file that is not JSON (L233); `parsed is None` (L265). Each bad shape is refused or skipped on the unmutated code (a single bad entry is kept as `AgentEntry.problem`, so that agent denies); the tests do not pin these branches one by one (C-163 covers the same ground as a builder card). [HIGH on survivors, MEDIUM that each branch behaves as designed]

CONCLUSION
The approval path is as safe as `_check` and the sentinel behind it; the weakest points are the unpinned selection layers and the retry-then-applied sequence. Proposed cards (coordinator numbers them; C-163 and C-164 already exist for neighbouring gaps):
- P1 builder MEDIUM-LOW, services/claude-approver/tests: a test per layer: (a) a tool use whose `evaluated_permission` is allow or deny, with an idle event that lists no event ids, is never answered (kills L530); (b) an ask that arrives after the idle event and is not listed in its `event_ids` is not answered (kills L588); (c) a duplicate event id delivered on two reads is processed once (kills L523); (d) a `custom_tool_result` clears the pending custom use (L541). Done when those four mutants go red.
- P2 builder LOW-MEDIUM: a `retry` outcome whose send had been applied: the next tick must not approve twice and should say it was a duplicate; decide whether to remember a "possibly sent" confirmation across ticks so the sentinel is not asked twice. Done when a test with a first send that raises after applying shows one effective approval and a counted duplicate.
- P3 builder LOW: pin the usage clamp (negative and non-numeric counters give 0 or refuse), the cursor-advance rule (L555), the 2xx boundary (L441) and the `snap is None` guard; and the config shapes in item 10 (some are already C-163).
- P4 coordinator/docs: add to the README's Declared list that the event cursor assumes the platform lists events in processing order (objection 2).

What I did NOT do: read `halt`, `heartbeat` or the SDK client; mutate the sentinel side; test against the real Managed Agents API; look at any estate.
