## Objections first (FORCE-O)
1. The two halves of this PR are tested unequally. The bundle test records `os.fstat(fd).st_size` at each fsync, so it proves the handle was flushed first: removing `flush()` (B2) is KILLED. The usage-cursor test records only the ORDER of fsync and replace, so removing `flush()` (U2) survives the PR's file and the whole claude-approver suite (319 passed). That is the same gap I reported on PR 645 (`fh.flush()` unpinned): without the flush the fsync syncs an empty buffer and the bytes are written after it. The fix is the one the bundle test already uses. LOW as a test gap; the code as written is correct.
2. The directory fsync after the rename is untested here too: U7 (removed), U8 (an OSError from it no longer swallowed) and U9 (the directory descriptor not closed) all survive the file, and U7 also survives the whole claude-approver suite. The comment says it is best effort; nothing proves it happens. LOW.
3. The cleanup clause catches `BaseException` (right for a full disk and an interrupt), but U6 (only `OSError`) survives: no test interrupts the write with a non-OSError. LOW.
4. The cursor still raises after a failed write (the tests assert `pytest.raises(OSError)` and that memory is unchanged, U11 killed), so the caller sees the failure; a persistent failure to write the cursor means re-posting usage after a restart, which is what the change exists to limit (HIGH, from the docstring).
Steelman: `UsageCursor.set` promises that a restart never re-posts a delta the governor already has; the old `write_text` then `os.replace` could leave an empty or partial cursor after power loss, and a failed write left `tmp-<pid>-<tid>` files behind. Now the file is written through an open handle, flushed and fsynced before the rename, cleaned up on any failure, and the export bundle's four files (chain_proof, events, signature, summary) are flushed and fsynced too.
