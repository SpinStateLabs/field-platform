POST /operator/verify-hash with the read key answers 401, as designed. Confidence HIGH (observed).
2. So PR 374 is the only thing standing between a read key and rotation-state, and only when its secret is configured. With FIELD_INTERNAL_SECRET set (or its hash), rotation-state needs `x-field-internal` in addition: read key alone 404; read key plus the right internal header 200 (probe). That is the intended composition: the read tier never reaches the internal routes without the second secret. But neither PR makes it the default, and the combination is not tested together (each PR's tests ran on its own tree; the merged tree's two test files plus the operator-health tests pass: 101). Condition C1. Confidence HIGH.
3. Can one authorise what the other forbids? PR 374 only narrows (an added header check inside the route); PR 369 only widens the set of callers that pass the perimeter for safe methods. They compose by AND: the perimeter first (369), then the route's internal check (374); I found no path where 374 admits a request the perimeter refused. The reverse (369 admitting something 374 forbids) happens only through objection 1 when 374 is unconfigured. HIGH.
4. A read key and the internal secret are never confused by the code: they travel in different headers (x-field-auth, x-field-internal); presenting the read key or the full key as the internal header gives 404; presenting the internal secret as x-field-auth is refused at the perimeter. Nothing stops an operator setting FIELD_INTERNAL_SECRET equal to the full key (accepted; with both headers equal it passes) or to the read key; PR 369 refuses read equal to full at install, PR 374 has no equivalent check. LOW-MEDIUM.

The route is "absent" (404) rather than 401 on a bad header, hiding the route's existence. Confidence HIGH.
