## Objections first
1. CRASH BETWEEN LEDGER AND STORE LEAVES THE TOKEN ACTIVE AND A RETRY WRITES A SECOND EVENT WITH A NEW ID. In delegation_authority/api.py:389-401 the ledger append precedes `save_revoked`. Probe (store raising once after a successful append): first call fails, introspection reports the token `active`, the retry returns 200, and the ledger holds 2 delegation.revoke events with 2 distinct revocation ids; the stored id is the second. The commit message says "one id, one event"; that holds only for the no-failure path. The ledger-first rule is the right order for an audit trail, but then the guarantee has to be stated as "at least one event, the last one wins". HIGH (observed).
2. TWO PROCESSES: BOTH APPEND, ONE ROW WINS. Probe with two apps on one store file and one ledger, each ledger call delayed 0.3 s: both callers get the same (winner's) id back, the ledger holds 2 events, and one of the two events carries an id no token stores. The comment at api.py:380-382 admits it; `_won` is discarded at api.py:401, so the loser cannot even log the orphan. Anyone reconciling ledger events against token rows will find a revocation id with no token. HIGH (observed).
3. ONE LOCK, NETWORK CALL INSIDE. `app.state.revoke_lock` (api.py:140) is process-wide, not per token, and is held across `ledger.append` (api.py:391-399). Probe: ledger delayed 1.0 s, two revokes of two different tokens in one process complete at 1.02 s and 2.03 s: serial. In an incident, revoking N tokens costs N times the ledger latency, and a hung ledger blocks every revoke up to the client timeout while holding the lock. The comment says "one revoke of a token at a time"; the code is "one revoke at a time". HIGH (observed) on behaviour; whether it matters depends on the client timeout, which I did not read. MEDIUM.
4. /introspect DISTINGUISHES UNKNOWN FROM REVOKED. An unknown id returns status `revoked` with reason "unknown token id — treated as revoked (fail closed)"; a known revoked id returns "token is revoked" (api.py:410-415 versus 423). The oauth endpoint returns `{"active": false}` for both. A caller of /introspect can enumerate which ids exist. The oauth route documents "must not leak WHY"; /introspect makes no such claim. LOW (observed).
5. A TOKEN ROW CAN NOT BE FOUND THEN REVOKED BETWEEN THE FIRST GET AND THE LOCKED RE-READ WITHOUT A REGISTRY RE-CHECK: the list-bound reach check runs on the pre-lock read (api.py:343-376). The token's agent_id cannot change, so the check stays valid. No defect; noted so it is not re-raised. HIGH.

## Steelman
The in-process race is closed and tested (the PR's 16 tests pass; M1 and M3 below go red). A conditional UPDATE means a second process cannot overwrite the winner's id (observed), the returned id is always the stored one, and a ledger outage refuses 502 with the token still active (PR test; fail-closed on the write, which is the documented rule). Revoking an already-revoked token writes nothing.

## Recommended structural fix
Make the idempotency key the ledger event, not the row: derive `revocation_id` from the token id (for example a keyed hash) so a retry or a loser writes the same id, or have the ledger append take an idempotency key. Lock per token id. State the guarantee in the docstring as at-least-once with a stable id.
